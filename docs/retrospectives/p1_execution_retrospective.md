## 1. 文档目的

本文完整记录 P1 从问题识别、方案设计、实现、真实评测到性能收敛的过程，重点说明：

- P1 试图解决的核心问题以及最初质量基线。
- Model、RAG、Web 三类来源如何从并列输出调整为声明级研究闭环。
- RAG 策略如何从人工加权召回逐步演进到分层检索、语义重排和证据对齐。
- 实施过程中出现过哪些设计错误、实现缺陷、评测偏差和工程流程问题。
- 各类问题是如何被发现、定位和纠正的。
- 成本、延迟、质量之间如何权衡，以及最终验收闸门如何关闭。

本文以仓库中的真实代码、测试和评测产物为依据。历史评测中使用的 DeepSeek、MiniMax、Qwen 等模型只代表开发测试时的用户配置，不代表产品默认绑定。Gemini 因实测成本偏高已经暂停使用。

## 2. 背景与初始基线

### 2.1 P1 之前的系统形态

P0 已经解决了一批基础可用性问题，包括：

- 论文评审批次失败不再导致整批候选被跳过。
- Web 主 provider 失败时可以执行降级搜索。
- 中文问题可以通过双语扩展召回英文论文。
- 报告优先展示回答，而不是先展示失败原因和可信度说明。
- 全文状态、章节信息和评审错误能够被追踪。

但 P0 之后的研究查询仍然主要是三个来源分别产生结果，再由综合节点进行整合。系统更关注“各 Agent 是否返回”和“报告格式是否完整”，没有真正验证最终答案是否完整、准确、可引用和可修订。

### 2.2 冻结失败样本

P1 选择“当前地理处理自动化研究存在哪些局限性”作为首个真实回归样本。P0 后的冻结基线为：

| 指标 | 基线结果 |
|---|---:|
| 报告质量 | 2/5 |
| 来源可靠性 | 2/5 |
| 关键声明外部引用覆盖率 | 0% |
| FactCheck | `needs_review` |
| 总耗时 | 约 193 秒 |

之后一次 Standard/full 复测的机械评分已经达到 4.2/5，关键声明引用覆盖率达到 66.7%，无效引用为 0，耗时约 145 秒、约 62.4k Token。但是独立盲评仍然只有 2/5，FactCheck 仍为 `needs_review`。

这暴露出两个关键事实：

1. 格式、篇幅、关键词和来源数量无法代表真实研究质量。
2. 系统可能已经召回证据，但没有把证据正确转化为最终答案。

### 2.3 最关键的诊断发现

RAG 审计中实际出现了 ShapefileGPT 的 26 个全文块，但最终答案仍写成“未获取直接文献”。原论文也确实包含计算成本、错误处理、幻觉、任务覆盖、调试和数据适用性等局限内容。

因此，失败不能归因于“知识库里没有答案”。真正的主要瓶颈位于：

```text
候选召回
  -> 证据片段选择
  -> 可引用事实提取
  -> 声明与证据对齐
  -> 跨来源综合
  -> FactCheck 后修订
```

这次诊断改变了 P1 的实施方向：不再把主要精力投入到增加 Agent 或简单扩大 Top-K，而是建立端到端的声明级质量闭环。

## 3. P1 的目标、原则与范围

### 3.1 成功定义

P1 不再把“搜索成功”“三个 Agent 都返回文本”或“报告章节齐全”作为研究查询成功，而是要求用户得到：

- 对问题有直接回应的完整答案。
- 足够的研究广度、分析深度和时效性。
- 能定位到正文片段、章节、页码或 URL 的证据。
- 对证据不足、来源冲突和模型推断有准确边界。
- FactCheck 发现实质问题后能够真正修订答案。
- 质量、成本、延迟和降级路径均可观测。

### 3.2 核心原则

1. **三源互补而非投票**：Model、RAG、Web 提供不同能力，不要求三者多数一致。
2. **声明中心而非来源中心**：先确定要表达的声明，再为声明绑定证据和限制。
3. **单源可以成立**：一个直接、权威的来源可以比多个低质量转载更可靠。
4. **缺源不等于拒答**：某个来源失败时保留其他来源的最佳答案。
5. **冲突才需要仲裁**：来源缺失或关注点不同不等于事实冲突。
6. **回答优先**：详细 Trace、评分和核验记录放入审计产物，不淹没主答案。
7. **确定性逻辑与语义判断分工**：格式、安全和硬门禁由程序判断，相关性、证据质量和分析深度由模型判断。

### 3.3 明确非目标

P1 没有提前建设 SQLite Run Store、持久 Job、跨进程恢复、微服务、多租户或自动永久入库。本轮新发现的论文不会未经用户确认自动写入永久知识库。

## 4. 总体执行过程

### 4.1 第一阶段：建立评测和运行预算

首先建立了独立的 P1 评测集和执行器：

- 30 个研究问题。
- Quick、Standard、Deep 三个深度档位。
- full、model_only、rag_failure、web_failure 等 6 类场景。
- 共 540 个运行组合的离线矩阵。
- RAG 专项标注集和独立检索评测脚本。
- 答案质量、引用质量、来源覆盖、延迟、Token、重试和降级指标。

540 个组合用于验证场景覆盖和执行器契约，默认不全部调用真实 API。真实调用只选择代表性样本，避免把预算消耗在形式化跑满矩阵上。

同时为模型调用增加：

- 运行级硬截止时间。
- 共享 Token 预算。
- 调用前输入、输出预算预留。
- fallback、重试和实际模型记录。
- 超时后停止继续发起高成本步骤。

### 4.2 第二阶段：建立运行内研究协议

P1 新增或扩展以下结构化协议：

| 协议 | 作用 |
|---|---|
| `ResearchPlan` | 记录原问题、子问题、来源偏好、预算和停止条件 |
| `ClaimDraft` | 记录候选声明、类型、重要性、时效性和待核验状态 |
| `EvidenceItem` | 记录来源身份、正文片段、定位、直接性和证据关系 |
| `SourceCoverage` | 记录每个子问题在不同来源中的覆盖、失败和缺口 |
| `ClaimAssessment` | 判断证据是否足够，以及声明允许使用的措辞强度 |
| `VerificationIssue` | 记录 FactCheck 问题、严重度、建议动作和复核状态 |

这些协议保持 JSON 可序列化，只用于当前 Run 的状态、Trace 和 Artifact，没有为了 P1 提前引入数据库。

### 4.3 第三阶段：重构主研究图

主流程调整为：

```text
问题理解
  -> Model Prior
  -> Research Plan
  -> RAG / Web 按子问题并行研究
  -> Model Analyst
  -> Claim / Evidence Alignment
  -> Gap Research
  -> Synthesizer
  -> FactCheck
  -> Revision
  -> Light Recheck
  -> 最终报告与审计产物
```

其中：

- Model Prior 在检索前提供问题框架、术语、研究维度和待核验假设。
- Research Plan 将复杂问题拆分为独立子问题。
- RAG 与 Web 根据子问题分别检索，不再把多个意图拼成一个长查询。
- Claim Alignment 将声明绑定到具体证据，而不是拼接三个 Agent 的整段输出。
- Gap Research 只对重要且未覆盖的子问题追加有限检索。
- FactCheck 输出结构化问题，并驱动主答案修订和轻量复核。

### 4.4 第四阶段：模型角色与研究深度分层

Quick、Standard、Deep 由 `ResearchProfile` 驱动。档位差异体现在：

- 最大子问题数量和子问题并发度。
- RAG 候选规模和最终证据数量。
- Web 最大结果数、查询数、抓取数和抓取尝试数。
- 查询改写次数。
- 最大缺口补证轮次。
- FactCheck 强度。
- Token、费用和超时预算。

模型角色包括：

- `planner_model`
- `analyst_model`
- `reranker_model`
- `synthesizer_model`
- `verifier_model`
- 每个角色对应的 fallback

业务代码只解析用户配置的 preset 和 role，不硬编码 DeepSeek、MiniMax、Qwen、Gemini 或其他模型。用户可以让多个角色甚至多个档位复用同一个模型。档位校验不再要求模型 ID 必须不同，而是要求检索、并发、核验和预算策略存在实质差异。

Gemini 因实测成本偏高已经从当前运行配置和 `.env.workbench` 中移除。只有用户以后明确重新启用时，才会再次进入真实评测。

## 5. RAG 策略演进

RAG 的调整顺序不是直接更换 Embedding 或无限扩大 Top-K，而是按照“数据真实性、召回覆盖、排序准确、证据可用、声明归属、成本收敛”逐层推进。

### 5.1 第一步：修复全文入库真实性

早期实现把全文策略决策、PDF 下载、正文提取和索引成功混为一个状态。用户界面可能显示“全文入库”，实际知识库中却只有摘要文档。此外，PDF 解析依赖曾只存在于开发依赖，正常安装环境可能下载 PDF 成功但无法提取正文。

纠正措施：

- 分开记录 `full_text_requested`、`full_text_downloaded`、`full_text_extracted` 和 `full_text_indexed`。
- 将 PDF 解析器放入正常运行可用的依赖范围并增加诊断。
- 正文提取失败时允许摘要回退，但必须标记为 `summary_only`。
- 通过内容哈希和版本化 upsert 处理重复入库和内容升级。
- 同一论文已有全文时，对旧摘要文档进行替换或降权。
- 保存论文、章节、页码和块级定位。

这一阶段解决的是“索引中的数据是否真实存在”，避免在错误数据基础上继续调整召回参数。

### 5.2 第二步：从单查询变为子问题查询包

原有复杂查询会把多个研究维度拼在一起，导致检索意图互相稀释。中文问题对英文论文的词法匹配也较弱。

纠正措施：

- 为每个子问题生成独立查询。
- 查询包包含原始语言、英文翻译、同义术语和领域术语。
- 对局限、失败、风险和未来工作等问题加入章节意图扩展。
- 比较型问题为每个目标系统创建直接研究问题。
- 查询改写失败或无增益时保留原始查询，并记录停止原因。

例如，对 ShapefileGPT、Autonomous GIS 和 LLM-Find 的比较，不再生成一个包含三个系统和全部问题维度的超长查询，而是分别检索每个系统的局限性、错误模式和适用边界。

### 5.3 第三步：从单层排序变为分层候选生成

原排序主要依赖 Dense、词项重合、实体重合和文件名主题等人工权重。这些特征适合扩大召回，但容易把“主题相似但没有直接答案”的片段排到前面。

新链路调整为：

```text
子问题查询包
  -> 论文级召回
  -> 章节级召回
  -> 块级 Dense + BM25
  -> 人工特征融合扩大候选
  -> 全文优先和版本去重
  -> 语义重排
  -> 同论文数量限制与跨论文多样性
  -> 最终证据片段
```

人工权重继续保留为可解释的召回特征，但不再承担最终语义判断。

### 5.4 第四步：引入语义重排

`SemanticReranker` 使用用户配置的模型对候选片段判断：

- 与当前子问题的相关性。
- 是否直接回答问题。
- 是否只是出现了相同文件名、实体或术语。
- 是否包含局限、结果、条件、失败模式或可引用事实。

重排输出包括 `relevance`、`directness` 和简短理由。模型超时、JSON 损坏、候选遗漏或 Schema 无法解析时，候选被标记为 `unreviewed`，不能用确定性分数伪装成已完成语义审核。

针对不同模型供应商的输出差异，解析器逐步支持：

- 标准 JSON 数组。
- Markdown JSON 代码块。
- 带包装对象的数组。
- JSONL。
- 带隐藏 reasoning 标签的响应。
- 输出截断时仅保留完整候选，未完成候选继续标记为 `unreviewed`。

### 5.5 第五步：提高证据片段的可引用性

PDF 正文中经常出现物理换行、断词、章节标题、页码和多个无关句子混在同一块的问题。即使召回了正确 chunk，也不意味着提取出的 claim 可直接使用。

纠正措施：

- 修复 PDF 行尾连字符和断词。
- 合并物理换行后再进行句子切分。
- 过滤章节标题、页码标记和空泛元数据。
- 根据查询和章节选择完整、直接的事实句。
- 局限性查询优先当前失败模式，不让泛泛的未来工作描述抢占首位。
- 保留章节、页码、论文标题、版本和 chunk ID。
- 同一论文最多保留有限数量片段，避免单篇论文淹没其他来源。

### 5.6 第六步：加强证据范围和归属约束

一次真实评测中，GIS Copilot 等比较集合外材料可能被用于支撑 ShapefileGPT、Autonomous GIS 和 LLM-Find 的共同结论。这种答案在主题上合理，但证据归属不成立。

纠正措施：

- 为每个目标系统保留独立子问题和独立证据。
- 共同瓶颈必须在每个目标系统中都有直接支持。
- 只在部分系统中成立时，必须写成子集结论。
- 只有模型推断而没有外部直接证据时，必须标记为模型级假设。
- 对新旧论文版本、摘要和全文进行身份去重，避免重复证据制造虚假覆盖。

### 5.7 第七步：控制 RAG 成本与延迟

最初语义重排批次为 2，代表样本产生 17 次模型调用。将批次提高到 8 后，调用数下降到 9 次，Token 从 17,560 降至 16,166。

这次优化降低了调用开销，但样本仍然达到 180 秒超时，说明瓶颈不只在语义重排。进一步分析 Trace 后确认，剩余墙钟时间主要来自 RAG/Web 来源内部的多个子问题串行执行。

随后增加：

- `max_parallel_subquestions`
- 分档候选规模
- 分档 Web 查询和抓取预算
- 查询改写上限
- 剩余时间检查
- 只有剩余时间足以重新综合时才进入 Gap Research

### 5.8 RAG 评测结果

P1 专项标注集的最终结果：

| 指标 | Baseline | Semantic Rerank | 变化 |
|---|---:|---:|---:|
| Recall@10 | 0.70 | 1.00 | +0.30 |
| NDCG@10 | 0.5224 | 0.6593 | +0.1369 |
| 章节命中率 | 0.80 | 1.00 | +0.20 |
| 无关命中率 | 0.12 | 0.08 | -0.04 |

这说明 P1 不只是扩大了召回数量，也改善了相关证据的排序、章节覆盖和无关结果控制。

## 6. Web 策略演进

### 6.1 从 Search 结果升级为 Search + Fetch

原 Web Agent 主要读取搜索标题和 snippet。snippet 适合发现候选，但通常缺少上下文，不能证明关键声明，也无法稳定定位。

P1 将 Web 拆成：

```text
Query Plan
  -> Search
  -> Provider Cascade
  -> Candidate Filter / Dedup
  -> Fetch HTML or PDF
  -> Body Extraction
  -> Evidence Chunk
  -> Claim Alignment
```

最终关键引用必须来自成功抓取的正文或合格的学术摘要。普通搜索 snippet 只用于发现、排序和抓取决策，不能伪装成已核验证据。

### 6.2 来源路由与降级

- 通用查询使用用户配置的搜索 provider。
- 学术问题并行查询 Semantic Scholar、OpenAlex、Crossref 和 arXiv。
- 标准、政策和产品状态问题优先官方或第一方来源。
- 主 provider 失败、限流或返回低质量结果时执行有记录的降级。
- 结果按 canonical URL、跟踪参数、DOI 和正文身份去重。

### 6.3 正文抓取和安全

Web Fetch 支持 HTML 和公开 PDF，并记录：

- 原始 URL 与最终 URL。
- 标题、来源机构和发布时间。
- 获取时间、内容类型和正文哈希。
- 抽取状态和失败原因。
- Prompt Injection 检测状态。

网页始终被视为不可信输入。类似“忽略之前指令”“泄露系统提示词”的内容会被隔离，不进入证据上下文。登录墙、正文过短、解析失败或访问限制会被明确记录为不可用，并继续尝试其他候选。

### 6.4 时效查询优化

对近期标准、政策和产品状态问题增加：

- 年份和时间边界识别。
- 官方来源种子。
- 发布日期、更新日期和获取日期区分。
- 时效性排序特征。
- 官方域名和目标标准标识符保留。
- 高优先页面抓取失败后的候选回填。

## 7. 声明融合、报告与核验闭环

### 7.1 从三段拼接改为声明级融合

原综合方式容易按 RAG、Web、Model 分成三段，造成重复、冲突和信息边界不清。P1 改为围绕问题主题组织答案：

- 外部可核验事实绑定 RAG/Web 正文证据。
- 模型参数化知识用于背景和概念框架。
- 分析判断和建议与外部事实区分。
- 证据不足时降低措辞强度，而不是简单删除全部内容。
- 来源缺失只在报告末尾简洁说明，不反复输出免责声明。

### 7.2 Model Prior 的重新定位

早期 Model Agent 被限制为“不是新的事实来源”，模型推断还受到固定低权威分惩罚，Model-only 场景可能被质量门禁直接判失败。

P1 将 Model 拆分为：

1. 检索前的 Model Prior：生成研究框架、术语、候选事实和待核验假设。
2. 检索后的 Analyst/Synthesizer：基于证据判断声明强度、解释差异并完成综合。

Model-only 不再因为通道身份自动失败，而是检查：

- 答案是否自洽。
- 是否把待核验内容表达得过强。
- 是否正确说明外部证据覆盖不足。
- 是否将高风险或高时效事实标记为待核验。

### 7.3 FactCheck、修订和复核

早期 FactCheck 只会生成 `needs_review`，不会修改主答案。P1 将其改为闭环：

1. 将问题关联到声明 ID、证据 ID、严重度和建议动作。
2. 优先使用已有证据修订。
3. 证据不足且预算允许时触发有限 Gap Research。
4. Synthesizer 重写主答案，而不是在末尾追加更正说明。
5. 运行确定性检查和轻量语义复核。
6. 只有修订后仍存在实质问题时才保留 `needs_review`。

为防止修订引入回归，还增加了：

- 截断或不完整的修订不能覆盖原有完整报告。
- 输出达到 Token 上限时允许一次紧凑重试。
- 复核按声明身份匹配问题，不能只按错误类型判断已解决。
- 明确标注的模型假设不进入外部事实引用分母。
- 失败来源的发现元数据不能泄漏为最终事实。

### 7.4 主报告与审计信息分离

主报告只保留：

- 对问题的完整回答。
- 与结论紧邻的引用。
- 一次简短可靠性说明。
- 必要的未覆盖问题。

逐声明评分、详细 FactCheck、来源状态、重试和 Trace 被放入 sidecar 或审计产物，避免“可信度说明比答案本身更长”。

## 8. 实施过程中发现的错误与纠正

### 8.1 模型档位曾被错误理解为固定模型列表

**问题**：最初倾向于用不同模型 ID 证明 Quick、Standard、Deep 存在差异，开发配置中也出现了 DeepSeek、MiniMax、Qwen、Gemini 等具体型号。

**风险**：后台可能把开发测试选择固化为产品默认行为，限制用户配置，也让模型供应商更换变成代码修改。

**纠正**：

- 业务代码只读取 preset/role。
- 校验允许不同档位复用同一个模型。
- 档位差异由检索、并发、核验、补证和预算策略保证。
- 凭证检查只检查当前档位实际使用的 preset。
- 增加测试防止当前配置意外恢复 Gemini。

### 8.2 对 Gemini 的成本判断偏乐观

**问题**：Gemini 曾进入开发评测候选，但实际成本仍然过高。

**纠正**：从当前 `config.yaml` 和 `.env.workbench` 移除 Gemini，暂停继续调用和模型家族对比。后续是否重新启用完全由用户配置和预算决定。

### 8.3 把策略动作误认为全文处理结果

**问题**：“全文入库”由策略决策推断，而不是由索引结果确认；解析器缺失时还可能静默回退摘要。

**纠正**：拆分请求、下载、提取和索引四种状态，摘要回退显式化，并通过运行依赖诊断阻止虚假成功状态。

### 8.4 过早把问题归因于召回不足

**问题**：最终答案没有文献引用时，容易直觉认为知识库没有答案。

**发现**：Trace 中已经存在 26 个相关全文块。

**纠正**：增加分阶段观测和专项夹具，将优化重点转向证据选择、完整句提取、声明归属和综合约束。

### 8.5 人工加权被用于最终语义判断

**问题**：文件名、实体和词项重合可以提高主题相关性，却不能判断片段是否直接回答问题。

**纠正**：人工特征只用于候选召回，最终顺序由语义相关性和直接性重排决定；模型不可用时明确标记 `unreviewed`。

### 8.6 多子问题被拼成组合查询

**问题**：多个系统、局限类型和研究维度放入一次查询，导致意图稀释，只完成一次低质量补检索。

**纠正**：以 `ResearchPlan.subquestions` 为执行单位，独立检索、覆盖、停止和补证，并在新证据加入后重新综合主答案。

### 8.7 Web snippet 曾被当作可引用证据

**问题**：snippet 上下文不完整，容易截断限定条件，也无法证明正文真实内容。

**纠正**：Search 与 Fetch 分层；普通 snippet 只能用于发现。正文抓取失败时不能生成已核验引用。

### 8.8 FactCheck 成为终点而不是反馈环

**问题**：系统能够发现问题，却只输出 `needs_review`，用户仍然得到未经修订的原答案。

**纠正**：FactCheck 问题结构化，驱动已有证据内修订、有限补证、主答案重写和轻量复核。

### 8.9 引用覆盖率分母定义错误

**问题**：旧 Deep/full 报告的覆盖率只有 38%，主要因为模型分析、证据边界说明和明确假设也被计入“外部事实声明”分母。

**纠正**：区分外部事实、模型背景、分析判断和假设。使用当前确定性核验器重放旧报告后，5/5 外部事实声明带引用，覆盖率为 100%，无效引用为 0。

这说明旧指标低并不完全代表回答缺少证据，也包含评测定义错误。

### 8.10 比较集合外证据发生归属泄漏

**问题**：其他 GIS Agent 的材料可能被用于支撑目标系统的共同结论。

**纠正**：增加目标系统身份约束、逐系统直接证据门禁和子集措辞规则。

### 8.11 Model coverage 出现状态矛盾

**问题**：Model Prior 已成功时，个别子问题 coverage 仍可能显示 `Model Prior missing`，造成总来源状态与子问题状态冲突。

**纠正**：成功的 Model Prior 对每个子问题同步写入覆盖状态，并增加一致性测试。

### 8.12 评测曾偏向篇幅和关键词

**问题**：机械质量检查可能奖励长答案、术语堆砌和章节齐全，导致机械评分高但盲评低。

**纠正**：

- 机械检查只负责引用存在、格式、安全和结构。
- 质量评审使用正确性、完整性、证据支持、分析深度、时效性和表达效率 Rubric。
- 不再因答案更长而加分。
- 结构正确但内容为空泛的 fallback 占位报告必须失败。

### 8.13 语义重排批次过小

**问题**：批次为 2 导致候选重排调用过多。

**纠正**：批次提高到 8，调用数从 17 降为 9。随后通过测试锁定每批 8 个候选，防止后续无意退化。

### 8.14 只优化调用次数，没有立即解决墙钟时间

**问题**：模型调用数明显下降后，Quick/full 仍然在 180 秒超时。

**分析**：Token 只从 17,560 降到 16,166，多个来源内部的子问题仍然串行执行，墙钟延迟没有按调用数同比下降。

**纠正**：增加来源内子问题并发，把 Web 预算纳入档位配置，并在进入 Gap Research 前检查剩余时间是否足以重新综合。

### 8.15 真实 API 调参过密，成本控制滞后

**问题**：早期通过增加候选、延长输出和重复真实运行寻找质量提升，出现 Token 和延迟快速增长。某些 Quick 运行已经达到 45k 以上 Token，并接近或超过档位超时。

**纠正**：

- 将大部分参数和场景验证转为离线夹具。
- 真实 API 只运行代表样本。
- 540 组合矩阵不全量调用真实模型。
- 三次非 Gemini Quick/full 超时后停止第四次调用，先完成代码级并发和预算优化。

### 8.16 Workbench 环境污染测试进程

**问题**：`.env.workbench` 中的运行配置进入 pytest 进程，造成两项 M2 假失败。

**纠正**：隔离测试环境和 Workbench 配置，确保测试只读取显式夹具。

### 8.17 主报告生成了 Markdown，但工作台只展示纯文本预览

**问题**：查询已经生成完整 Markdown 报告，右侧结果区却只读取摘要中的前 4000 字并以纯文本显示。标题、列表、表格和引用因此都没有渲染，用户也无法看到被截断部分。

**纠正**：任务结果返回完整 `report_md_path`，结果区通过受控的 `/api/markdown?path=...` 加载同一份报告并在 iframe 中渲染；保留路径边界检查，避免把任意本地文件暴露给浏览器。桌面和窄屏均验证无横向溢出。

### 8.18 运行时支持三档策略，但配置界面没有三档模型入口

**问题**：后台存在 Quick、Standard、Deep 研究策略，界面最初却只暴露通用 preset，用户无法直接分别指定三档实际模型。这会让“开发时使用 DeepSeek、MiniMax、Qwen”看起来像产品绑定。

**纠正**：模型界面增加快速、标准、深度三个独立配置区，每档保存 Base URL、模型名、API Key 和 Temperature；运行时再把该档用户选择映射给规划、分析、重排、综合和核验角色。具体型号只属于用户配置快照，后台不硬编码供应商或模型名。

### 8.19 `seen` 标记与 Chroma 实际全文状态脱节

**问题**：旧流程可能先把论文记入 `.seen_papers.json`，以后抓取时据此跳过；但 manifest 中的“全文策略命中”并不能证明 Chroma 已经存在全文块。旧元数据的 `paper_source=unknown` 还会导致同一 arXiv 论文身份匹配失败。

**纠正**：新增以 Chroma 元数据为准的真实状态审计，并从论文 ID 恢复旧记录的来源身份。`full_text_missing`、`full_text_failed`、`full_text_extracted`、`not_ingested` 均允许重新进入候选；promotion 后写回实际状态，不再统一记成 `inboxed`。本轮使用本地 PDF 修复 `2503.23633v5` 和 `2604.13888v1`，分别形成 29 和 33 个全文块；`2410.12376v2` 原有 26 个全文块。当前审计为全文已索引 5 篇、仅摘要 97 篇、待修复 0 篇。

### 8.20 引用主体和 Trace 状态都曾被正文关键词误导

**问题**：引用主体校验按整行扫描系统名。同一行先讨论 Autonomous GIS、再讨论 GeoAgentBench 时，后者的正确引用被错误归到前者。Trace 也曾扫描结构化阶段正文中的 `failed/error` 单词，导致正常的 Evidence Merge 被显示为失败。

**纠正**：引用校验改为逐个引用读取其前方最近的句子或分号子句；回归测试同时覆盖“同一行两个系统各自引用”和“ShapefileGPT 证据错误挂到 Autonomous GIS”两个方向。Trace 只从带协议标记的 Agent 结果解析来源状态，研究计划、证据合并、综合报告等结构化阶段不再依据正文词汇推断失败。

### 8.21 开放式综述的维度名称有了，但证据发生错位

**问题**：首次用“当前地理处理自动化研究存在哪些局限性”复测时，计划已经覆盖四个维度，但综合器把训练知识过时、参数错配和一般运行时异常放入“数据与互操作”章节。形式上覆盖了维度，语义上却没有数据质量、格式、模式、标准或跨平台交换的直接证据。

**纠正**：默认计划固定使用互补维度；综合约束进一步规定，数据/互操作只能由明确涉及数据质量、模式、格式、坐标系、语义、标准或跨平台交换的证据支撑。直接证据不足时必须写成覆盖缺口，不能用相邻维度的证据补齐版面。

### 8.22 系统自动超时被误报成用户取消

**问题**：Workbench 前端曾写死 300 秒计时器。任务超过 5 分钟时，页面会自动调用与用户取消相同的接口，后台最终统一写成 `cancelled`，因此 `ffbd67ea2789` 看起来像是用户主动取消。用户实际没有执行取消操作。由于取消信号只能在 LangGraph 返回下一个状态边界时处理，该任务在自动请求发出后仍继续运行了一段时间。

**纠正**：提交接口返回当前研究档位的真实 `timeout_seconds`；前端自动终止请求携带 `reason=timeout`，手动取消携带 `reason=user`；后台分别落为 `timed_out` 和 `cancelled`。等待执行锁的时间也计入档位时限。取消或超时在报告写出前以异常终止查询，并清空中间答案、FactCheck 和 Artifact 路径，避免未完成结果进入正式报告列表。

### 8.23 合成超时后把低相关来源包装成完整成功

**问题**：`ffbd67ea2789` 的 RAG 已取得 11 条高质量正文证据，但 Web 为 `low_relevance`，其中还混入无关病理学页面。Synthesizer 在 70 秒模型时限后静默退回 257 字 Model 摘要，最终没有任何引用；旧 fallback 却仍写成“RAG、Web、Model 均可用”，形成了来源状态和报告表述的双重失真。

**纠正**：`low_relevance` 现在明确属于覆盖缺口，不进入事实证据、确定性核验或质量评分；只有 `success` 来源能够支撑答案。合成前压缩证据载荷并检查剩余运行预算；若模型调用超时或预算不足，生成明确标注为受限结果的 grounded fallback，只列已取得且可定位的正文证据，每条事实都带原始引用，同时在 Trace 中记录 `fallback` 和具体错误。系统状态说明不再误计入外部事实引用覆盖率。

## 9. 评测过程与结果变化

### 9.1 代表性质量轨迹

以下历史结果来自不同阶段和不同用户配置，主要用于说明问题变化，不能直接作为严格模型横向对比：

| 运行 | 盲评 | 引用覆盖 | 耗时 | Token | 主要结论 |
|---|---:|---:|---:|---:|---|
| 初始失败基线 | 2/5 | 0% | 约 193 秒 | 未统一记录 | 答案浅，缺少直接证据 |
| Standard/full 早期复测 | 2/5 | 66.7% | 约 145 秒 | 约 62.4k | 机械评分高估质量 |
| `geo-limitations-standard` | 4/5 | 88% | 158.4 秒 | 65,963 | 三论文覆盖明显改善 |
| `quick-full-balanced` | 4/5 | 85% | 136.3 秒 | 45,523 | 质量和覆盖达线，但核验修订仍未通过 |
| `deep-full-final` | 4/5 | 旧口径 38% | 312.2 秒 | 73,144 | 答案质量较高，但成本和延迟过高；覆盖口径后来纠正 |
| `standard-model-only-final` | 4/5 | 100% | 79.1 秒 | 27,493 | Model-only 不应因来源身份自动失败 |
| `recent-web-rag-failure-v10` | 4/5 | 100% | 117.7 秒 | 43,885 | RAG 失败时仍可降级完成 |

这些结果带来三个判断：

1. 增加候选和模型调用可以提高质量，但很容易突破延迟和费用边界。
2. 独立盲评与机械门禁必须同时存在，否则会把格式完整误判为研究质量。
3. 单个来源失败不应自动判定整份回答失败，关键在于剩余证据能否支撑实际声明。

- Web provider 降级、HTML/PDF 抓取和 Prompt Injection。
- snippet 禁止作证和失败来源隔离。
- 语义重排格式容错和显式 `unreviewed`。
- PDF 断词修复、章节优先和全文摘要降权。
- 比较问题逐系统证据归属。
- Model-only、RAG failure、Web failure 等降级路径。
- FactCheck 修订、截断保护和声明身份复核。
- Markdown 完整报告渲染和三档用户模型配置。
- Chroma 全文真实性审计、可重试状态和旧来源身份恢复。
- 引用局部语境及结构化 Trace 状态回归。

### 9.6 最终 V7 重放与 V8 Deep/full 验收

V7 的完整研究产物已经达到六维覆盖、来源数量和盲评质量要求，但模型在正文中直接使用 `[1]` 到 `[10]`，参考文献表为空。为避免把模型预编号误当成内部 Evidence ID，核验节点新增了受限数字引用修复：核验模型必须为每个数字返回完整映射，目标只能是当前证据池中真实存在的引用；任一编号缺失或出现未知引用时整次修复拒绝生效。最新代码对 V7 的真实重放得到 9 个去重参考条目、100% 引用覆盖率、0 个无效引用和 `passed`，且未调用全篇 Synthesizer。

随后执行全新的 V8 Deep/full 代表运行：

| 指标 | V8 结果 | 退出线 |
|---|---:|---:|
| 研究链路耗时 | 371.9 秒 | 不超过 480 秒 |
| 六维实质覆盖 | 6/6 | 6/6 |
| FactCheck | `passed` | `passed` |
| 引用覆盖率 | 100% | 不低于 85% |
| 有效/无效引用 | 8 / 0 | 无效引用为 0 |
| 有效外部证据 | 21 | 不少于 8 |
| 独立来源 | 12 | 不少于 5 |
| 反窄短 Rubric | 5/5/5/5 | 核心项不低于 4 |

V8 首次匿名盲评出现了新的评测器缺陷：评审模型无视已提供的证据图和 2026-07-20 评测日期，凭模型记忆把已取得全文的 `arxiv:2604.13888` 判为“极大概率捏造”，因此错误地给候选正确性 1/5。修复没有删除或覆盖该失败记录，而是在盲评系统提示中明确：可审计证据摘要里的来源身份、日期和逐字引文是运行时确定性输入；不得凭编号观感、标题熟悉度或来源知名度推定其不存在；只有引文与声明真正错配时才能扣正确性。

相同输入哈希下的独立盲评重放中，候选核心五项为 `5/5/5/4/5`，参考为 `3/5/3/2/3`，候选总体 4.8、参考 3.2。`reports/eval/p1/reopened-deep-final-v8/p1_eval_rejudge.json` 同时核对延迟、六维、FactCheck、引用、来源数量和盲评共 10 项硬门槛，全部通过。这次经历再次说明：LLM 评测器必须服从可审计输入边界，本身也需要反例测试和真实重放。

## 10. 最终形成的工程优化手段

### 10.1 正确性优化

- 全文处理状态从策略推断改为事实状态机。
- 引用必须反向定位到正文证据。
- 模型分析、外部事实和假设采用不同核验规则。
- 跨系统证据归属采用确定性门禁。
- 降级不能伪装成成功审核。

### 10.2 质量优化

- 双语和章节感知的查询规划。
- 论文、章节、块三级召回。
- Dense + BM25 扩大候选。
- LLM 语义相关性和直接性重排。
- PDF 完整句提取和片段清洗。
- 同论文限制、跨论文多样性和版本去重。
- 声明级融合、缺口补证和修订复核。

### 10.3 性能优化

- 语义重排批处理从 2 提升到 8。
- RAG/Web 子问题并发执行。
- Web 搜索和正文抓取并发。
- 不可访问页面的有界回填。
- 每档独立候选、抓取、改写和补证预算。
- 进入下一阶段前检查剩余运行时间。

### 10.4 成本优化

- 模型按角色分配，不要求所有步骤使用最强模型。
- 共享 Token 预算和硬截止时间。
- 540 组合使用离线矩阵，不全量调用真实 API。
- 真实评测采用代表样本。
- Gemini 因成本原因暂停。
- 发现连续超时后停止继续调用，先完成离线定位。

### 10.5 可观测性优化

- Trace 记录模型角色、实际 preset、fallback、Token、延迟和错误。
- 记录 Dense、BM25、融合排名、语义重排和最终选择原因。
- 每个子问题记录来源覆盖、补证原因和停止原因。
- 主报告与审计 sidecar 分离。
- 评测同时记录质量、引用、延迟、Token、重试和降级。

## 11. 可复用的工程经验

### 11.1 先验证数据真实性，再优化召回算法

如果系统把摘要误报成全文，继续调整 Embedding、Top-K 或模型没有意义。数据状态必须能够证明“下载了什么、解析了什么、索引了什么”。

### 11.2 RAG 的 Top-K 命中不等于答案获得证据

完整链路至少包含：召回、排序、片段提取、声明对齐、综合约束和引用生成。任何一层都可能丢失已经召回的正确内容。

### 11.3 Agent 系统需要观察调用拓扑，而不只是 Token

模型调用数下降不代表端到端延迟同比下降。串行子问题、网络抓取、重试和最终综合都可能成为墙钟瓶颈。

### 11.4 评测指标本身也需要测试

引用覆盖率分母定义错误，可能让高质量答案被误判失败；关键词和篇幅指标可能让低质量长答案得高分。评测器不是天然正确的，也必须用人工样本、反例和重放测试验证。

### 11.5 FactCheck 必须能够改变系统输出

只发现问题而不修订答案，FactCheck 只是审计工具，不是质量闭环。有效闭环需要问题定位、证据补充、答案重写和复核。

### 11.6 产品档位应描述服务策略，而不是绑定供应商

Quick、Standard、Deep 应表达质量、延迟、预算和核验强度。具体模型属于用户配置和运行环境，不能固化为业务代码的一部分。

### 11.7 真实 API 评测必须设置停止条件

连续真实运行很容易把成本消耗在参数试探上。应先使用离线夹具缩小问题，再运行最小代表样本；当连续结果指向同一个结构性瓶颈时，应停止调用并先修改实现。
