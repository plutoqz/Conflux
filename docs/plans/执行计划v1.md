## 1. 使用方式

`architecture.md` 负责长期方向，本文件负责第一轮实施。实施时不要求一次完成 M1-M6；每个阶段开始前确认当期范围，完成后根据真实问题更新状态。

本方案的成功标准不是新增模块数量，而是：

- 用户可以定义和运行自己的能力，同时不直接依赖核心私有状态。
- 现有研究查询、论文、项目和审计能力可以逐步迁移，不发生大范围停摆。
- 论文和搜索结果的语义判断真正由 LLM 完成，失败时不会被确定性分数伪装成已评审。
- 任务、证据、产物和审批可以追溯、恢复和迁移。
- 测试、安全和抽象成本与真实风险相称，不阻碍日常开发。

## 2. 全局实现规则

### 2.1 代码和数据边界

第一轮在当前单仓库中建立边界，不立即拆分多个 Python 包或服务：

```text
src/conflux/
  core/       # 运行上下文、协议、事件、策略和存储端口
  sdk/        # Plugin、Capability、Workflow、Evaluator、Renderer
  builtin/    # 第一方能力，按协议接入
  adapters/   # 模型、RAG、Web、SQLite、Chroma、CLI、HTTP
  workbench/  # UI 和 HTTP 适配，只调用 Application API
```

当前模块可以分阶段迁移。迁移前保留兼容适配器，迁移完成后标记移除版本，禁止永久保留两条主要路径。

### 2.2 数据协议

核心边界使用稳定、JSON 可序列化的协议：

- `RunContext`：工作区、模型、预算、取消、权限和运行标识。
- `StepResult`：状态、输出、证据引用、产物引用、指标和错误。
- `ArtifactRef`：产物 ID、类型、哈希、位置、来源 Run/Step。
- `ApprovalRequest`：待确认操作、差异、风险、输入哈希和审批结果。
- `TraceEvent`：开始、完成、失败、重试、降级、审批和恢复。

插件不能接收完整 LangGraph 状态，不能写入核心全局变量，不能直接修改工作台对象。

### 2.3 LLM 评审规则

确定性逻辑只做召回、去重、格式校验、负面条件和硬性安全门禁。LLM 负责：

- 搜索结果和论文的语义相关性。
- 研究价值、方法/数据集复用价值和证据质量。
- 候选排序、边界候选是否需要深评。
- 冲突解释、报告综合和开放式研究计划。

LLM 评审必须输出 `relevance`、`research_value`、`evidence_quality`、`reasoning`、`confidence`、`needs_deeper_review`。模型失败、超时或 Schema 无法修复时输出 `unreviewed`，不能自动入库或提升为高置信证据。

### 2.4 变更控制

每个阶段均建立：

- 范围和非目标。
- 受影响模块和数据格式。
- 新增依赖及其移除条件。
- 快速测试、阶段测试和真实 API 测试分层。
- 回滚开关或恢复步骤。

以下情况必须暂停并更新架构决策：插件需要核心私有状态、出现 YAML/数据库双写、需要预先建设多租户/微服务、单个示例要求核心加入领域分支、或连续两次修复都扩大核心协议。

## 4. M0：基线与实施准备

### 4.1 目标

- 记录当前行为和性能基线。
- 准备不污染源码运行目录的测试夹具。
- 建立轻量 ADR/问题记录，不增加重审批流程。

### 4.2 实现方法

- 在临时目录运行 `python -m pytest -q`、离线检索评测和离线报告评测。
- 记录当前测试数量、检索指标、报告验收率、失败来源泄漏、平均/分位延迟和已知失败样本。
- 建立 `tests/fixtures/architecture/` 目录约定，保存插件、工作流、迁移、来源变化和 LLM 录制响应夹具。
- 测试不得写入现有 `reports/`、`data/chroma_db/` 或用户项目路径。
- 记录查询、论文 inbox、论文 promote、项目计划、进度审计和工作台任务的当前入口。

### 4.3 验收标准

- 基线结果可以在新机器或临时工作区重复生成。
- 基线报告明确列出当前 RAG/Web 确定性评分的限制。
- 当前功能行为没有因 M0 改变。
- 后续阶段可以引用同一份基线，不依赖个人未提交文件。

### 4.4 失败处理

如果基线本身不稳定，先修复夹具或登记缺陷，不进入 M1。不得将不稳定行为包装成重构后的回归或收益。

## 5. M1：扩展协议最小闭环

### 5.1 目标

让一个能力可以被发现、校验、执行、追踪和测试，同时不修改核心固定来源列表和工作台专用路由。

### 5.2 建议代码边界

```text
src/conflux/core/contracts.py
src/conflux/core/registry.py
src/conflux/core/policy.py
src/conflux/sdk/manifest.py
src/conflux/sdk/plugin.py
src/conflux/sdk/testing.py
src/conflux/adapters/plugin_loader.py
```

### 5.3 实现方法

- SDK 边界使用 Pydantic v2，直接声明依赖；核心内部可继续使用现有 dataclass/TypedDict。
- 定义 `PluginManifest`、`CapabilitySpec`、`WorkflowDefinition`、`StepResult`、`PluginContext`。
- Manifest 包含 ID、版本、入口、能力、权限、配置、Schema、超时、副作用和 SDK 兼容范围。
- Registry 从内置插件和用户显式指定目录加载 Manifest，不扫描未知 Python 文件。
- 通过 entry point 或明确路径加载插件；只加载通过版本、Schema、权限和入口校验的插件。
- `PluginContext` 仅提供日志、配置、模型、存储、证据登记和 Artifact 服务。
- 第一阶段插件标记为可信进程内代码；权限用于校验和审计，不宣称提供沙箱。

### 5.4 CLI

```text
conflux plugin list
conflux plugin validate <path>
conflux plugin inspect <plugin-id>
conflux workflow validate <path>
```

### 5.5 测试范围

契约测试覆盖：Manifest 缺失字段、版本不兼容、未知能力、Schema 错误、权限不足、插件异常封装、禁用插件、事件记录和 Secret 脱敏。

不为简单代理函数建立重复的多层测试；重点覆盖协议分支和安全边界。

### 5.6 验收标准

- 至少一个第一方能力通过 Registry 注册并独立执行。
- 新增能力不需要修改 `MultiAgentState`、固定来源枚举或工作台专用 API。
- 输入输出可以导出和校验 JSON Schema。
- 异常统一转换为 `StepResult`，不泄露 Secret，不直接修改共享状态。
- 协议分支契约测试覆盖 100%。
- 现有测试、离线评测和工作台测试不回归。

### 5.7 回滚

新 Registry 默认只在显式开关下启用，保留当前内置调用路径。协议失败时删除实验性加载器不影响现有查询和工作台。

## 6. M2：第一方能力迁移与 YAML 工作流

### 6.1 目标

将核心能力通过同一 SDK 接入，并让技术用户使用 YAML 组合已安装能力，不引入可视化编排。

### 6.2 动态结果协议

将固定的 `rag_result`、`web_result`、`model_result` 逐步迁移为带 reducer 的动态 `source_results` 集合。过渡期保留旧字段适配器，但新报告、Trace 和仲裁只读取统一集合。

`SourceResult.source` 改为 namespaced ID，例如 `builtin.rag` 或 `plugin.example.search`。来源展示名、证据类型和权限从 Registry 元数据读取。

### 6.3 第一方迁移顺序

1. RAG Connector：确定性召回/硬过滤，LLM 语义评审。
2. Web Connector：结果规范化，LLM 相关性/证据质量评审。
3. Model Analyst：直接读取结构化 `StepResult`，移除图内文本 marker 中转。
4. Paper Workflow：批量 LLM 评审、边界候选深评和人工入库确认。
5. Project/Audit Workflow：计划分析、证据核验和审计作为统一步骤。

### 6.4 YAML 工作流

YAML 只描述已安装能力和连接，不执行任意 Python：

```yaml
api_version: conflux.dev/v1alpha1
kind: Workflow
id: research.query
version: 0.1.0
inputs:
  query: {type: string, required: true}
steps:
  - id: retrieve
    uses: builtin.rag.search
    mode: deterministic
  - id: semantic_review
    uses: builtin.research.evidence_review
    mode: agentic
  - id: approve
    uses: builtin.human.approval
    mode: human
```

编译前检查能力存在性、Schema 连通性、循环停止条件、预算、权限和副作用。编译后生成版本化工作流和文本图预览。

### 6.5 LLM 评审实现

- 批量阅读研究画像、查询、标题、摘要或搜索片段。
- 输出 `relevance`、`research_value`、`evidence_quality`、`reasoning`、`confidence`、`needs_deeper_review`。
- 缓存键包含候选内容哈希、画像版本、Prompt 版本和模型版本。
- 普通候选使用批量和轻量模型；边界、高价值或冲突候选再做深评。
- 模型失败、超时或 Schema 修复失败时标记 `unreviewed`，不能自动入库。

### 6.6 验收标准

- 一个外部来源和一个本地查询工作流可以完成 YAML 校验、编译和 Dry Run。
- 新增来源不修改核心固定来源枚举、报告模板和 Trace 映射。
- 论文评审可以追溯候选哈希、画像、Prompt、模型、理由和不确定性。
- LLM 不可用时界面显示 `unreviewed` 原因和下一步。
- 旧 CLI/工作台至少有一个兼容适配路径。
- 失败来源泄漏保持 0，报告验收率不低于 M0 基线。
- 无可视化编排页面。

### 6.7 回滚

新工作流通过显式配置启用，默认保留旧路径。动态结果适配器必须记录删除版本，不允许长期双路径作为默认实现。

## P0：研究质量与可用性修复（已完成）

### P0.1 目标

在进入 M3 持久运行和数据迁移前，先解决当前影响基本可用性的正确性问题：论文语义评审失败导致整批跳过、Web 搜索单一 provider 失败、中文问题召回英文论文不足、研究回答被可信度说明淹没，以及 RAG 证据质量和全文状态不清晰。

P0 是 M2 的后置修复闸门。它不改变 `architecture.md` 的长期边界，不引入 SQLite、服务化、微服务或可视化编排。

### P0.2 全局原则

- LLM 评审失败时保留候选和确定性排序，但不得把确定性分数伪装成语义评审结果。
- `unreviewed` 不等于 `skip`；未评审候选可以展示、重试和人工处理，但不能自动提升为高置信证据或无审批入库。
- 主答案先回答问题，再附证据、可信度和缺口；FactCheck、仲裁和原始日志作为可展开审计信息。
- 来源可信度按证据项的相关性、权威性、时效性、引用完整性和多源一致性判断，不按 RAG/Web/Model 通道绝对化。
- 确定性逻辑负责召回、去重、格式校验、硬性过滤和安全门禁；LLM 负责语义相关性、研究价值、证据质量和候选重排。
- 所有降级、重试、临时结果和失败原因必须可见、可追溯、可再次执行。

### P0.3 工作包 A：论文语义评审容错

受影响边界：`builtin.paper.review`、`builtin.research.evidence_review`、论文 inbox、Workbench 评审状态。

实现要求：

- 将大批次拆分为 3-5 篇的小批次，批次之间独立成功或失败。
- 单篇或单批次异常不得影响其他候选。
- 初评成功、深评失败时保留初评结果；仅将深评失败候选标记为 `unreviewed` 或 `needs_deeper_review`。
- 对超时、认证失败、JSON 截断、数量不匹配、Schema 错误和二次修复失败使用结构化错误码。
- 评审失败最多自动重试一次，使用有限退避并记录重试原因。
- 评审结果至少区分 `deterministic_score`、`semantic_score`、`review_status` 和 `candidate_status`。
- 评审失败时保留确定性候选排序和原始结果，但不得将其写成已完成的 LLM 相关性判断。
- 评审完成后重新写出 inbox JSON/Markdown；失败原因、模型、Prompt、候选哈希和下一步操作必须写入产物。
- Workbench 不再只显示“配置模型后重试”，必须展示可操作的失败原因。

验收标准：

- 10 篇论文中任意 1 批失败时，其余批次仍保留评审结果。
- 初评成功而深评超时时，初评结果不丢失。
- LLM 不可用时论文不会被整批设为 `skip`，而是显示 `unreviewed/provisional`。
- 未评审论文不会自动变为高置信证据或无审批进入知识库。
- 评审失败原因可在 CLI、Workbench 和 inbox 产物中定位。

### P0.4 工作包 B：Web provider 多级降级

实现统一 `SearchProvider` 适配边界，支持配置化 provider 链：

```text
主 provider
  -> DuckDuckGo / 备用通用搜索 API
  -> Bing 或 Google 的授权 API / SerpAPI
  -> Semantic Scholar / OpenAlex / Crossref / arXiv
  -> LLM 统一语义评审与去重
```

降级触发条件包括请求失败、超时、限流、有效 URL 过少、去重后候选过少、低质量域名占比过高或 LLM 评审后有效候选不足。不得直接抓取 Google/Bing 搜索页面作为默认实现；需要使用授权 API 或聚合服务。

学术查询判断扩展“局限性、评估、风险、模型、算法、机制、研究现状、失败模式”等中英文意图词，但不对所有开放问题强制触发学术 API。边界问题可以通过轻量模型判断是否需要学术搜索。

验收标准：

- 主 provider 失败时能自动进入备用 provider，并在 Trace 中记录切换原因。
- provider 结果可以按 URL、DOI、论文 ID 去重并合并。
- 备用结果不会绕过统一的 LLM 语义评审和证据状态协议。
- 无备用凭证时仍能明确显示可用的学术 API、失败来源和下一步，而不是静默失败。

### P0.5 工作包 C：跨语言 RAG 和论文全文质量

实现一个独立的 `QueryRewriteProvider`，将原始查询、术语扩展和可选 LLM 中英改写分开，避免底层检索器直接依赖模型。

检索链路要求：

- 中文原始查询、英文翻译查询和领域扩展查询并行召回。
- Chroma 的真实查询距离必须转换为明确的 Dense 相似度并传递给后续排序。
- 禁止使用论文发现阶段的 `relevance_score` 作为当前查询的 Dense 分数。
- BM25 使用语言感知分词；跨语言场景降低词法分数对最终判断的影响。
- 候选先扩大召回，再由 LLM 做语义重排；确定性阈值不得直接淘汰所有跨语言候选。
- 论文查询支持 `limitations`、`challenges`、`failure modes`、`future work`、`research gaps` 等章节词扩展。

论文入库要求区分：

```text
full_text_requested
full_text_downloaded
full_text_extracted
full_text_indexed
```

论文全文应尽量保留 `abstract`、`method`、`results`、`limitations`、`discussion`、`future_work` 等章节元数据。内容更新使用内容哈希和版本化 upsert，不能因为相同 `chunk_id` 永久跳过更新。

验收标准：

- 中文问题能够稳定召回英文相关论文，且不因词法分数为零直接丢弃。
- Dense、BM25、融合分数和最终 LLM 评审结果可以分别追溯。
- 论文没有下载或提取全文时，界面和产物明确显示原因。
- 针对“局限性/失败模式/未来工作”的查询能够优先命中对应章节或明确说明知识库缺口。
- 重复入库和内容更新不会产生旧摘要永久遮蔽新全文的问题。

### P0.6 工作包 D：回答先行与可信度后置

重构报告综合和 Model-only fallback 行为。主报告默认结构为：

```markdown
## 核心回答
## 分析
## 证据支撑
## 可信度评估
## 需要进一步核验
```

实现要求：

- 在现有条件下先给出尽可能完整的回答、分类、原因和工程分析。
- Model-only 场景允许输出临时分析，但必须逐条标记为模型推断。
- `low_relevance` 只能降低相关结论的可信度，不应自动把整个回答变成拒答。
- 可信度按声明或证据项评估，不能只给一个笼统的全局低分。
- FactCheck、三源仲裁、原始来源状态和运行日志进入附录或可展开区域。
- 报告必须区分“没有证据”“证据弱”“Model 推断”和“工具失败”。

验收标准：

- 用户打开报告首先看到问题答案，而不是失败原因或免责声明。
- RAG/Web 不足但 Model 有内容时，仍能得到结构化临时回答。
- 低可信度说明位于答案之后，且不会遮蔽核心结论。
- 关键结论可以定位到来源、证据类型和模型推断状态。
- 现有失败来源泄漏、Prompt Injection 泄漏和 FactCheck 安全约束不回归。

### P0.7 工作包 E：状态、诊断和分层验证

- 运行结果区区分“候选召回”“语义评审”“答案生成”“可信度核验”和“降级重试”。

## P1：三源研究质量闭环（已完成验收）

### P1.1 阶段目标与成功定义

P1 的首要目标重新明确为：**依靠 Model、RAG 和 Web 三源的互补优势，使最终回答的质量、广度和深度向 GPT Deep Research 看齐，同时提供明确、可追溯的置信度评价。**“看齐”指在同一问题、相近时间边界和可比研究深度下，经盲评后在正确性、维度覆盖、机制分析、案例证据、洞察深度、建议价值和表达连贯性上不低于参考报告，而不是机械追求相同篇幅或来源数量。

优先级必须保持如下顺序，不得倒置：

1. **完整回答质量**：首先产出有实质内容、兼具广度和深度的答案。
2. **研究覆盖与证据增强**：利用 Web 扩大边界、RAG 深挖正文、Model 建立框架并完成跨来源综合。
3. **置信度与可追溯性**：对已经形成的关键结论评价可靠程度，说明依据和缺口。
4. **成本与延迟**：在用户选择的档位预算内优化，不能通过系统性删减维度、案例、分析和建议来换取达标。

P1 不再以“搜索成功、三个 Agent 都返回文本、报告格式完整、引用覆盖率高或 FactCheck 无格式错误”单独作为研究查询成功。局部证据全部有引用，但只回答少数维度的短报告，仍属于失败。

P1 完成后，研究查询必须具备以下能力：

- Model 使用较新的大参数模型提供世界知识、概念框架、研究维度和待核验假设，不再被当成“不允许产生新事实”的低等来源。
- RAG 优先利用本地论文和用户知识资产，能够从真实全文、章节和具体片段中召回与问题直接相关的证据。
- Web 提供知识库之外的广度和时效性，从搜索发现继续获取网页或 PDF 正文，不能只依赖标题和摘要片段作证。
- 三源按声明互补，不要求三者同时出现或多数一致才允许回答；任一来源缺失时仍给出当前条件下尽可能完整的答案，并只在报告末尾简洁说明覆盖缺口。
- 研究过程能够识别答案缺口，按独立子问题补充检索，在 FactCheck 发现实质问题后修订主答案并重新核验。
- 低、中、高研究深度使用不同等级、不同预算的模型和研究循环，用户选择的深度真实改变质量、成本和延迟，而不是只改变 Prompt 或 Token 上限。
- 广泛综述类问题必须覆盖计划中的重要维度，并为每个核心维度组织“结论、机制、证据或案例、影响、缓解方向或明确缺口”，不能用少量高置信声明替代完整回答。
- 正文以连续阅读体验为先，只使用 `[1]`、`[2]`、`[1,3]` 等紧凑数字引用；完整来源、定位信息和引用内容统一附在正文后的“参考文献与证据”中。
- 置信度评价和分层统一放在整份报告最后的“置信度附录”，不得穿插在正文各段反复打断阅读。

置信度是对高质量答案的解释层，不是答案内容的准入替代品。对于有分析价值但外部证据不足的低风险判断，系统应保留其分析价值，并在最后的置信度附录中标记为中、低或待核验；不得为了提高引用覆盖率或置信度分数而默认删除整个维度。

### P1.2 产品原则与非目标

三源协议遵循以下原则：

1. **互补而非投票**：RAG、Web、Model 是不同认知能力，不是必须达成一致的三个投票者。
2. **声明中心**：先识别报告要表达的事实、判断和建议，再为每条声明绑定来源、证据和限制；不按 Agent 输出整段拼接。
3. **单源可成立**：高权威、直接相关的单一来源可以支撑声明；多个低质量转载不能因为数量多而制造高可靠性。
4. **模型知识可使用**：模型世界知识可以用于背景、解释、分类、推理和候选事实，但要区分参数化知识、分析判断和外部可核验证据。涉及高时效、高风险或精确数字的事实应优先补充 RAG/Web 证据。
5. **缺源不拒答**：来源失败或覆盖不足会触发补证、降级和简洁说明，不自动把整份答案降为拒答或失败。
6. **冲突才仲裁**：只有来源对同一声明形成实质矛盾时才进入仲裁；来源缺失、侧重点不同或证据粒度不同不算冲突。
7. **回答优先**：主报告首先完整回答问题。正文只保留紧凑数字引用，不穿插来源长标识、置信度标签、来源状态、运行日志或免责声明。
8. **质量与成本同时可见**：每次真实评测同时记录答案质量、引用质量、来源覆盖、延迟、Token、费用、重试和降级。
9. **置信度后置**：逐声明置信度参与内部补证、措辞和修订，但面向用户的分层结果统一放在报告最后的附录中，不破坏正文阅读节奏。
10. **不以少写换高分**：引用覆盖率、引用正确率和高置信声明比例是质量约束，不得通过缩小声明集合、删除未充分核验维度或压缩分析来提高。

P1 明确不包含：

- SQLite Run Store、持久 Job、跨进程恢复和初始化迁移。
- Postgres、Redis、Worker、微服务或多租户建设。
- 默认将本轮临时发现的论文永久写入用户知识库。
- 大规模 Workbench 视觉重构或可视化工作流编辑器。
- M4 的跨运行、可版本化 Evidence Ledger；P1 只实现单次 Run 内的声明与证据协议，并为 M4 保留兼容边界。

### P1.3 当前质量基线与必须关闭的问题

P1 以真实失败查询“当前地理处理自动化研究存在哪些局限性”为首个回归样本。P0 后的冻结基线报告质量为 2/5、来源可靠性为 2/5、关键声明外部引用覆盖率为 0%、FactCheck 为 `needs_review`，总耗时约 193 秒。原论文实际包含足够的限制、失败模式和未来工作内容，因此该结果不能归因于“知识库没有答案”。

截至 2026-07-18 的最新 Standard/full 复测已经证明链路有所改善，但仍未达到退出线：机械质量评分为 4.2/5，关键声明引用覆盖率为 66.7%，无效引用为 0，FactCheck 仍为 `needs_review`；独立盲评总分为 2/5，耗时约 145 秒、约 62.4k Token。RAG 审计中实际出现了 ShapefileGPT 的 26 个全文块，但最终答案仍将其写成“未获取直接文献”，说明当前剩余问题主要位于“证据片段选择 -> 声明对齐 -> 综合约束”链路，而不是论文不存在或全文未入库。

P1 必须逐项关闭以下已确认问题：

- 全文入库界面按策略决策显示“全文入库”，但实际可能仅创建 `#summary` 文档；下载、提取和索引状态被混为一谈。
- PDF 正文提取依赖仅存在于开发依赖，正常运行环境可能缺少解析器，导致下载成功但正文静默缺失。
- RAG 最终排序仍主要依赖 Dense、词项、实体和文件名主题的人工权重，缺少真正的语义重排；章节命中和具体引用不足。
- Model Agent 被限制为“不是新的事实来源”，模型推断固定获得过低权威分，Model-only 又被质量门禁直接判失败，浪费了新模型的世界知识。
- Web 结果停留在搜索标题和 snippet，没有网页/PDF 获取、正文抽取和可引用片段，因此既浅又难以核验。
- 深度研究把多个子问题拼成一个组合查询，只进行一次追加检索，查询意图相互稀释。
- FactCheck 发现问题后不会驱动主答案修订；深度研究结束后也不会基于新增证据重新综合主报告。
- 当前深度质量评分偏向关键词检查，可能把篇幅和术语出现误判为研究质量。
- `reasoning` 与 `cheap` 等模型角色可能解析到同一个轻量模型，低、中、高模式没有形成真实能力差异。
- 报告反复强调可信度、三源缺失和失败原因，信息密度高但回答本身不够完整，评价对象发生倒置。
- 最新真实运行表明机械评分仍可能奖励“少量声明全部有引用”的短报告，来源覆盖 gap 没有直接触发补证，内部指标与用户感知质量再次脱节。
- Standard/Deep 的固定子问题、候选、最终证据和报告字符上限限制了广泛综述；Evidence Analyst 又可能因墙钟预留被跳过，三源在实际运行中退化为窄 RAG 加受限 Model。
- Web 缺少稳定的学术搜索和高质量外部扩展能力；仅依赖当前通用搜索降级时，无法承担 GPT Deep Research 级别的知识广度。
- 当前正文暴露长 RAG/Web 引用标识，并把可靠性说明作为正文固定章节，不符合“连续正文、参考文献后置、置信度附录最后呈现”的阅读目标。

以上问题均应有对应代码改动、回归测试或评测样本。不得仅通过放宽报告验收阈值、增加免责声明或延长输出解决。

### P1.4 目标流程与运行内协议

P1 将研究查询调整为以下主流程：

```text
问题理解
  -> Model Prior：形成问题框架、研究维度和待核验声明
  -> Research Plan：拆分独立子问题，定义来源偏好和停止条件
  -> RAG / Web 并行补证，Model 持续提供分析候选
  -> Claim Alignment：逐声明绑定证据、识别缺口与真实冲突
  -> Coverage Gate / Gap Loop：重要维度未覆盖时继续检索或明确形成待核验分析
  -> Synthesizer：先按问题维度生成兼具广度和深度的完整正文
  -> Citation Compiler：将正文来源统一编号，并生成参考文献与证据条目
  -> FactCheck：检查事实、数字引用、遗漏、冲突、分析深度和过度推断
  -> Revision：按问题清单修订主答案
  -> Light Recheck：确认修订有效且未引入新问题
  -> Confidence Appendix：对关键结论分层并解释依据、冲突和缺口
  -> 最终报告：完整正文 -> 参考文献与证据 -> 置信度附录（最后一节）
```

新增或扩展运行内结构化协议：

- `ResearchPlan`：原问题、问题类型、目标读者、时间边界、子问题、来源偏好、预算和停止条件。
- `ClaimDraft`：声明 ID、声明文本、类型、重要性、时效性、风险等级、待核验项和生成来源。
- `EvidenceItem`：来源通道、来源身份、正文片段、页码/章节/URL、发布时间、获取时间、直接性、权威性和支持/限制/矛盾关系。
- `SourceCoverage`：每个子问题在 Model/RAG/Web 的可用、失败、未需要、已覆盖和待补证状态。
- `ClaimAssessment`：证据是否足以表达声明、允许的措辞强度、冲突、限制和建议动作，不以固定通道权重直接计算真值。
- `VerificationIssue`：关联声明、问题类型、严重度、证据、修订建议和复核状态。
- `CitationEntry`：稳定数字序号、来源类型、题名/作者/机构、日期、URL 或论文 ID、页码/章节/Chunk 定位、原始引用内容及其支持的声明 ID。
- `ConfidenceAssessment`：关键结论 ID、置信度等级、证据序号、评价依据、冲突、时效性和待核验条件；只在最终附录中面向用户呈现。

协议必须保持 JSON 可序列化，先作为 Run 内 `StepResult`/Artifact 使用；不得为了 P1 提前建设数据库。正文数字引用必须经 `CitationEntry` 反向定位到 `EvidenceItem`，所有关键结论必须能定位到对应 `ClaimDraft/ClaimAssessment`，并在 `ConfidenceAssessment` 中得到评价或明确标记为待核验分析。

### P1.5 低、中、高模型分层与路由

研究深度必须由显式 `ResearchProfile` 驱动，至少包含模型角色、RAG/Web 检索预算、子问题并发、最大补证轮次、候选规模、FactCheck 强度、Token/费用上限和超时。模型供应商和具体型号全部由用户配置，业务代码只读取 preset/role，不硬编码 DeepSeek、MiniMax、Qwen、Gemini 或其他模型。当前开发评测曾使用 DeepSeek、MiniMax、Qwen 等配置，但这些值不构成产品默认绑定；Gemini 因实测成本偏高暂停使用和对比，后续只有在用户明确重新启用时才进入真实评测。

初始分层：

| 模式 | 模型策略 | 研究循环 | 适用场景 |
|---|---|---|---|
| 低 | 轻量/Flash 级模型负责规划、重排和综合；允许关键步骤共享同一轻量模型 | 单轮 RAG/Web，少量候选；仅对关键事实轻核验 | 快速背景查询、低风险问题、成本敏感场景 |
| 中 | 中高档模型负责 Model Prior、最终综合和 FactCheck；轻量模型负责查询改写、候选初筛和格式修复 | 最多 1 轮缺口补证，标准候选规模，完整修订一次 | 默认研究查询、技术比较、文献综述 |
| 高 | 最新稳定旗舰/Pro 级模型负责 Model Prior、复杂重排、综合、冲突分析和 FactCheck；轻量模型只做机械辅助 | 最多 2 轮缺口补证，更大候选集，对关键声明交叉核验 | 高价值决策、复杂综述、强时效或高风险问题 |

高/Deep 档是与 GPT Deep Research 进行同题对标和 P1 首要目标验收的直接档位。中/Standard 档允许在成本和延迟上折中，但不能通过删除重要维度或只保留易引用内容而退化成摘要；低/Quick 档明确定位为快速研究，不冒充 Deep Research 等价产物。

实现要求：

- 配置中明确 `planner_model`、`analyst_model`、`reranker_model`、`synthesizer_model`、`verifier_model` 和各自 fallback。
- 启动诊断应显示每个角色最终解析后的 preset、provider、model、版本和能力档位。用户可以有意复用同一模型，但低、中、高的检索、并发、核验和预算策略必须有实质差异。
- fallback 必须记录原因和实际模型，不能静默把高模式降成低模型后仍显示“高深度”。
- 模型路由按任务难度和角色决定，不要求所有步骤都调用最强模型；强模型优先用于问题框架、最终综合、复杂冲突和修订。
- Prompt、模型版本、采样参数、Token、成本和延迟进入 Trace，以便进行模型/Prompt 对比。
- 模型不可用时保留 RAG/Web 证据并使用可用 fallback 综合；若无法生成最终答案，应明确是生成能力失败，而不是把已有证据判为无价值。
- 每档必须使用阶段级时间预算，保证覆盖分析、最终综合和必要核验有实际执行窗口；不得以单次模型最大超时乘以剩余调用数的粗粒度预留，导致 Evidence Analyst 在正常运行中系统性被跳过。
- 用户选择某档位即表示接受该档预算。预算优化首先减少重复调用、无效搜索和串行等待，不先压缩核心维度、案例、分析链和建议。

验收标准：

- 低、中、高三种配置的检索、并发、核验和预算明显不同，并有配置/契约测试防止档位策略意外坍缩；不以模型 ID 必须不同作为硬门禁。
- 同一评测集能生成按模式分组的质量、成本和延迟报告，不能只比较报告长度。
- 模型提供商或模型家族对比由用户在明确预算下选择；Gemini 当前暂停，不作为 P1 退出阻塞项。默认模型只能来自用户配置和真实评测结果，不能由后台代码决定。

### P1.6 Model Prior、研究计划与问题覆盖

将当前 Model Agent 拆成两个职责：

1. `Model Prior` 在外部检索前生成背景框架、可能答案、关键术语、时间敏感点、争议点和待核验声明，用于扩大研究广度，不直接伪装成已引用事实。
2. `Evidence Analyst/Synthesizer` 在检索后读取证据，判断每条声明可表达的强度，完成综合、冲突解释和修订。

实现要求：

- 移除“Model 不是新的事实来源”的绝对限制和 `model_inference=0.2` 一类固定通道惩罚。
- Model Prior 输出必须区分通用背景、候选事实、分析推断和建议；高时效、精确数字、人物/机构归属和高风险事实默认进入待核验列表。
- 质量门禁不再因 `Model-only` 自动失败，而是检查答案是否自洽、是否把不可核验事实说得过强、是否清楚说明外部证据覆盖不足。
- Research Plan 为每个子问题建立覆盖矩阵，明确优先使用 RAG、Web 或 Model 的理由；不强求每个子问题调用全部来源。
- 模型生成的同义词、英文术语、代表性方法和可能来源类型可以进入 RAG/Web 查询规划，但不能直接成为伪造引用。
- Model Prior 形成的关键维度必须成为最终正文骨架或明确的研究缺口，Synthesizer 不得只展开最容易引用的一个维度而丢弃其余框架。
- Model 提供的解释、机制和建议可以自然进入正文，不再单独插入“非外部事实”等打断阅读的固定分区；其证据边界和置信度统一在报告最后的置信度附录说明。

验收标准：

- RAG/Web 均不可用时，低风险开放问题仍能得到有结构、有实质内容的临时答案，且只在末尾说明外部证据未覆盖。
- Model-only 不再被固定权重或通道规则直接判为失败；高风险事实仍会触发待核验或谨慎措辞。
- Model Prior 提出的关键研究维度能够在最终答案或“未覆盖问题”中逐项闭合，避免规划完成后被丢弃。

### P1.7 全文入库真实性与分层 RAG

先修复知识输入真实性，再优化召回和排序。受影响边界至少包括论文下载/提取、`paper_indexer`、RAG Connector、入库报告和 Workbench 状态显示。

全文链路要求：

- 将 PDF 正文解析器放入正常安装可用的运行时依赖或默认启用的 knowledge extra，并由 `conflux doctor`/启动诊断检查；不得只存在于 dev 依赖。
- 统一记录 `full_text_requested`、`full_text_downloaded`、`full_text_extracted`、`full_text_indexed` 和失败原因；UI 的“全文入库”只能由实际索引结果决定，不能由策略动作推断。
- 正文提取失败时允许摘要回退，但文档类型、报告和 Trace 必须明确为 `summary_only`，并提供重试入口。
- 使用内容哈希和版本化 upsert；同一论文从摘要升级到全文时必须替换或降权旧摘要文档，不能永久被已有 `chunk_id` 遮蔽。
- 保留论文、章节、页码和块级定位；优先识别 `abstract`、`method`、`results`、`limitations`、`discussion`、`future_work`。

RAG 检索链路要求：

```text
子问题查询包（原文 + 英译 + 术语/章节扩展）
  -> 论文级召回
  -> 章节级召回
  -> 块级 Dense + BM25 扩大候选
  -> 去重和同论文多样性控制
  -> Cross-Encoder 或 LLM 语义重排
  -> 证据片段提取与逐声明对齐
```

- 人工加权融合仅作为可解释召回特征，不再承担最终语义判断；文件名、实体重合不能把不相关内容推到最终证据首位。
- 分开记录原始 Dense、BM25、融合排名、语义重排结果和最终采用原因。
- 先扩大候选再重排，候选规模由研究模式控制；跨语言词法分数为零不能直接淘汰候选。
- 对局限、失败模式、未来工作等问题优先检索对应章节，并允许围绕每个子问题生成独立查询包。
- 最终引用必须包含可复核文本片段和页码/章节；不能只引用论文标题或摘要元数据。

专项回归至少覆盖 ShapefileGPT、Autonomous GIS 和 LLM-Find 的限制章节，验证原文中已存在的计算成本、错误处理、幻觉、任务覆盖、代码失败、调试、栅格支持、在线数据发现、多模态、上下文和数据适用性等信息可以被召回并用于回答。

验收标准：

- 下载成功但解析器缺失的场景会显式失败诊断，不再显示“全文入库”。
- 三篇专项论文的限制章节能进入扩大候选集，并有直接片段进入语义重排后的证据集。
- P1 标注集上的 `recall@10` 初始目标不低于 0.80，且 `NDCG@10`、无关命中率和章节命中率相对 P0 基线改善；若未达标不得用放宽答案门禁代替检索修复。
- 每条被采用的 RAG 关键证据均可定位到论文、章节/页码和原文片段。

### P1.8 Web Search、Fetch 与来源路由

将 Web 能力拆成 `Search` 和 `Fetch` 两层。搜索标题和 snippet 只用于发现、去重和抓取排序，默认不作为支撑关键声明的主要证据。

实现要求：

- Query Planner 按子问题生成 2-4 个互补查询，覆盖原始语言、英文术语、时效限定和来源类型，不把全部子问题拼成一个长查询。
- 通用问题走授权搜索 API；学术问题优先路由 Semantic Scholar、OpenAlex、Crossref、arXiv 和论文落地页；标准、产品和政策问题优先官方/第一方来源。
- Fetch 支持 HTML 和可公开访问的 PDF，记录最终 URL、标题、作者/机构、发布时间/更新时间、获取时间、内容类型和正文哈希。
- 正文抽取后按段落/章节切块，保留可引用定位；遇到登录墙、robots/服务条款限制、下载失败或正文过短时标记为 `unfetched`，继续使用其他来源。
- 对相同 URL、canonical URL、DOI 和高度相似正文去重；转载数量不能提升原始声明的权威性。
- 网页内容始终视为不可信输入，隔离 Prompt Injection 指令，仅提取事实内容和来源元数据。
- 搜索结果经过语义相关性、来源类型、直接性、时效性和正文可得性排序；权威性按具体来源判断，不按“Web”通道一概降低。

验收标准：

- 最终引用的 Web 关键证据必须来自成功获取的正文片段；仅 snippet 可用时不能伪装成已核验正文。
- 主搜索 provider 失败、部分页面不可访问或学术 API 限流时，研究仍能降级完成并在末尾只说明实际覆盖缺口。
- 至少覆盖 HTML、PDF、重定向、重复转载、正文抽取失败、Prompt Injection 和来源更新时间缺失的测试场景。
- 时效型评测问题能引用知识截止日期之后的有效 Web 信息，并区分发布日、更新日和获取日。

### P1.9 自适应子问题研究循环

以 `ResearchPlan.subquestions` 为循环单位，替换当前将多个子问题拼成一个组合查询的做法。每个子问题独立记录查询、候选、证据、覆盖和停止原因。

补证触发条件包括：

- 重要声明没有直接证据，或只有待核验的 Model Prior。
- RAG 命中论文但没有命中相关章节/片段。
- Web 只有 snippet、转载或过期内容。
- 来源对同一声明实质冲突。
- FactCheck 发现关键遗漏、引用不支持、措辞过强或时效性问题。

循环规则：

- 先修改查询、来源类型或章节定位，再决定是否扩大候选，不能无差别重复同一搜索。
- 中模式最多 1 轮、高模式最多 2 轮缺口补证；低模式默认不循环，仅对关键事实例外。
- 达到证据充分、边际收益过低、预算/时间上限、来源不可用或继续检索不会改变结论时停止，并记录原因。
- 来源缺失本身不触发无限搜索；若 Model + 单一高质量来源已足够回答，可直接综合。
- 真正冲突进入专门仲裁，输出冲突点、来源差异、时间/定义差异和允许的结论范围，不以简单多数决解决。

P1 将“本轮临时论文语料库”提升为达到首要目标的必要能力：当本地 RAG 覆盖不足而 Web 或学术搜索发现高价值论文时，`RunScopedCorpusProvider` 应在当前 Run 内下载、解析、切块和检索全文，用于继续补证和综合。Run 结束后由用户决定是否永久晋升；P1 仍不允许未经确认自动写入永久知识库。

验收标准：

- Trace 中可以看到每个子问题独立的查询、来源覆盖、补证原因和停止原因。
- 组合问题不会再只产生一个混合 RAG/Web 查询。
- 新增证据后必须重新进入声明对齐和综合，不能只追加一段“深度研究结果”。

### P1.10 声明融合、完整报告、数字引用与置信度附录

Synthesizer 以 `ClaimAssessment` 和已采用 `EvidenceItem` 为输入，不直接拼接三个来源的整段输出。声明分为外部可核验事实、模型参数化背景、分析判断、建议和未解决问题，并使用与证据强度匹配的措辞。

融合规则：

- 直接、高权威且与声明完全匹配的 RAG/Web 单源证据可以支撑事实；多源独立一致用于增强而非准入。
- Model Prior 可补充解释、分类、机制推理和低风险背景；没有外部证据时不得虚构引用，并避免对高风险/强时效事实作确定断言。
- 来源冲突时保留不同结论及其条件，优先解释定义、样本、时间和方法差异；无法解决时明确不确定范围。
- 每个关键外部事实的引用必须通过引用解析器校验，确认数字序号能解析到成功来源、定位信息和实际支撑内容。
- 主答案追求覆盖研究问题，而不是覆盖所有来源；只有与结论相关的证据进入正文。
- 广泛综述的每个重要维度原则上包含结论、作用机制、代表性证据或案例、影响边界，以及缓解方向或待解决问题；无直接证据时允许保留有价值的 Model 分析，但必须进入最后的置信度分层。
- 报告长度随问题复杂度、研究档位、维度数量和证据密度动态决定，不设置与 Deep Research 目标冲突的固定低字符上限；同时继续禁止重复、空泛扩写和术语堆砌。

默认报告结构调整为：

```markdown
## 回答
（按问题自然组织完整结论、机制、案例、影响和建议，不单独堆砌三源输出；正文只出现 [1]、[2]、[1,3] 等紧凑数字引用）

### 维度一
（连续正文）

### 维度二
（连续正文）

## 参考文献与证据
1. 来源题名、作者/机构、年份、来源类型、URL/论文 ID、页码/章节/Chunk 定位。
   - 引用内容：实际用于支撑正文结论的原文片段；必要时附忠实中文释义。
2. ...

## 置信度附录
| 关键结论 | 置信度 | 依据 | 限制与待核验项 |
|---|---|---|---|
| 结论 A | 高/中/低/待核验 | [1][3] 或 Model 综合 | ... |
```

实现要求：

- 正文不得出现 `[RAG:paper:...#fulltext-x]`、`[Web:https://...]` 等内部长标识，不直接展开 URL、Chunk ID、来源状态、抓取失败或逐声明评分。
- `Citation Compiler` 对实际采用的 `EvidenceItem` 去重并稳定编号；同一证据在全文重复使用同一数字，不同证据不得复用一个数字。
- 正文引用使用 `[1]`、`[2]`、`[1,3]` 等格式，放在相关句或段落末尾。完整书目信息、网页信息、正文定位和实际引用内容只在“参考文献与证据”中出现。
- “参考文献与证据”中的每一项都必须包含足以复核正文的引用内容；只有题名、URL 或论文摘要元数据不能算完整证据条目。
- “置信度附录”必须是报告最后一个顶层章节。附录按关键结论分层，不逐句复述正文，也不在正文中反复插入高/中/低标签。
- 置信度等级至少包含 `高`、`中`、`低`、`待核验`，综合考虑证据直接性、来源权威性、时效性、独立一致性、冲突和推理跨度，不能按 RAG/Web/Model 通道固定赋值。
- 置信度较低不等于默认删除。对问题完整性有价值、风险可控且明确属于分析判断的内容可以保留；高风险、强时效或精确事实在证据不足时必须补证、降强措辞或标为待核验。
- 全局状态、逐声明原始评分、来源覆盖矩阵、运行日志和详细 FactCheck 继续保留在审计 Artifact 或 Workbench 展开区，不进入用户正文。

验收标准：

- 用户首先连续读到完整答案，不被来源长标识、置信度标签、运行状态或免责声明打断。
- 所有正文数字引用均能解析到唯一的参考文献与证据条目，且条目中的引用内容直接支持对应结论；Model 分析没有被伪装成外部引用。
- 置信度附录固定在报告最后，覆盖全部关键结论并给出可理解的分层理由；正文中不重复展示该评价。
- 来源失败场景仍输出当前条件下尽可能完整的答案，并在最后附录中准确反映证据缺口，不以删减大部分正文换取高置信度。
- 三源均可用时，最终报告按主题/问题组织，而不是按 RAG、Web、Model 三段机械排列。

### P1.11 FactCheck、修订与轻量复核闭环

FactCheck 从报告末尾的被动标签改为可执行质量步骤，输出结构化 `VerificationIssue[]`：

- `unsupported_claim`：引用不存在、引用不支持或只有 snippet。
- `overstated_claim`：证据只支持相关性/可能性，答案却写成因果或确定事实。
- `missing_dimension`：Research Plan 的重要维度未回答、只有标题没有实质分析，或 `SourceCoverage` 已标记关键 gap 却没有补证/待核验处理。
- `stale_or_undated`：时效型事实缺少适当日期或来源已过期。
- `source_conflict`：相同定义和时间范围下的来源实质矛盾。
- `citation_mismatch`：引用 ID、页码、URL 或片段与声明不匹配。
- `unsafe_content_use`：采纳网页中的指令性内容或泄漏失败来源。

闭环要求：

1. FactCheck 将问题关联到声明 ID、证据 ID、严重度和建议动作。
2. 严重问题优先触发已有证据内修订；重要维度覆盖不足时，即使语义核验器没有额外报错，也必须由 `SourceCoverage` 直接生成补证问题并进入受预算约束的子问题研究。
3. Synthesizer 基于问题清单和新增证据重写主答案，而不是在末尾追加修正说明。
4. Citation Compiler 在正文稳定后重新编号并生成“参考文献与证据”，避免修订造成悬空、错号或重复编号。
5. Light Recheck 复核被修改声明、数字引用解析、证据内容、覆盖矩阵、置信度附录和安全门禁。
6. 超过模式允许轮次或仍存在关键问题时输出 `needs_review`，但保留已修订的最佳答案，并在最后的置信度附录准确标出影响范围。

深度质量评分移除纯关键词和章节齐全达标逻辑，按优先级采用“完整性与问题覆盖、分析深度、事实正确、案例与机制、建议价值、证据支持、来源质量、时效性、表达连贯性”的评审 Rubric。引用正确和置信度校准是必要约束，但不得通过减少正文声明提高总分。确定性检查只负责数字引用解析、证据条目完整性、URL/页码格式、失败来源泄漏、附录顺序等可机械验证项。

验收标准：

- 人工注入一个错误引用、一个过强结论和一个遗漏维度后，FactCheck 能定位问题，主答案被实际改写，复核状态可追溯。
- 深度研究新增证据后重新生成主报告，旧结论不会与追加内容并存冲突。
- `needs_review` 表示修订后仍有实质问题，不再只是 FactCheck 已发现但未处理的终点标签。
- 将“只展开一个有引用维度、其余维度一句带过”的报告作为固定反例；即使现有声明引用率为 100%，也必须因广度和深度不足而失败并触发补证或重写。

### P1.12 评测集、消融实验与可观测性

P1 建立独立的研究质量评测集，不以现有离线模板通过率代替真实答案质量。评测集首版不少于 30 个问题，至少覆盖：

- 本地论文可直接回答但需要章节级检索的问题。
- 需要 Model 世界知识提供框架和跨论文综合的问题。
- 需要近期 Web 信息的问题。
- 中英跨语言、复杂多子问题、来源冲突和定义歧义问题。
- RAG 缺失、Web 失败、Model fallback、PDF 提取失败和只有摘要的降级问题。
- 地理处理自动化局限性专项回归及其关键原文声明。
- 与 `reports/workbench/deep-research-report.md` 的同题盲评对标，重点比较维度覆盖、机制、案例、影响、建议和整体可读性，不把篇幅或来源数量本身作为得分代理。

每次 P1 候选版本至少校验以下消融矩阵定义和离线契约；真实 API 默认采用分层代表性样本，不因矩阵存在就自动运行全部 540 个组合。只有用户明确批准预算后才执行全量真实矩阵：

| 场景 | 目的 |
|---|---|
| Model only | 验证模型世界知识的独立价值和恰当边界 |
| Model + RAG | 验证本地知识对准确性、深度和引用的增益 |
| Model + Web | 验证广度、时效性和外部证据增益 |
| Model + RAG + Web | 验证完整三源流程是否产生净收益 |
| 任一来源失败 | 验证降级后仍可回答且说明不过度 |
| 低/中/高模式 | 验证模型、循环、质量、成本和延迟确有差异 |

评测指标：

- **首要产出指标**：人工/强模型匿名成对盲评，对比 GPT Deep Research 参考报告的正确性、完整性、维度广度、机制与因果分析深度、案例具体性、建议可操作性、时效性和表达连贯性，均使用明确 1-5 Rubric，并记录偏好胜/平/负。
- **覆盖指标**：重要子问题完成率、核心维度实质展开率、每个维度的机制/案例/影响/建议覆盖、未闭合高重要度 gap 数；不能用章节标题命中代替实质覆盖。
- **引用与证据约束**：关键外部声明覆盖率、数字引用正确率、引用内容直接支持率、证据条目完整率、失效引用率；这些指标作为正确性门禁，不替代首要产出评分。
- **置信度指标**：关键结论附录覆盖率、分层理由完整率、人工复核一致率、过度自信率和低置信内容误删率；置信度评价不得出现在正文阅读区。
- RAG：`recall@k`、`NDCG@k`、章节命中率、无关命中率、重排前后增益。
- Web：正文获取率、被引用来源正文可用率、学术/官方/一手来源比例、重复转载率、时效覆盖、知识库外新增核心维度数和 RunScoped 全文入库成功率。
- 闭环：FactCheck 问题发现率、修订成功率、复核后残留严重问题数。
- 运行：分模式 p50/p95 延迟、Token、费用、搜索/抓取次数、补证轮次、超时和 fallback。

P1 重新定义后的退出目标：

- “地理处理自动化局限性”使用 Deep 档进行同题匿名成对盲评，在总体偏好以及正确性、广度、深度、案例和建议五项核心指标上不得低于 GPT Deep Research 参考报告；任何一项低于 4/5 均不通过。
- 该专项至少实质展开数据、算法/方法、系统工程、评估与基准、治理/伦理、应用边界等互补维度；每个核心维度包含机制，并尽可能包含直接证据或案例、影响和缓解方向。缺证据时保留有价值分析并在附录降级，不得静默删除维度。
- 专项报告应获得足以支撑广泛综述的多样化来源。初始门禁为不少于 8 个有效外部来源、其中不少于 5 个独立学术/官方/一手来源；来源计数只是覆盖下限，重复转载和与结论不直接相关的材料不计入。
- 分层真实样本的首要产出质量中位数不低于 4/5，Deep 档关键样本不得低于 4/5；Standard 档不得出现重要维度系统性缺失。全量 30 问继续用于离线合同、录制响应和用户批准后的批量复测。
- 关键外部声明数字引用正确率不低于 95%、覆盖率不低于 85%，证据条目完整率和被引用 Web 正文可用率为 100%；只有 snippet 的结果不得计为已核验证据。
- 全部关键结论进入最后的置信度附录，人工抽样分层一致率不低于 85%，不得存在高风险事实被标为高置信却无直接证据的情况；正文不得穿插置信度标签或内部来源长标识。
- Model-only 和任一来源失败场景不因通道规则直接失败，但首要产出评分仍必须如实反映广度、深度和时效损失，不能因引用分母缩小获得虚高评价。
- P1 新链路不降低 P0 的安全指标：失败来源泄漏和 Prompt Injection 泄漏保持 0。
- 低、中、高模式的质量/成本/延迟差异可以被测量；Deep 档必须体现稳定的质量增益。成本和延迟超限需要继续优化，但不能以牺牲 Deep 档首要产出目标作为退出方式。

所有自动评审必须保留评审模型、Prompt、输入哈希和理由，并抽样人工复核，避免“生成模型和评分模型共享偏好”造成虚高。评测报告需同时列出失败样本，不能只报告平均分。

|---|---|---|---|
| 8 | GPT Deep Research 对标基线 | 同题参考报告拆解、1-5 分 Rubric、匿名成对盲评器、失败反例 | 能稳定识别“引用正确但广度/深度不足”的短报告为失败 |

工作包 8-13 不得仅以接口、单元测试或 Artifact 已生成作为完成标准。每完成一个工作包，都要重跑“当前地理处理自动化研究存在哪些局限性”代表样本并与参考报告盲评；若真实报告未改善，应先纠正该工作包的策略或实现，再进入下一步。

分层验证要求：

- 日常快速测试使用固定论文片段、录制网页、FakeModel 和临时索引，覆盖协议、路由、降级和修订分支。
- 阶段测试使用完整 PDF、HTML/PDF 抽取、跨语言查询、来源冲突和模型录制响应。
- 真实 API 测试显式开启，使用用户配置的低/中/高档代表性样本，记录实际 provider/model、质量、成本、延迟、限流与 fallback。Gemini 当前暂停，不得由测试脚本隐式启用。
- 每完成一个顺序项即更新评测报告，不允许全部实现后才第一次检查答案质量。

回滚策略：

- 新研究流程使用 `research_pipeline_v2` 或等价显式开关，P1 稳定前保留 P0 路径用于对照和紧急回滚。
- `ResearchPlan`、`ClaimDraft`、`EvidenceItem` 等协议带版本号；旧报告读取路径保持兼容，但新流程不长期双写两套主状态。
- Web Fetch 可单独关闭并退回 Search 发现 + RAG/Model；语义重排可切换到备用模型，但必须显示降级。
- 全文索引升级前保留原文和索引快照；失败时可重建索引，不删除用户论文或审批记录。
- 回滚不得恢复“策略决定即显示全文入库”、Model-only 固定失败、snippet 作为已核验证据或 FactCheck 不修订答案等已知错误行为。

P1 总验收必须同时满足：

1. Deep 档在同题、相近时间边界下与 GPT Deep Research 参考报告匿名成对盲评，总体偏好以及正确性、广度、深度、案例和建议五项核心指标达到 P1.12 退出目标；不能用篇幅、引用率或格式完整代替。
2. 三源按声明互补并产生可测量的净收益；缺少任一来源时仍尽可能完整回答，并在附录如实降低相关结论置信度，而不是删除重要维度。
3. 低、中、高研究深度使用用户配置的模型角色，并具有真实不同的检索、并发、预算和循环策略；允许用户有意复用模型，后台不得写死具体提供商或型号，Gemini 保持暂停。
4. 论文全文状态真实；RAG 能从相关章节召回、语义重排并提供可定位的直接片段，摘要记录不能伪装成全文入库。
5. Web 能从搜索进入高质量网页或 PDF 正文获取；关键引用不依赖标题或 snippet，当前 Run 发现的高价值论文可通过 `RunScopedCorpusProvider` 临时解析和补证。
6. 子问题独立研究；重要维度 coverage gap 能自动触发有限补证，新增证据会重新综合主答案，阶段预算保证 Evidence Analyst、Synthesizer、FactCheck 和必要修订实际执行。
7. Model 世界知识用于建立完整框架、解释机制和综合洞察，不再被系统性贬低；高风险、强时效和精确事实仍受到适当核验约束。
8. FactCheck 能驱动修订和复核；质量评分能识别窄、浅、无案例或无建议的报告，不再因“少量声明全部有引用”或关键词出现而虚高。
9. 最终报告严格采用“完整正文 → 参考文献与证据 → 置信度附录”的顺序；正文只显示稳定数字引用，参考条目包含完整来源、定位和实际引用内容，置信度附录是最后一个顶层章节。
10. 三源消融、来源故障、模型对比、专项回归和真实 API 评测达到 P1.12 全部退出目标；成本和延迟作为显式约束持续优化，但不得以牺牲 Deep 档回答质量、广度和深度换取通过。
11. 全量测试、安全回归和 `git diff --check` 通过，且未引入 M3/M6 范围内容。

P1 未完成或验收不通过时，不进入 M3 的 SQLite Run Store、持久 Job、初始化或迁移实现。

## P1.5：泛化深度研究与内容扩展（实现及离线验收完成；真实对标待预算；V2 answer_first 已替代为默认管道）

### P1.5.1 阶段目标与成功定义

P1.5 位于已验收的 P1 与 P2 之间。P1 已证明三源研究链路可以在代表性问题上形成结构完整、证据可追溯的回答，但后续真实使用表明：单个领域特例达到预期，不等于系统已经具备跨领域、跨问题类型的稳定深度研究能力；报告结构正确，也不等于内容广度、细节密度和主动补缺能力已经达到成熟深度研究智能体水平。

P1.5 的首要目标是：**将 P1 的单题高质量能力泛化为由问题原型、动态领域地图、覆盖矩阵和分层综合共同驱动的深度研究能力，并保证 RAG 缺失时仍可由 Web 正文证据与明确标注的 Model 分析形成可信报告。**

成功不能由某个领域的专用规则、固定章节模板、单次真实报告或单一引用率证明。P1.5 完成后必须同时具备：

- 面对不同领域的宽泛综述、现状趋势、局限挑战、技术比较、因果机制、方案设计和证据综述问题，能够先建立问题地图，再按覆盖缺口持续检索。
- 本地 RAG 为 `no_evidence`、`failed` 或没有相关语料时，只要 Web 取得可用正文证据，研究流程仍能完成事实充分、引用有效的报告；不得把 RAG 缺失误判为整个研究失败。
- Deep 档不再受固定少量子问题、固定 8 条最终证据或一次整体综合的结构性限制；预算根据问题广度、维度数量、证据稀缺度和冲突程度动态分配。
- 最终报告的章节标题、顺序和内容要求由问题原型、用户意图与动态研究维度生成，不为地理处理、医学、法律、材料、软件工程或任何单一领域写死模板。
- 报告每个主要章节都能回溯到研究问题、覆盖目标、证据要求和完成状态；不能以篇幅增长、来源堆叠或模型常识扩写冒充研究深度。

### P1.5.2 范围原则与非目标

P1.5 遵循以下原则：

1. **问题类型优先于领域特例。** 允许配置领域词表、来源适配器和术语别名，但不得在核心研究图中为单个主题硬编码方法分类或固定答案章节。
2. **RAG 是可选证据源，不是流程前置条件。** Model、RAG、Web 保持不同证据角色和独立状态；一个来源缺失不应阻断其他来源继续研究。
3. **先覆盖、再深挖、后综合。** 宽泛问题先建立领域地图和覆盖矩阵，再对关键维度进行深度检索；不得由最先返回的少数论文重新定义整个问题范围。
4. **丰富度来自证据化展开。** 增加章节和篇幅必须伴随新的机制、案例、比较、边界或证据，不允许重复改写同一观点填充长度。
5. **报告结构是动态契约。** 系统只规定回答完整性、证据追踪和可靠性等功能要求，不规定某个领域必须出现哪些标题。

P1.5 不提前实施 P2 的项目论文关联、审批写回和论文雷达界面，不实施 M3 的持久 Job、SQLite Repository 或跨进程调度，也不把临时领域分类自动写入永久知识库。

### P1.5.3 关键建设项 1：通用问题类型规划器

将当前主要依赖自由生成子问题和少量领域归一化规则的规划方式，升级为显式 `QueryArchetype` 与 `ResearchStrategy` 协议。首版至少识别：

- 方法、技术或方案综述。
- 现状、进展与趋势分析。
- 局限、挑战与开放问题。
- 对象、技术或观点比较。
- 因果关系、作用机制与影响分析。
- 解决方案、架构或实施路径设计。
- 证据综述、共识与争议评估。

每种问题原型只定义通用研究动作，不携带领域章节。例如“方法综述”要求发现分类维度、机制、代表实现、适用条件、优势、限制、成熟度和组合关系；具体分类名称必须由查询、Model prior、术语发现和首轮证据共同生成。

新增或扩展以下运行内协议：

```text
QueryArchetype
  type
  confidence
  user_intent
  expected_research_actions[]
  required_synthesis_functions[]

DomainMap
  scope
  key_concepts[]
  terminology[]
  dimensions[]
  dimension_relations[]
  disputed_boundaries[]
  discovery_sources[]
```

低置信问题类型允许形成主类型与次类型组合，但必须记录选择理由。规划失败时退回通用探索流程，不能退回到某个领域专用模板。

### P1.5.4 关键建设项 2：广度扫描与深度追踪循环

宽泛问题采用“领域地图 -> 广度扫描 -> 维度筛选 -> 逐维深挖 -> 覆盖复核”的循环，不再直接把固定 4-6 个子问题作为最终研究边界。

目标流程：

```text
Query + QueryArchetype
  -> exploratory terminology and taxonomy discovery
  -> DomainMap / ResearchDimension[]
  -> breadth queries for every major dimension
  -> CoverageMatrix
  -> prioritize important, weak, conflicting, or evidence-poor dimensions
  -> targeted depth queries
  -> update evidence and coverage
  -> repeat until coverage, saturation, budget, or explicit evidence scarcity stop
```

`ResearchDimension` 至少包含：维度名称、纳入理由、父子关系、需要回答的问题、期望证据类型、重要性、当前覆盖、冲突、缺口和停止条件。首轮发现的新维度必须经过相关性和去重判断后才能进入计划，不能无限扩张。

`CoverageMatrix` 不只记录“是否有结果”，还要记录：

- 是否取得正文证据，而非仅有搜索标题或摘要片段。
- 是否覆盖定义、机制、代表实现、适用条件、局限、比较或其他由问题原型要求的研究动作。
- 是否存在至少一个高权威来源，以及是否需要第二个独立来源交叉验证。
- 是否存在来源冲突、时间冲突、术语歧义或只有 Model 分析没有外部证据。
- 当前维度是已覆盖、部分覆盖、证据稀缺、相互冲突还是超出范围。

停止条件改为覆盖和证据饱和联合判断。达到固定搜索次数或结果数量不能单独结束 Deep 研究。

### P1.5.5 关键建设项 3：动态证据与运行预算

将 `max_subquestions`、`final_evidence_limit`、Web 抓取数、报告长度和缺口迭代次数从固定档位上限升级为“档位基础预算 + 问题复杂度调整 + 全局硬上限”。复杂度至少参考：

- 问题原型及其要求的研究动作数量。
- 动态领域地图中的主要维度和子维度数量。
- 时间范围、比较对象数量和用户要求的细节层级。
- 已取得证据的权威性、多样性、冲突和稀缺程度。
- RAG、Web、学术 API 和官方来源的实际健康状态。

Deep 档的初始工程建议是：宽泛问题允许约 8-15 个主要研究维度、20-40 条进入最终综合的高价值证据，以及按章节分配的输出预算；这些数字是可配置起点，不是所有问题必须填满的质量指标。窄问题应主动收缩，证据稀缺问题应明确停止并报告缺口。

预算分配必须满足：

- 先为每个高重要性维度保留最低检索和证据预算，再把剩余预算投入冲突、缺口和关键细节。
- 同一来源或同一观点不能通过重复条目挤占证据预算。
- 报告长度随已验证内容增长，而不是随用户问题字数或固定档位机械增长。
- 超时降级仍按 `DomainMap` 和 `CoverageMatrix` 输出已完成维度、未完成维度和下一步检索，不退化为少量链接或无结构摘要。

### P1.5.6 关键建设项 4：章节级研究与分层综合

将“一次性把全部证据交给单个综合器”调整为章节级综合和全局综合两层流程：

```text
ResearchDimension + scoped evidence
  -> SectionDraft / SectionClaim[]
  -> section-level citation and completeness verification
  -> cross-section comparison, deduplication, and conflict analysis
  -> complete report synthesis
  -> global factcheck and gap review
```

每个章节先独立完成本维度的回答、机制展开、代表证据、适用边界和未解决问题，再由全局综合器处理跨维度关系、共同模式、差异、组合方案和总体结论。全局综合不得压缩掉已经通过章节核验的关键机制或限制，也不得简单拼接多个小报告。

章节级产物至少记录：`dimension_id`、研究问题、关键声明、证据引用、内容覆盖、冲突、未解决缺口、建议篇幅和综合优先级。FactCheck 发现单个章节不足时，优先生成针对该章节的检索问题，而不是重写整篇报告后再次丢失其他章节细节。

### P1.5.7 关键建设项 5：来源类型路由与 RAG 空库降级

来源路由从“所有问题统一搜三源”升级为按维度和证据需求生成 `SourcePlan`。通用来源类型至少包括：

- 学术综述、原始研究、预印本和基准评测。
- 官方文档、标准、规范、政策和版本说明。
- 开源仓库、技术文档和可复现实验材料。
- 权威机构报告、数据集说明和高质量案例研究。
- Model parametric knowledge，用于概念框架、查询扩展、机制分析和建议，但不伪装成外部引用。

不同领域可以注册来源适配器和权威域规则，但核心路由只依赖证据需求、来源类型、时效性和权威性，不依赖硬编码领域答案。

RAG 空库或无相关内容时必须满足：

1. RAG 返回明确的 `no_evidence` 或 `low_relevance`，不得伪装成功，也不得阻断 Web 和 Model。
2. Web 继续执行学术 API、官方来源和通用正文检索；取得正文证据后按正常外部事实参与综合和核验。
3. RAG 缺失本身不降低 Web 已充分支持声明的置信度，只作为来源覆盖状态披露。
4. Web 也无法取得正文时，允许输出明确标注的 Model 分析、已发现线索和待核验问题，但不得把搜索摘要、URL 或模型记忆包装成已证实事实。
5. 增加 `RAG=empty/Web=success`、`RAG=failed/Web=success`、`RAG=success/Web=failed`、双外部源失败等独立回归场景。

### P1.5.8 关键建设项 6：泛化深度研究报告契约

P1.5 不定义任何领域专用的“标准报告目录”。报告由 `QueryArchetype + DomainMap + CoverageMatrix + UserIntent` 动态生成 `ReportOutline`，再为每一节生成 `SectionContract`：

```text
ReportOutline
  query_archetype
  audience
  scope
  answer_strategy
  sections[]
  cross_section_synthesis[]
  citation_policy
  reliability_policy

SectionContract
  id
  title
  function
  dimension_ids[]
  questions_to_answer[]
  required_claim_types[]
  evidence_requirements[]
  comparison_axes[]
  dependencies[]
  coverage_target
  length_budget
```

`SectionContract.function` 使用通用功能角色，例如直接回答、范围界定、分类展开、机制解释、证据比较、时间演化、适用边界、实施建议、争议与缺口；标题必须根据实际问题和研究维度生成。系统不得要求所有报告包含固定数量的章节，也不得把某个领域的工具、方法、机构或术语写入默认结构。

无论最终章节如何生成，完整报告必须满足以下功能要求：

- 开头直接回答用户问题并交代必要的范围和时间边界。
- 主体覆盖所有高重要性研究维度，并在适用时展开机制、证据、代表实现、比较、限制和成熟度。
- 对跨维度关系进行综合，说明互补、替代、依赖、冲突或演化关系，而不是只列清单。
- 仅在用户问题需要时生成选型、行动或实施建议，不强迫所有研究报告输出建议。
- 结尾披露证据边界、争议、未覆盖维度、来源状态和需要继续研究的问题。
- 参考文献与声明引用可回溯，Model 分析与外部事实在正文和置信度评价中保持可区分。

报告丰富度评价采用“维度覆盖、机制展开、证据密度、比较综合、案例或实现细节、边界条件、洞察增量和表达连贯性”，不得使用章节数量或字符数单独评分。

## P2：项目驱动论文雷达（核心协议/引擎已实现，退出标准待验证）

### P2.1 阶段目标与成功定义

P2 将论文发现从独立的画像工具升级为项目管理的一部分。项目目标、研究问题、当前里程碑、下一步行动、审计风险和证据缺口共同驱动论文搜索；论文筛选和全文分析结果再以可审查建议的形式回到项目，而不是停留在全局论文 inbox 或自动改写项目计划。

本阶段直接借鉴 AcademyHunter 的有效经验：人工设计的研究 Track、多条布尔查询、时间窗口、分层过滤、项目化分析结构和高信息密度日报。同时保留 Conflux 已有边界：LLM 负责语义判断，确定性规则只承担召回和门禁；深度结论必须基于摘要或全文证据；计划写入和知识晋升必须经用户确认。

P2 成功后，用户应能从一个已登记项目直接启动论文雷达，并回答以下问题：

- 当前项目为什么搜索这些论文，搜索意图来自哪个目标、里程碑、风险或研究问题。
- 每篇论文与哪个项目节点相关，能提供方法、数据集、基线、指标、背景、反例还是竞争信息。
- 哪些分析仅由摘要支持，哪些已经由全文章节、页码和 Chunk 支持。
- 论文是否建议加入项目资料库、关联里程碑、形成实验建议、登记风险或创建下一步行动。
- 哪些建议尚未确认，且项目 YAML、知识库和历史报告没有被自动改写。

### P2.2 优先级与范围边界

| 最高 | B. Track 化搜索扩面 | 使用人工可审查的 Track/QuerySpec 扩大 arXiv 和 Semantic Scholar 搜索面 | 与 A 并行 |
| 高 | C. 项目上下文与搜索意图 | 从计划、当前里程碑、下一步行动和审计风险生成有来源的 SearchIntent | A/B 稳定后 |
| 高 | D. 全文证据化项目影响分析 | 高价值论文先获取全文，再生成带来源定位的项目影响和行动建议 | P1 全文链路可复用 |
| 高 | E. Workbench 项目研究视图与审批 | 在项目页处理论文、覆盖缺口和写回建议 | A-D 的用户闭环 |

P2 明确不包含：

- 不把关键词或向量相似度直接包装成项目结论。
- 不要求模型填满摘要无法支持的方法、数据集、基线、结果或章节字段；证据不足时必须返回 `unknown` 或 `needs_full_text`。

### P2.5 搜索扩面与 QuerySpec

将当前从平铺关键词自动生成少量查询的方式升级为“人工 Track 为主、自动补充为辅”。每个 Track 至少包括：

```yaml
- id: runtime_reliability
  name: 智能体可靠性、审计与可复现性
  description: 错误分类、恢复、重规划、运行证据和实验复现
  related_rqs: [RQ2, RQ3]
  queries:
    - terms: "agent recovery OR replanning OR self-healing"
      suffix: "workflow OR execution"
      categories: [cs.AI, cs.SE]
    - terms: "audit trail OR provenance"
      suffix: "agent OR AI workflow"
      categories: [cs.AI, cs.SE, cs.DB]
```

`QuerySpec` 至少记录：`id`、`track_id`、`source`、`query`、`categories`、`date_window`、`max_results`、`priority`、`provenance`、`profile_version` 和 `project_context_version`。

来源优先顺序：

1. arXiv：近期预印本、分类和日期窗口，补齐 User-Agent、重试、指数退避、分页、查询级失败隔离和限速诊断。
2. Semantic Scholar：标题/摘要搜索、引用信息、相似论文和引用链；首期先稳定现有搜索，再开放图扩展。
3. OpenAlex：只有在 arXiv/Semantic Scholar 对期刊、会议或历史论文覆盖不足的标注集上证明有收益后加入。
4. Crossref：优先作为 DOI、出版物和期刊元数据补全源，不直接承担主要语义搜索。

搜索预算按用途分配，建议初始比例为：长期核心 Track 60%、当前里程碑和阻塞问题 30%、探索性/竞争情报 10%。比例是可配置起点，必须通过 M5 标注集评测调整，不写死为领域真理。

### P2.7 论文身份、项目关联和已见状态

论文元数据是全局实体，项目相关性是项目级实体。不得继续使用单一全局“已见”状态决定所有项目是否跳过某篇论文。

P2 文件模式先定义兼容协议，M3 再迁入 Repository：

```text
PaperIdentity
  source / canonical_id / version / doi / title_hash

ProjectPaperLink
  project_id / paper_identity
  status: discovered | shortlisted | rejected | saved | promoted | needs_review
  matched_intent_ids
  matched_track_ids
  matched_rq_ids
  matched_milestone_ids
  evidence_utility
  relevance / urgency / novelty / review_confidence
  profile_version / project_context_version / prompt_version / model_version
```

去重规则：

- DOI、来源 ID 和规范化标题用于硬身份合并；arXiv 基础 ID 与版本分别记录，不能把新版本永久当作已处理旧内容。
- 语义去重用于发现近似工作、扩展版和重复发布，不取代来源身份。
- 同一论文可以对项目 A 已拒绝、对项目 B 待精读；项目状态互不覆盖。
- 所有已处理候选均记录状态，避免低相关论文每天重复消耗 Embedding 和 LLM；项目上下文或评审版本变化时允许受控重评。
- 多条查询命中同一论文时合并全部 Track、意图和查询来源，不保留“先命中的唯一 Track”。

### P2.8 分层评分与全文分析

候选筛选采用多轴结果，不把所有判断压成一个不可解释的总分：

- `project_relevance`：与总体目标和研究问题的相关性。
- `milestone_relevance`：与当前阶段、下一步行动或阻塞问题的相关性。
- `evidence_utility`：method、dataset、baseline、metric、background、counterexample、competitor 或 none。
- `novelty`：相对项目已有论文和知识库的新增信息。
- `urgency`：是否直接影响当前里程碑或风险处置。
- `review_confidence`：模型对上述判断的置信度，不表示论文结论为真。

执行顺序：确定性负向门禁和身份去重 -> Embedding 粗排 -> 批量 LLM 语义评审 -> 边界候选深评。Embedding 应批量计算并缓存，避免去重和 L1 排序为同一候选重复请求。

高价值候选进入深度分析前必须先尝试获取全文。分析字段至少包括：问题、方法、实验、局限、项目对比、关联 RQ、关联里程碑、可复用资源、引用位置建议和后续行动建议；每个事实性字段必须附带 `evidence_scope`、`evidence_refs` 和 `confidence`。只有摘要时不得给出摘要未包含的具体模型、数据集、基线、数值结果或章节号。

- 将论文永久晋升到知识库。
- 修改项目 YAML、项目文档或历史报告。

写回失败时建议保留为 `proposed/needs_review`，不得因为 UI 或文件写入失败丢失论文证据和用户已做出的选择。

### P2.10 Workbench 项目研究视图

在项目详情增加 `Research` 页签，优先完成以下工作流：

- 从选中项目直接运行论文雷达，不再重复选择画像和项目路径。
- 显示本次搜索意图、来源、预算、命中数量、去重数量、已见跳过和失败查询。
- 显示“今日发现”“当前里程碑相关”“待全文分析”“已保存”“已拒绝”和“待审批建议”。
- 提供 RQ/里程碑 x method/dataset/baseline/metric/background/counterexample 覆盖矩阵。
- 论文行提供熟悉的命令操作：保存、忽略、精读、关联到项目节点、提出实验、加入知识库；不使用解释性大段帮助文本。
- 项目 Overview 显示研究缺口和待处理建议数量，但不把论文数量或模型评分包装成真实项目进展。

P2 退出标准：

- 已登记项目可以直接运行论文雷达，项目、画像、输出和状态关联明确。

## 8. M4：Evidence Ledger 与验证闭环

### 8.1 目标

将当前单次运行的 Evidence Graph 提升为可版本化、可追踪、可影响分析的证据账本。

### 8.2 数据实体

- `SourceSnapshot`：来源身份、内容哈希、抓取时间和版本。
- `EvidenceItem`：声明、引用区间、证据类型、限制和来源 Snapshot。
- `Claim`：报告或项目结论、状态、置信度和生成 Run。
- `EvidenceRelation`：支持、矛盾、派生、替代和影响关系。
- `Transformation`：检索、LLM 评审、仲裁、综合和修订的输入输出哈希。

模型置信度不等于事实真值；历史 Evidence 不被新运行覆盖，只产生新版本或关系。

### 8.3 验证和深化

- FactCheck 输出结构化问题列表。
- 有结构性问题时回到 Synthesizer 修订一次，再运行轻量核查。
- 超过 `max_verify_iterations` 或仍有关键未验证声明时进入 `needs_review`。
- Deep Research 只在证据覆盖不足、冲突、高风险或用户选择时触发。
- 子问题独立记录检索、LLM 评审、仲裁和证据，不拼成不可分辨的一次查询。

### 8.4 影响分析

来源变化时找到受影响的 Claim、Report、ProjectPlan 和 ProgressAudit，创建待确认复核 Run；不自动改写历史报告或项目计划。

### 8.5 验收标准

- 每个报告关键声明可定位到 Evidence ID、Source Snapshot 和生成步骤。
- 来源失效或替换后可以列出受影响声明和产物。
- 失败来源泄漏可被修订路径移除或降级，保留前后版本。
- 未验证、冲突和被替代状态可在报告和工作台区分。
- 离线冲突、来源失败、Prompt Injection 和证据变化夹具通过。

## 9. M5：LLM 评审评测与示例扩展

### 9.1 目标

验证 LLM 语义评审比旧确定性评分更适合研究场景，并验证 SDK 对不同扩展类型的支持。成功不以扩展数量衡量。

### 9.2 评测方法

- 建立小规模人工标注集：查询、候选论文/搜索结果、相关性、研究价值和证据质量。
- 在 P2 的项目级候选集中标注 SearchIntent 命中、里程碑/RQ 关联、证据用途、无依据分析和项目行动建议可接受性。
- 计算 `precision@k`、`recall@k`、`NDCG@k`、边界候选一致性和理由完整性。
- 计算搜索面增益、稳定拒绝项重复处理率、跨项目状态隔离正确率、全文分析证据覆盖率和无依据字段率。
- 对比旧确定性评分、LLM 批量评审、LLM 深评和混合策略。
- 记录模型、Prompt、画像、候选哈希、缓存、Token、延迟和成本。
- 对工作流、插件和模型做最小消融矩阵。

### 9.3 示例扩展选择

在 M1/M2 协议稳定后另行选定，至少覆盖一个数据源扩展和一个工作流或评测扩展。选择依据是真实使用价值、数据合法可得性、维护成本、协议边界覆盖和不增加领域核心分支。当前不固定具体名单。

### 9.4 验收标准

- LLM 评审结构化输出成功率 100%；失败样本必须为 `unreviewed`。
- 人工标注集上主要指标相对 M0 不下降；下降时必须记录适用场景和调整方案。
- 高价值、无关和边界样本都有可解释输出。
- 相对 P2 基线扩大搜索面后，目标 Track 的召回有可测提升，且无依据分析率不升高。
- 至少两个互补扩展通过 SDK 契约测试，其中至少一个不是纯数据源连接器。
- 默认使用离线 FakeModel 或录制响应；真实 API 评测必须显式开启。
- 评测同时报告质量、成本和延迟，不以报告长度或 Agent 数量判定成功。

## 10. M6：条件触发的服务化

### 10.1 启动条件

只有出现以下任一真实需求才评估：两个以上独立工作区并发、SQLite 队列成为可观测瓶颈、需要跨机器访问/远程 Worker/集中备份，或可信进程内插件无法满足实际隔离要求。

### 10.2 实现方法

- Postgres 替换 Run/Approval/Repository，保留迁移和 Repository 接口。
- 本地对象目录替换 S3 兼容存储，ArtifactRef 语义不变。
- Worker 使用持久队列、租约、幂等键和心跳。
- 第三方插件使用子进程或远程运行时，声明网络、文件和 Secret 权限。
- 增加工作区级访问控制和审计，不把多租户权限提前下放到本地模式。

### 10.3 验收标准

- 同一 WorkflowDefinition 和插件在本地与 Worker 模式产生兼容 StepResult。
- Worker 崩溃或网络重试不会重复提交有副作用操作。
- 工作区之间不能读取对方 Run、Artifact、Evidence 或 Secret。
- 服务化失败时可以导出工作区并恢复到单机模式。

## 12. 问题发现、回滚与复盘

### 12.1 问题分类

- 正确性：证据、引用、状态或结果错误。
- 边界：职责泄漏、插件依赖私有状态或数据双写。
- 性能：LLM、索引、队列或 UI 超出基线。
- 安全：Secret、路径、不可信内容或副作用失控。
- 体验：配置、调试、审批或开发复杂度明显上升。

### 12.2 处理流程

1. 用最小夹具复现并记录影响。
2. 判断是当前阶段修复还是架构决策变化。
3. 优先修复正确性和安全问题，必要时暂停新增功能。
4. 用最小改动修正，补充一条防回归测试或评测样本。
5. 更新验收、兼容说明和本文档偏差记录。
6. 连续两次修复都需要扩大核心边界时暂停并重新审查抽象。

### 12.3 回滚原则

- 协议变化通过版本号和适配器过渡，兼容层必须有删除版本。
- 存储迁移采用备份、事务和单向导入，保留原始文件。
- 新工作流先用显式开关启用，稳定一个版本后再考虑默认路径。
- 自动写入失败保留待审批状态，不因回滚丢失用户决策或证据。
