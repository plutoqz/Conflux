## 0. 文档职责与结论

本文档定义论文雷达（Paper Radar）检索扩池的目标、分层检索协议、数据协议改动、执行层改造、持久化游标、已入库排除、评测方案、迁移策略与分阶段验收。它解决三个已确认问题：

1. **强相关论文漏检**：`strong_recall@20` 中位数 0.25–0.5，波动大（0.5/0.75/0.25）。Cap 网格实验显示 cap80 可把 strong_recall@20 提到 0.75，证明瓶颈在候选池宽度而非评审精度。
2. **覆盖不足**：arXiv 仅按 `submittedDate` 降序取最近提交且不分页；S2 已支持的 `year`/`offset`/`citationCount` 参数全部闲置；LLM 查询变体生成是 no-op stub。经典/里程碑论文永远无法进入候选池。
3. **重复检索与重复入库**：非最新论文（milestone/classic）每次运行都重检索；跨画像已入库论文未排除，同一论文被多个画像反复检索入库。

核心结论：**先扩池（粗排 top-100），再用免费信号压回固定 LLM 精排预算（top-40），把"池子宽度 ×2.5"与"成本不变"同时实现**。扩池与降采样是一个迭代的两半，必须一起做，否则成本翻倍且无收益（cap100 单次质量最高但成本 ×2.4 的教训）。同时用 `retrieval_cursors` 让低频层只按需检索、用全局 `papers` 表排除已入库论文。

## 1. 问题定义与证据基线

### 1.1 已确认事实（代码级）

1. `arxiv_source.search_arxiv()`（`arxiv_source.py:111-137`）：固定 `sortBy=submittedDate`、`start=0`、无分页；经典论文永远不可达。**arXiv API `sortBy` 仅支持 `relevance`/`lastUpdatedDate`/`submittedDate`，无 citationCount**。
2. `semantic_scholar_source.search_semantic_scholar()`（`semantic_scholar_source.py:39-111`）：已支持 `year_from/year_to`、`offset` 分页、`fieldsOfStudy`，返回 `citationCount`；但 `radar._execute_queries()`（`radar.py:342-352`）只传 `query + max_results`，其余能力全部闲置。
3. `query_builder.resolve_query_specs()`（`query_builder.py:37-83`）：每个 TrackQuery 展开为 1 个 QuerySpec，`max_results ≤ 50`，单窗口。
4. `intent_generator._enrich_with_llm()`（`intent_generator.py:165-173`）：**no-op stub**，无查询变体、同义词、子主题展开。
5. `TrackQuery.date_window_days` 默认 365（`p2_contracts.py:70`），是唯一时间维度，且对 arXiv 无效（arXiv 不分页也拿不到窗口外结果）。
6. **全局 `papers` 表已存在**（`sqlite_store.py:142-154`）：`paper_key` 主键、`UNIQUE(source, canonical_id)`、含 `doi`/`title_hash`/`metadata_json`——天然是"跨画像已入库论文登记表"，可直接复用为检索排除表，无需新表。
7. `seen_state`（P2 项目级稳定拒绝）只覆盖"本项目已拒绝"，不覆盖"其他画像已入库"与"低频层已检索过"。

### 1.2 评测证据

| 配置 | strong_recall@20 median | 成本 | 结论 |
|---|---|---|---|
| pointwise cap40（现状默认） | 0.3256–0.5 | 40 调用 / 41–48k tokens | 基线 |
| listwise cap60 | 0.3256 | 8 调用 / 42k tokens | 解析失败 1-2 批/轮，质量降 |
| **cap80 listwise** | **0.75** | 更高 | **扩池有效，但当时未降采样，成本无约束** |
| cap100 pointwise 单次 | 质量最高 | ×2.4 | 成本不可接受 |
| 无 LLM 粗排（KG 高密度池） | 0.3488 | 0 tokens | LLM 评审在稀疏 GIS 池有收益，高密度池无收益 |

结论：候选池宽度是 strong_recall 的主要瓶颈；成本约束靠降采样而非缩小池子。

## 2. 目标与非目标

### 2.1 目标

1. 论文雷达覆盖"近 1 年前沿 / 近 3 年热门 / 近 10 年里程碑 / 近 20 年经典"四个时间层。
2. 每 Track 检索预算有界（去重后总候选 ≤ 400），成本不因扩池失控。
3. LLM 精排调用数保持现状（`semantic_review_limit=40`），靠降采样把 top-100 压回 40。
4. 低频层（milestone/classic）由 `retrieval_cursors` 控制轮询频率，经典论文不全量重检索。
5. 跨画像已入库论文在检索去重阶段被排除（复用全局 `papers` 表）。
6. 引用种子（已入库/已确认论文的引用图 1-2 跳）纳入首轮，覆盖"无查询词可达"的领域骨架论文。
7. 离线评测可复现：P2 75 篇 + KG 136 篇标注集上 strong_recall@20 中位数 ≥ 0.75，且三次运行波动 < 0.15。
8. 与标注集同口径：`build_p2_label_candidates.py` 与运行候选使用同一分层检索协议（吸取"标注候选与运行候选检索口径不一致"的历史教训）。

### 2.2 非目标

- 不改 LLM 评审 prompt 语义（引用信号注入属问题 1 的第二条路径，不在本计划首轮）。
- 不新增外部数据源（OpenAlex/Crossref 已存在于 Web 层，论文雷达首轮只用 arXiv + S2）。
- 不引入新调度框架（复用 M3 JobQueue 周期任务）。
- LLM 查询变体生成（同义词/子主题/方法名/数据集名）列为第三阶段，首轮只做确定性术语展开（0 成本）。

## 3. 核心设计：分层检索协议

### 3.1 覆盖分层定义（arXiv 能力边界已确认）

| tier | 窗口 | arXiv | S2 | 排序 | 轮询频率 | 候选用途 |
|---|---|---|---|---|---|---|
| `frontier` | 近 1 年 | ✅ `submittedDate` 降序 | ✅ 当年 | 时间 | 每次运行 | 前沿追踪 |
| `hot` | 近 3 年 | ✅ `relevance` | ✅ `year`+relevance | 相关性 | 每次运行 | 热门细分方向 |
| `milestone` | 近 10 年 | ❌ 无 citationCount | ✅ `year`+citationCount | 被引降序 | 低频（默认 30 天） | 里程碑论文 |
| `classic` | 近 20 年 | ❌ 无 citationCount | ✅ `year`+citationCount+venue | 被引降序 | 低频（默认 30 天） | 经典论文 |

- **arXiv 排序边界**：`sortBy` 支持 `relevance`/`lastUpdatedDate`/`submittedDate`，无 citationCount → frontier/hot 可用 arXiv，milestone/classic 仅 S2。
- hot 层 arXiv relevance + S2 relevance 双跑（arXiv relevance 是关键词相关，质量一般但扩池可用；双源互补后去重）。
- **tier 配额**（每 Track 内，按总候选预算分配，可调）：

| tier | 配额占比 |
|---|---|
| frontier | 30% |
| hot | 40% |
| milestone | 20% |
| classic | 10% |

示例：`max_candidates=100` 的 Track，frontier 30 / hot 40 / milestone 20 / classic 10。

### 3.2 数据协议改动（`src/conflux/core/p2_contracts.py`）

**`QuerySpec` 新增字段（全部带默认值，向后兼容）**：

```python
class QuerySpec(BaseModel):

```

**`TrackQuery` 新增字段**：

```python
class TrackQuery(BaseModel):
```

**`ProjectResearchConfig` 新增（可选，全局默认）**：

**协议版本**：`P2_PROTOCOL_VERSION` 升级为 `conflux.dev/p2/v1alpha2`；旧 run JSON 缺新字段时 Pydantic 默认值兜底，`evaluate_p2_run` 兼容读取。

### 3.3 持久化游标：`retrieval_cursors` 表（migration `0006`）

问题 2 的落点：记录"该画像的某 track 的某 tier 最后检索到哪个窗口"，低频层（milestone/classic）据此跳过未到期重检索。

```sql
CREATE TABLE IF NOT EXISTS retrieval_cursors (
    profile_id TEXT NOT NULL,
    track_id TEXT NOT NULL,
    tier TEXT NOT NULL,            -- frontier | hot | milestone | classic
    last_retrieved_at REAL NOT NULL,   -- epoch seconds
    last_run_id TEXT NOT NULL DEFAULT '',
    last_year_from INTEGER,
    last_year_to INTEGER,
    candidate_count INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (profile_id, track_id, tier)
);
```

语义：

- `tier_refresh_days[tier] == 0`（frontier/hot）→ 每次运行都检索。
- `tier_refresh_days[tier] > 0`（milestone/classic 默认 30）→ 距 `last_retrieved_at` 不足 N 天则跳过该 tier，直接复用上次结果（保存在 `RadarRunResult` 或从 run 历史读取）。
- 经典层**首次**触发时全量（近 20 年 citationCount 降序），之后每 30 天重检索一次，天然解决"经典论文不需要次次参与检索"。
- 同一 profile 的多个项目共享同一 `retrieval_cursors`（profile_id 维度，因为同一画像不同项目检索同一批论文）；`track_id` 维度细分。
- 迁移：`SCHEMA_MIGRATIONS` 追加 `0006_retrieval_cursors`；旧库升级 `conflux migrate` 幂等执行；不触发任何旧数据改写。

### 3.4 分层窗口展开器（新文件 `src/conflux/paper_radar/tier_expander.py`）

`resolve_query_specs` 的每 1 个 TrackQuery 按 tiers 展开为最多 4 个 QuerySpec（tier 从 `track.tiers` 或 `config.coverage_tiers` 解析）：

```python
TIER_WINDOW = {
    "frontier":  (1,  "submittedDate"),
    "hot":       (3,  "relevance"),
    "milestone": (10, "citationCount"),
    "classic":   (20, "citationCount"),
}
ARXIV_CAPABLE_TIERS = {"frontier", "hot"}   # arXiv 无 citationCount

def expand_tier_specs(base: TrackQuery, track: Track, config: ProjectResearchConfig) -> list[QuerySpec]:
    # 每个 tier 生成 QuerySpec：
    #   year_from/year_to 按 TIER_WINDOW
    #   sort_by 按 TIER_WINDOW
    #   max_results = track_budget * tier_quota // query_count // source_count
    #   classic: venue_filters = profile.target_venues[:5], citationCount >= config.classic_min_citations
    #   milestone/classic: 仅 S2（不生成 arXiv spec）
```

- 对 arXiv：`frontier` 用 `submittedDate` 降序；`hot` 用 `relevance`；milestone/classic 不生成 arXiv spec。
- 对 S2：全部四层都请求，`year_from/year_to`、`offset` 分页（`per_page` 最多 100，翻 1-2 页）。

### 3.5 执行层改造

**`arxiv_source.search_arxiv()`**：新增 `sort_by: str = "submittedDate"` 透传（`urlencode` 中 `sortBy` 取传入值）：

```python
params = {
    "search_query": search_query,
    "start": max(0, start),
    "max_results": max_results,
    "sortBy": sort_by,          # "submittedDate" | "relevance"
    "sortOrder": "descending",
}
```

**`semantic_scholar_source.search_semantic_scholar()`**：参数已齐备（`year_from/year_to/offset`），新增 `sort: str = "relevance"` 透传；`citationCount:desc` 需真实验证 S2 graph API 是否支持 `sort` 参数——**不支持则降级为**：`offset` 翻 2 页（top-100）后客户端按 `citationCount` 稳定排序（relevance 排序本身已倾向高被引，客户端排序兜底足够）。

**`radar._execute_queries()`**：将完整 QuerySpec 传入（不再只传 query+max_results）：

```python
if spec.source == PaperSource.ARXIV:
    papers = search_arxiv(
        spec.query, max_results=spec.max_results,
        categories=spec.categories,
        sort_by="submittedDate" if spec.coverage_tier == "frontier" else "relevance",
        start=spec.offset,
    )
elif spec.source == PaperSource.SEMANTIC_SCHOLAR:
    papers = search_semantic_scholar(
        spec.query, max_results=spec.max_results,
        offset=spec.offset,
        year_from=spec.year_from, year_to=spec.year_to,
        fields_of_study=["Computer Science"],
        sort=spec.sort_by,
    )
```

### 3.6 预算与去重（含已入库排除）

- 每 Track 总候选预算：`int(config.max_candidates * track.budget_ratio)`；四层按 §3.1 配额细分。
- `_deduplicate_papers()` 扩展：
  - 新增 `arxiv_id ↔ S2 paperId` 跨源去重（`PaperIdentity` 已有 `title_hash`/`doi`；S2 返回的 `externalIds.ArXiv` 直接提供 arxiv_id 映射）。
  - **已入库排除（问题 3）**：检索去重后，用 `papers` 表全部 `paper_key`（加载为内存 set，量级 ≤ 数千，无性能问题）过滤掉已入库论文；`skip_ingested` 关闭时跳过该过滤（如主动复查场景）。
  - **已检索未入库排除**：仍走现有 `seen_state`（本项目已拒绝论文），两套机制互补：`papers` = 全局已入库；`seen_state` = 本项目已拒绝。
- 去重后总池上界 400（`max_candidates` 上限 500 内），超限按 `provenance` 优先级裁剪（frontier 优先保留）。

### 3.7 粗排扩池 + 降采样（与问题 1 联动，本计划一并落地）

`radar.py` Step 4-5 改造：

1. 粗排从 `top-40` 改为 `top-100`（`embedding_coarse_rank` 已按全池排序，只改截断点）。
2. 降采样信号（免费，`coarse_rank.py` 返回 detail 中已有 dense/lexical，新增两列）：
   - `citation_boost`：`citationCount` 分档（0/1-10/11-50/51-200/200+ → 0/0.1/0.2/0.35/0.5）
   - `venue_boost`：命中 `profile.target_venues` +0.15
   - `final = 0.7*dense + 0.3*lexical + 0.25*citation_boost + 0.15*venue_boost`
3. 降采样后取 top-40 进 LLM 精排（`semantic_review_limit` 不变）。
4. 精排分数覆盖粗排分；未进精排的 top-40 之后论文保留粗排分但**不参与 shortlist 判定**（保持与现状"只信任 LLM 排序"一致的语义）。

### 3.8 引用种子扩展（用户确认纳入首轮，问题 2 的核心补充）

覆盖"无查询词可达"的领域骨架论文：经典论文常不在关键词检索的 top-100 里，但会出现在高相关论文的引用/被引列表中。

- **种子来源**：
  1. 全局 `papers` 表已入库论文（跨画像复用，天然去重）。
  2. 本项目已确认相关论文（P2 labels R2+ 的 canonical id / paper_key）。
  3. 用户手动钉住的论文（`seen_state` 之外新增可选 `seed_override` 列表，项目 YAML 配）。
- **扩展**：S2 `paper/{id}/references` + `citations` API，每种子各取前 `citation_seed_per_paper`（默认 20），深度 `citation_seed_hop`（默认 2）。
- **预算**：本轮引用种子 API 请求 ≤ `citation_seed_budget`（默认 100）。rate limit 1 req/s 下 100 请求 ≈ 100 秒，作为周期 Job 可接受；超出部分记入 `citation_seed_truncated` 并在结果中可见。
- **排除**：`papers` 表已入库论文 + `seen_state` 已拒绝论文 + 已在本轮候选池的论文。
- **接入**：作为 `provenance="citation_seed"` 的 PaperRecord 直接并入粗排池（不新增调度器）；与 `seen_state` 复用（已拒绝论文不重复扩展）。
- **触发条件**：`citation_seed_enabled=True` 且存在 ≥1 个种子（无种子时跳过并记录 `no_citation_seeds`）；经典/milestone 层被游标跳过时，引用种子仍可运行（它是增量补充而非替代）。

## 4. 查询变体生成（首轮含一个最小实现）

`intent_generator._enrich_with_llm` 从 no-op 改为真实实现，但**首轮只做确定性展开**，不做 LLM 调用（控制范围）：

- 术语变体表（内置小词典，可扩展）：`GNN → graph neural network | geometric deep learning`、`RAG → retrieval-augmented generation`、`GeoKG → geospatial knowledge graph` 等。
- 每个 TrackQuery.terms 展开为 `[原词, 变体1, 变体2]`（OR 拼接，不增加请求数：`(原词 OR 变体1 OR 变体2)`）。
- LLM 变体生成（同义词/子主题/方法名/数据集名）列为第三阶段，待离线评测确认确定性展开收益后再决定是否值得模型成本。

## 5. 评测方案

### 5.1 离线确定性评测（不调用 LLM，复用现有资产）

1. **候选池重建**：用新分层协议 + 冻结标注集的同一检索口径重新生成候选快照（改造 `scripts/build_p2_label_candidates.py` 使其调用 `tier_expander` + `_execute_queries`）。

3. **LLM 精排评测**：top-40 精排 + `eval_p2_radar.py --merge` 3 次中位数，与现有 `merge_pp_cap40_3runs_final.json` 基线直接对比。

## 9. 风险与控制

| 风险 | 控制 |
|---|---|
| S2 rate limit（1 req/s）使多窗口检索变慢（40-80 请求/轮 + 引用种子 ≤ 100） | frontier 全走 arXiv；milestone/classic 只在 S2；`citation_seed_budget` 硬上限；周期 Job 允许 2-4 分钟 |
| S2 不支持 `sort=citationCount` | 客户端排序降级：offset 翻 2 页取 top-100 后按 citationCount 稳定排序 |
| classic 层检索结果与画像相关度低 | venue_filters 按 target_venues 约束 + `classic_min_citations` 下界 + 负关键词过滤复用 |
| 扩池引入噪声拉低 precision | 降采样信号把高被引/权威 venue 前置；LLM 精排仍是最终裁决者 |
| 引用种子扩展跑偏（领域外引用） | 种子限定已入库/已确认论文；扩展结果仍过 embedding 粗排 + LLM 精排；预算上限截断 |
| 标注集与运行候选口径再次漂移 | `build_p2_label_candidates.py` 与 `_execute_queries` 共用同一 `tier_expander`（单一口径函数） |
| 评测集是 AI 代审标签 | 指标按"相对提升 + 波动收敛"解读，不宣称绝对质量；P2 人工抽查另行安排 |
| 粗排 top-40 之后论文不再 shortlist | 文档明确：未精排论文保留为 `discovered`，进入下轮 seen 状态；避免"粗排分当 LLM 分"的旧问题 |
| 游标导致低频层论文长期不刷新 | `tier_refresh_days` 可配；手动触发 `refresh=true` 强制重检索；`retrieval_cursors` 记录 `last_retrieved_at` 可视化 |

## 10. 与问题 1/3 的关系

- 本计划的 P2.6.3 已包含问题 1 的第一条路径（扩池 + 免费信号降采样）。问题 1 的其余路径（引用信号注入评审 prompt、边界候选多次采样、动态锚定 few-shot）依赖本计划扩池后的候选池，作为 P2.7 后续迭代，不混入本计划首轮。
- 扩池后 LLM 精排的 `semantic_review_limit` 保持 40，成本不变，这是本计划与"cap100 直接全评审"的本质区别。
- 引用种子（P2.6.3b）同时服务问题 2（覆盖经典/骨架论文）与问题 1（把"无查询词可达"的强相关论文送进候选池），是两问题的共享前置。
