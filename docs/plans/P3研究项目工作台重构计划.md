## 0. 文档职责与结论

本文档定义 P3“研究项目工作台”的问题、目标、用户流程、信息架构、技术架构、数据协议、性能指标、实施阶段和验收方法。它是详细设计与实施候选，不单独承担当前完成状态；P3 是否启动、推进到哪个阶段以及实际验收结果，统一记录在 `执行计划v1.md`。

P3 的核心结论是：当前问题不能通过重新排列页面卡片解决。必须建立一个持久、版本化、可追溯的项目状态层，把项目配置、机器观察和模型推断分开，再让计划、论文、知识库、研究查询、实验、Git 和 Evidence Ledger 围绕同一项目上下文工作。

目标形态不是通用项目管理软件，而是面向研究者的本地 ResearchOps 工作台：

```text
研究问题 / 假设 / 里程碑
          |
          v
代码、实验、论文、查询、知识库、证据变化
          |
          v
版本化项目状态 -> 状态判断 -> 待处理复核 -> 下一步研究行动
```

## 1. 问题定义与证据基线

### 1.1 已确认事实

当前实现具备项目 YAML 注册、Git 状态、文档/产物/报告统计、进度审计、计划分析、论文雷达和证据变化复核，但这些能力分别由不同入口采集、缓存和解释。

当前结构存在以下事实：

1. `build_projects_overview()` 在页面请求期间调用 `monitor_project()`；计划分析又独立调用一次项目监控和证据目录构建。
2. 项目总览缓存、进度审计快照、计划分析缓存、论文雷达状态和 Evidence Ledger 分属不同存储与响应结构，没有统一的项目状态版本。
3. 项目文档发现主要依赖用户配置、约定文件名和 Markdown 文档；未形成持久文档索引、类型校正、增量解析和项目理解快照。
4. 项目总览刷新模式仍为 manual；论文雷达已有持久 Job 和周期调度，但项目状态采集没有统一后台任务。
5. 分支功能只读取当前分支、HEAD、工作区和 ahead/behind，不管理分支与研究工作之间的关系。
6. 计划分析曾将 4 份文档、98,617 字符发送给模型，真实运行耗时 138.19 秒；这类深分析不能成为打开项目页的前置条件。
7. 页面把计划、研究雷达、证据文件、最近审计和配置作为并列模块展示，信息结构反映后端能力，而不是研究者的决策顺序。

### 1.2 用户反馈

用户真实体验暴露出：

- 页面信息杂乱，重点不明确。
- 项目状态刷新和分析处理慢。
- 配置项多且含义不清晰。
- 不能在登记项目后自动搜寻文档并建立对项目现状的理解。
- 项目监控与论文、RAG、研究查询、实验和证据复核之间缺少可见联动。

### 1.3 根因判断

优先级最高的三个根因是：

1. **缺少权威项目状态模型**：多个功能各自读取文件和生成摘要，导致重复工作、状态漂移和界面拼接。
2. **交互围绕功能模块而非研究任务**：用户需要判断当前重点、证据缺口、阻塞和下一步，现有页面首先展示的是技术状态与数量。
3. **同步采集与深度分析未分层**：便宜的本地观察、较慢的测试/远程检查和昂贵的 LLM 分析没有严格异步化和增量化。

### 1.4 待验证假设

以下判断需要在 P3.0 用户任务基线中验证：

- 研究者更适合以 Research Workstream，而不是通用 Task/Kanban 作为主要管理单元。
- 自动发现文档后，用户只需确认少数权威来源，而不需要手工配置文档目录和文件列表。
- 统一复核队列能够减少计划分析、论文候选、证据变化和失败任务在多个页面之间切换的成本。
- 从物化快照读取项目页，可以在不牺牲状态真实性的情况下把首屏延迟稳定控制在 500 ms 以内。

## 2. 目标用户与研究任务

### 2.1 目标用户

- 持续阅读论文、维护代码、运行实验和编写报告的研究生。
- 同时维护研究问题、知识库和工程原型的个人研究者。
- 需要向导师或合作者解释“做了什么、证据是什么、下一步是什么”的技术研究者。

### 2.2 核心痛点

研究者通常不是缺少文件，而是缺少以下判断：

1. 当前最重要的研究问题是什么？
2. 哪些结论已经有证据，哪些只是分析或假设？
3. 本周期产生了哪些可验证进展，而不是只有活动痕迹？
4. 哪些实验、查询或论文真正改变了项目判断？
5. 哪些证据已经过期、冲突或需要复核？
6. 下一步应该读论文、补实验、修代码、重建索引还是重新查询？
7. 当前任务消耗了多少时间、模型调用和预算？

### 2.3 核心用户任务

P3 必须优先支持以下任务，而不是追求页面功能数量：

| 编号 | 用户任务 | 成功结果 |
|---|---|---|
| U1 | 添加一个已有项目 | 不手工配置文档即可得到可审查的项目理解 |
| U2 | 每日查看项目 | 15 秒内识别当前重点、阻塞和下一步 |
| U3 | 判断真实进展 | 每项进展都能回到提交、测试、实验或报告 |
| U4 | 处理研究缺口 | 可直接触发论文雷达、研究查询、RAG 检查或实验行动 |
| U5 | 审查状态变化 | 在一个队列中处理计划漂移、证据变化、失败任务和新论文 |
| U6 | 汇报研究周期 | 从已确认状态生成带证据的周期摘要，而不是重新拼装文件 |

## 3. 目标与非目标

### 3.1 产品目标

1. 用户只提供项目路径，也能得到自动发现、可审查的项目概览。
2. 首屏集中呈现当前重点、真实进展、阻塞、证据缺口和下一步。
3. 项目状态来自版本化事实快照，模型只提出推断，不直接改写权威状态。
4. 论文、知识库、研究查询、实验、计划和 Evidence Ledger 通过稳定实体关系联动。
5. 所有慢操作进入持久后台任务，页面加载不等待远程请求、测试或模型。
6. 用户能够理解每个配置项的影响，并在大多数项目中不需要高级配置。

### 3.2 工程目标

1. 建立一个 SQLite 权威项目状态层，不继续扩展 JSON 缓存之间的隐式同步。
2. 采用增量文档索引和事件驱动刷新，避免重复扫描整个目录。
3. 将采集、状态归纳、模型推断、人工审批和展示拆成独立阶段。
4. 保留现有 `ProjectRegistry`、`JobQueue`、Evidence Ledger、SearchRun 和 Artifact 能力，通过迁移和适配器复用。
5. 新 API 返回稳定、版本化协议，Workbench 不直接组装多个底层模块响应。

### 3.3 非目标

- 不建设 Jira、Notion 或通用 Kanban 替代品。
- 不自动提交、切换、合并或推送 Git 分支。
- 不允许模型未经确认修改项目目标、里程碑、知识库或文件。
- 不在页面加载时扫描整个仓库、运行测试或调用模型。
- 不为了“自动理解”把整个代码仓库持续发送给模型。
- 不在 P3 引入 Postgres、Redis、微服务或新的远程 Worker。
- 不把提交数、文件数、论文数直接解释为研究进展。

## 4. 设计原则

### 4.1 三类状态严格分离

```text
Declared State：用户确认的目标、状态、计划和决策
Observed State：Git、文件、测试、运行、产物和来源变化事实
Inferred State：模型或规则提出的状态解释、风险和行动建议
```

界面不得把 `inferred=completed` 显示为“已完成”。推荐显示：

```text
人工计划：已完成
观察证据：测试失败，2 个验收条件缺少产物
系统建议：needs_review
```

### 4.2 证据先于状态

- `completed`、`blocked`、`risk` 和“真实进展”必须携带证据引用。
- 文件存在只表示可定位，不自动表示完成。
- 模型解释必须记录模型、Prompt、输入快照和来源引用。
- 过期快照必须显式显示数据时间和陈旧原因。

### 4.3 快路径与深路径分离

- 快路径：读取物化快照、当前任务和待处理数量。
- 中路径：增量文件/Git 采集、局部状态重算。
- 深路径：测试、远程检查、项目理解、计划分析和跨证据影响判断。
- 深路径永远异步执行，并允许取消、重试、恢复和查看部分结果。

### 4.4 渐进披露

首屏只回答当前判断和行动；文件列表、原始 Git 输出、模型 usage、文档分类理由和配置细节按需展开。

### 4.5 自动发现不等于自动确权

系统可以发现并分类文档，但不能静默认定某份文档是权威计划。权威文档必须由用户确认，或来自已明确登记的项目纲领。

## 5. 核心领域模型

### 5.1 ProjectDefinition

继续由 `projects/*.yaml` 管理用户声明和少量可移植配置：

- 项目标识、名称和本地路径。
- 项目类型：`code_research | literature_research | mixed`。
- 已确认项目纲领和权威计划文档。
- 测试命令和明确的扫描排除项。
- 自动化级别与预算上限。
- 研究画像引用。

不再要求用户预先填写文档目录、报告目录和结果目录才能使用；这些字段迁移为可选覆盖项。

### 5.2 ProjectDocument

```text
document_id
project_id
path
content_hash
kind                 charter/plan/decision/experiment/report/paper_note/code_doc/other
authority            candidate/confirmed/excluded
parse_status          pending/ready/partial/failed/unsupported
language
title
modified_at
indexed_at
extractor_version
classification_source rule/model/user
classification_confidence
metadata_json
```

文档正文不重复存入普通项目表；文本进入受控对象存储或现有 Artifact 存储，SQLite 保存身份、哈希、状态和定位信息。

### 5.3 ResearchWorkItem

统一承载研究工作的最小对象：

```text
work_item_id
project_id
kind                 research_question/hypothesis/milestone/experiment/decision/action
title
parent_id
declared_status      planned/in_progress/completed/blocked
observed_status      no_evidence/active/verified/failed/stale
inferred_status      planned/in_progress/completed/blocked/needs_review
acceptance_criteria
source_refs
evidence_refs
linked_branch
linked_run_ids
linked_paper_keys
updated_at
```

`declared_status` 只能由用户确认写入；`observed_status` 由确定性采集器计算；`inferred_status` 由有界规则或模型建议产生。

### 5.4 ProjectContextSnapshot

项目状态使用不可变、可比较的版本化快照：

```text
snapshot_id
project_id
revision
created_at
trigger              initial/file_change/git_change/manual/job_complete/scheduled
definition_version
document_index_version
git_state
work_items
knowledge_state
research_state
run_state
evidence_state
health
summary
```

`summary` 只能引用快照内的规范对象，不保存无法追溯的自由文本结论。

### 5.5 ProjectEvent

所有变化先标准化为事件：

- `document.discovered`
- `document.changed`
- `git.head_changed`
- `git.worktree_changed`
- `test.completed`
- `artifact.created`
- `research_query.completed`
- `paper_radar.completed`
- `paper.saved`
- `knowledge.index_changed`
- `evidence.source_changed`
- `work_item.confirmed`
- `review.resolved`

事件使用现有 EventStore 思路追加保存，状态构建器消费事件生成新快照。重复事件必须幂等。

### 5.6 ReviewItem

统一复核队列替代各页面独立的确认区域：

```text
review_id
project_id
kind                 plan_drift/evidence_change/new_paper/run_failure/index_stale/
                     document_authority/status_suggestion/branch_divergence
priority
status               pending/confirmed/dismissed/superseded
summary
impact_refs
evidence_refs
proposed_action
input_snapshot_id
created_at
resolved_at
```

优先级由影响范围、不确定性、时效性和用户当前工作流共同决定，不由模型单独给出。

## 6. 目标用户流程

### 6.1 添加项目

```text
选择本地目录
  -> 立即创建项目和空快照
  -> 后台执行快速目录/Git 发现
  -> 首屏先显示“正在理解项目”及已发现事实
  -> 后台解析和分类文档
  -> 生成项目理解候选
  -> 用户确认纲领、计划和排除项
  -> 建立第一个可审计项目基线
```

首次表单只包含：

1. 项目路径。
2. 项目类型，默认自动判断并允许修改。
3. 可选测试命令。

模型、目录、索引和论文源不作为首次使用阻断项。

### 6.2 每日查看

用户打开项目后，首屏从最近物化快照读取：

- 当前重点 Research Workstream。
- 待处理复核。
- 新进展和阻塞。
- 正在运行或失败的任务。
- 最近证据变化。
- 最优先下一步。

如果快照过期，页面显示旧状态和更新时间，同时后台刷新；不能用空白加载页替代已有状态。

### 6.3 周期审计

```text
选定上一个已确认基线
  -> 比较提交、测试、实验、报告、查询和论文状态
  -> 生成真实进展候选、弱信号和风险
  -> 关联人工计划和验收条件
  -> 用户确认需要写入的进展与计划调整
  -> 生成周期摘要和新基线
```

周期摘要只能使用已确认状态和证据；模型建议单独列入“待确认”，不能混入正式进展。

### 6.4 研究缺口处理

当工作项缺少证据时，用户可以从同一位置选择：

- 在项目知识库中检索。
- 运行研究查询。
- 创建论文雷达 SearchIntent。
- 建立实验行动。
- 标记为当前无法验证。

触发动作自动携带 `project_id`、`work_item_id`、问题文本、已有证据和预算，不要求用户重新配置上下文。

### 6.5 证据变化处理

```text
来源内容变化
  -> Evidence Ledger 产生影响集合
  -> 映射受影响 claim/report/work item
  -> 生成统一 ReviewItem
  -> 用户查看新旧来源和影响范围
  -> 确认、驳回或触发重新查询/重建
```

## 7. 信息架构与界面方案

### 7.1 顶层结构

项目页只保留四个主视图和一个跨视图复核入口：

1. **概览**：当前重点、进展、阻塞、下一步、运行状态。
2. **研究工作**：研究问题、假设、里程碑、实验和决策。
3. **证据与知识**：claims、来源、论文、RAG 覆盖和证据变化。
4. **活动与运行**：任务、查询、测试、索引、成本、耗时和失败。
5. **待处理**：跨功能 Review Inbox，固定入口显示数量和最高优先级。

配置不再作为主视图；通过项目标题旁的设置入口进入。

### 7.2 概览页

首屏结构按决策顺序排列：

```text
项目标题 / 当前状态 / 数据更新时间 / 刷新状态

当前重点
  研究问题、当前阶段、最近证据、下一步操作

需要处理
  阻塞、证据变化、失败任务、计划漂移

最近验证进展
  最多 5 项，每项显示证据类型和时间

运行中
  查询、论文雷达、索引、测试、项目理解任务
```

Git 分支、文档数、报告数和模型配置不占据首屏主要位置。

### 7.3 研究工作页

采用紧凑的层级表格或树状列表，不使用装饰性卡片或通用看板：

| 工作项 | 人工状态 | 观察状态 | 证据 | 关联运行 | 下一步 |
|---|---|---|---|---|---|

展开工作项后显示验收标准、分支、提交、实验、报告、论文和状态历史。

### 7.4 证据与知识页

按研究问题组织，而不是按存储后端组织：

- 已支持 claims。
- 冲突或不充分 claims。
- 关联论文和本地文档。
- RAG 索引覆盖与过期状态。
- 来源变化和受影响产物。

Chroma collection、embedding 维度、chunk 数量等技术信息放入可展开的索引诊断区。

### 7.5 活动与运行页

使用统一任务表：

| 任务 | 关联工作项 | 状态 | 阶段 | 耗时 | Token/成本 | 产物 | 操作 |
|---|---|---|---|---|---|---|---|

支持查看事件、取消、重试、恢复和打开产物。失败状态必须说明原因、影响和建议动作。

### 7.6 配置页

分为三组：

1. **基础**：路径、项目类型、测试命令、自动化级别。
2. **发现与关联**：确认的纲领、排除文件、产物规则、研究画像。
3. **高级**：模型路由、预算、远程检查、论文源、索引策略。

自动发现的值显示“检测结果”和来源，不直接伪装为用户配置。

## 8. 自动文档发现与项目理解

### 8.1 发现范围

默认扫描：

- 根目录约定文档：PROJECT、README、AGENTS、DESIGN、PRODUCT、PLAN、ROADMAP、CHANGELOG。
- `docs/`、`notes/`、`experiments/`、`reports/`、`papers/` 等候选目录。
- Markdown、纯文本、PDF、DOCX、Notebook、YAML、JSON、CSV/TSV 等支持提取的文件。
- Git 历史中最近修改且当前仍存在的研究相关文档。

遵循：

- `.gitignore`。
- 内置噪声目录，如 `.git`、虚拟环境、构建目录、依赖目录和缓存。
- 用户项目排除规则。
- 单文件大小、文件数量和总文本预算。

### 8.2 分阶段处理

#### D0：目录与身份发现

- 只读取路径、大小、修改时间和文件类型。
- 计算候选优先级，不读取大文件正文。
- 建立 `ProjectDocument` candidate 记录。

#### D1：确定性解析

- 对变化文件计算内容哈希。
- 使用结构化解析器提取标题、目录、Markdown 标题、Notebook 单元、PDF 页码和 DOCX 段落。
- 保留路径、行号、页码和内容区间。
- 解析失败保留 `partial/failed`，不阻断其他文档。

#### D2：规则分类

- 根据文件名、目录、标题和结构判断文档类型。
- 规则只用于候选分类和优先级，不能自动确认为权威文档。
- 输出分类理由和置信度。

#### D3：增量语义理解

- 只发送新增或变化文档的受控片段。
- 提取目标、研究问题、假设、里程碑、实验、决策、结论、风险和后续行动候选。
- 每个候选必须绑定文档位置。
- 模型输出经过 Schema、来源、长度和噪声校验。
- 模型不可用时保留规则发现结果，状态为 `unreviewed`。

#### D4：人工确权

- 用户确认项目纲领、计划文档和需要排除的噪声来源。
- 确认后更新 `ProjectDefinition`，不修改原始项目文档。
- 文档内容变化后，旧确认保持身份但进入 `stale` 复核。

### 8.3 增量策略

- 监听器只产生“可能变化”事件，最终以哈希确认。
- 文件删除、移动和重命名必须保留旧身份与迁移关系。
- 未变化文件不重新解析、不调用模型。
- 文档索引版本由解析器版本、规则版本和内容哈希共同决定。
- 关闭监听或平台不支持时，使用有界轮询和手动刷新降级。

## 9. 项目状态构建机制

### 9.1 Collector

采集器只产生规范事实，不生成用户结论：

- `GitCollector`
- `DocumentCollector`
- `ArtifactCollector`
- `TestCollector`
- `RunCollector`
- `KnowledgeCollector`
- `PaperCollector`
- `EvidenceCollector`

每个 Collector 声明输入版本、超时、增量游标、产生事件和错误语义。

### 9.2 Project State Builder

State Builder 消费规范事件并创建快照：

1. 读取最近快照。
2. 应用新事件。
3. 重新计算受影响分区，不重算整个项目。
4. 运行确定性健康规则。
5. 写入不可变快照和当前物化视图。
6. 产生需要模型分析或人工复核的后续 Job。

### 9.3 状态推断

确定性规则优先处理：

- 测试通过/失败。
- 产物是否存在及是否变化。
- Git 分支、提交和工作区状态。
- 索引是否覆盖最新文档版本。
- 证据来源是否变化。
- 运行是否完成、超时、失败或取消。

模型只处理：

- 文档内容对应哪个研究问题或工作项。
- 多项证据是否共同支持状态变化建议。
- 当前阻塞和下一步的研究语义解释。
- 新论文或研究报告对计划的潜在影响。

### 9.4 状态写入门禁

- 观察事实自动写入。
- 模型建议写入 `ReviewItem`。
- 用户确认后才写入 Declared State。
- 写入前校验输入快照仍是当前版本；过期建议必须重新分析或显式确认。

## 10. 跨功能联动设计

### 10.1 论文雷达

- SearchIntent 必须关联 `project_id` 和可选 `work_item_id`。
- 新论文显示其覆盖的研究问题、证据缺口和推荐动作。
- 保存论文后可触发全文获取、知识库入库候选和 RAG 索引任务。
- 论文评审失败保持 `unreviewed`，不能成为里程碑完成证据。

### 10.2 研究查询

- 从工作项触发查询时自动带入研究问题、已有证据、已知缺口和预算。
- 查询完成后将 ClaimRecord、EvidenceRecord、报告和成本指标关联到工作项。
- `insufficient/uncertain` claims 自动形成证据缺口候选。
- 报告建议不能自动写入计划，必须进入复核队列。

### 10.3 RAG 与知识库

- 展示项目文档总数、可索引数、已索引版本、过期版本和解析失败。
- 项目快照保存 collection、embedding、chunker 和 corpus 版本。
- 文档变化后只标记受影响索引范围，不自动执行高成本全量重建。
- RAG 失败案例可以关联工作项并进入检索评测集。

### 10.4 Git 与分支

- 允许用户把当前分支关联到 Workstream 或 Experiment。
- 根据分支名、提交信息和文件改动提出关联建议，但必须人工确认。
- 显示分支是否脏、是否领先/落后以及关联工作项验收状态。
- P3 不执行分支创建、切换、合并、rebase、push 或 PR 操作。

### 10.5 实验与产物

- 支持用户定义实验产物规则和成功判据。
- 新产物按路径、manifest 或运行记录关联 Experiment。
- 文件时间戳只能表示变化；实验完成必须有可验证状态、指标或用户确认。
- 失败实验保留并可进入风险或下一步，不删除、不隐藏。

### 10.6 Evidence Ledger

- 来源版本变化映射到 claims、报告、工作项和周期摘要。
- 复核页显示来源变化前后差异及影响路径。
- 重新查询、重新生成报告或维持原判断均作为显式决策记录。

### 10.7 周期摘要

- 周期摘要读取已确认的 Declared State 和 Observed State。
- 只引用快照内证据，不重新扫描整个项目。
- 自动区分真实进展、进行中活动、失败实验、风险和下周期建议。

## 11. 技术架构

### 11.1 模块边界

现有模块调整：

- `project_events`
- `project_snapshots`
- `project_current_state`
- `project_reviews`
- `project_review_impacts`
- `project_discovery_cursors`

大正文和快照大对象使用 Artifact/Object 存储；SQLite 只保存索引、关系、状态和内容哈希。

### 11.3 权威来源

- 项目定义和用户确认计划：YAML。

- RAG 向量：可重建派生索引。

禁止 YAML 和 SQLite 同时保存同一权威字段。SQLite 可以保存 YAML 的版本哈希和只读投影，不成为第二写入源。

## 12. 配置模型

### 12.1 自动化级别

```text
observe   只采集本地事实，不调用模型，不自动运行测试
suggest   后台生成项目理解和行动建议，所有写入需确认
managed   允许已批准的周期测试、雷达和索引增量任务
```

默认 `suggest`，但没有模型凭证时自动退化为 `observe`，并明确说明缺少哪些增强能力。

### 12.2 基础配置

- 项目路径。
- 项目名称，可自动取目录名。
- 项目类型，可自动建议。
- 可选测试命令。
- 自动化级别。

### 12.3 高级配置

- include/exclude glob。
- 权威纲领和计划文档。
- 产物识别规则和实验 manifest。
- 模型路由、单次预算和周期预算。
- 论文来源、周期和候选上限。
- 远程 Git 检查频率。
- 文档解析器和 RAG 索引策略。

每项配置必须显示默认值、影响范围、是否产生网络/模型调用、成本风险和恢复方式。

## 13. 性能、成本和可靠性指标

以下指标是 P3 验收目标，不代表当前能力。

### 13.1 页面与 API

| 指标 | 目标 | 测量条件 |
|---|---:|---|
| 已缓存项目状态 API P95 | <= 300 ms | 本地 SQLite，单项目快照 <= 5 MB |
| 项目首屏可交互 P95 | <= 800 ms | 典型本地开发机，不等待后台任务 |
| 页面状态事件可见延迟 P95 | <= 1 s | Worker 已提交 EventStore |
| 切换项目 P95 | <= 500 ms | 两个项目均已有快照 |
| 首屏阻塞模型调用 | 0 次 | 所有项目规模 |
| 首屏阻塞远程请求 | 0 次 | 所有项目规模 |

### 13.2 发现与增量刷新

| 指标 | 目标 | 测量条件 |
|---|---:|---|
| 10,000 文件初次路径发现 P95 | <= 15 s | 排除依赖/构建目录，不阻塞首屏 |
| 100 个变化文件增量确认 P95 | <= 2 s | 内容哈希和元数据更新 |
| 本地 Git 状态采集 P95 | <= 500 ms | 普通仓库，不访问远程 |
| 远程 Git 检查超时 | <= 5 s | 异步任务，失败不影响本地状态 |
| 未变化项目模型调用 | 0 次 | 文档与规则版本均未变化 |
| 增量解析重复率 | < 1% | 相同哈希和解析器版本不得重复处理 |

### 13.3 文档理解质量

建立至少 3 个真实项目、每个项目不少于 20 份候选文档的人工标注集：

| 指标 | 目标 |
|---|---:|
| 权威文档候选 Recall | >= 0.90 |
| 自动确认为权威的错误数 | 0，系统不得自动确权 |
| 文档类型 Macro-F1 | >= 0.80 |
| 抽取项来源定位有效率 | 100% |
| 噪声计划条目进入可确认列表比例 | <= 5% |
| `completed` 状态建议证据充分率 | >= 0.95 |

### 13.4 用户体验

| 指标 | 目标 |
|---|---:|
| 添加项目必填字段 | <= 3 个 |
| 添加项目到首个可用概览 | <= 30 s，深分析可继续后台运行 |
| 定位当前重点/阻塞/下一步 | 中位数 <= 15 s |
| U1-U6 任务完成率 | >= 90% |
| 单个复核项完成操作 | <= 3 个主要交互步骤 |
| 核心流程键盘可达率 | 100% |
| 320px 宽、200% 文本缩放 | 无内容重叠和水平功能丢失 |

### 13.5 成本

- 页面浏览零模型成本。
- 项目理解只处理变化文档，缓存键包含文档哈希、解析器、Prompt 和模型版本。
- 默认单项目单次项目理解输入上限 20,000 tokens；超出后按文档优先级分批，不截断为无定位摘要。
- 默认单项目每日自动分析预算可配置，预算耗尽后保留 pending 状态，不静默跳过。
- 所有模型任务记录输入/输出 tokens、供应商 usage、耗时、模型和估算成本；缺少 usage 时标记 unknown。

### 13.6 可靠性

- 服务重启后 queued/running 项目任务可恢复或按 lease 回收。
- 同一事件重复消费不产生重复 WorkItem、Review 或快照。
- 旧快照和旧文档版本不可覆盖删除。
- 项目目录暂时不可访问时保留最近快照并标记 stale/error。
- 单个解析器、模型或远程检查失败不能阻断其他状态采集。

## 14. 安全与隐私

- 默认本地处理项目文件，不上传完整项目。
- 模型调用只包含明确选中的受控片段和来源定位。
- 不可信项目文档按外部输入处理，不能改变系统指令、工具权限或写入范围。
- 测试任务继续使用脱敏环境，不继承模型和搜索 API Key。
- 文件写入、计划更新、知识入库和高风险操作使用 ApprovalStore。
- 所有路径必须验证位于已登记项目根目录内；符号链接和目录穿越需要明确处理。
- UI 不展示 Secret，日志和 Artifact 必须脱敏。

## 15. 评测与验证方案

### 15.1 固定项目集

至少建立三类项目：

1. Conflux：代码、文档、论文、报告和 Evidence Ledger 均存在的混合项目。
2. GIS Agent 项目：代码和实验为主，文档结构不完整。
3. 文献研究项目：无 Git 或代码较少，以论文笔记、PDF、表格和报告为主。

冻结：项目文件快照、Git revision、文档标注、用户任务、模型配置、Prompt 版本和预算。

### 15.2 评测层级

1. 单元测试：协议、分类规则、状态合并、幂等和门禁。
2. 合同测试：Collector、Repository、Job、API 和 SSE。
3. 回放测试：固定项目事件流和模型响应。
4. 集成测试：真实临时 Git 仓库、文档变化、测试结果和重启恢复。
5. 真实能力测试：三个真实项目的自动发现、理解质量、页面任务和成本。

### 15.3 A/B 对照

比较当前项目页与 P3：

- 首屏时间。
- 完成 U1-U6 的时间和错误率。
- 手工配置字段数量。
- 重复扫描和模型调用次数。
- 用户是否能正确区分人工计划、机器事实和模型建议。
- 项目理解中有来源定位的条目比例。

同一项目和任务顺序需要平衡，避免只用 Conflux 本身调优后宣称泛化。

- 未变化文档零重复模型调用。
- 解析失败可见且不阻断其他文档。

回滚：保留自动发现索引，关闭 D3 模型分析并退化为规则候选。

### P3.3：新项目概览与统一待处理队列

目标：用研究者任务替换当前模块拼接页面。

工作：

- 实现概览、研究工作、证据与知识、活动与运行四个主视图。
- 实现统一 Review Inbox。
- 前端从快照读取并通过 SSE 增量更新。
- 将设置移出主导航，按基础/发现/高级分组。
- 完成桌面、移动端、键盘和 200% 缩放验证。

验收：

- 首屏和任务完成指标达标。
- 页面无同步模型、测试和远程调用。
- 用户能够区分三类状态。
- 所有高风险写入仍需确认。

回滚：保留旧项目页一个版本，通过 feature flag 切换。

### P3.4：研究工作与跨功能关联

目标：建立 WorkItem 与论文、查询、知识、实验和分支的真实关系。

工作：

- 论文雷达支持 `work_item_id` 和证据缺口来源。
- 研究查询产物关联 WorkItem、claims、证据和成本。
- RAG 暴露项目文档覆盖、索引版本和过期状态。
- Git/实验/报告产生状态关联建议。
- Evidence Ledger 影响映射到 WorkItem 和 Review Inbox。

验收：

- 至少两个真实项目完成“缺口 -> 搜索/查询 -> 证据 -> 计划复核”闭环。
- 关联建议均有证据和来源版本。
- 跨功能失败不产生错误完成状态。

### P3.5：周期审计与研究摘要

目标：用统一快照替换独立目录扫描式进度审计。

工作：

- 将 `progress_audit` 迁移为快照比较器。
- 关联验收标准、失败实验、查询和论文变化。
- 生成已确认的周期摘要和下一周期候选。
- 保留现有 Markdown/JSON 导出兼容。

验收：

- 每项真实进展有证据引用。
- 文件数量和模型判断不被包装为完成。
- 旧基线可迁移或明确标记不可比较。

### P3.6：性能收敛与旧路径移除

目标：达到指标并删除长期双路径。

工作：

- 完成性能基准、真实项目 A/B 和成本评测。
- 修复慢查询、快照过大和重复事件。
- 删除旧 JSON 项目缓存写入和旧页面聚合逻辑。
- 保留明确版本的只读迁移工具和 Artifact。

验收：

- 页面、发现、质量、成本和可靠性指标达标。
- 旧路径不再承担主流程。
- 全量测试、迁移测试和真实项目 smoke 通过。

## 17. 迁移策略

### 17.1 现有数据

- `projects/*.yaml` 原样保留并补充版本字段。
- `project_snapshot.json` 和 `progress_audit.json` 作为历史 Artifact 导入，不直接改写。
- 项目监控 JSON 缓存导入为一次性观察快照，并标记 `legacy_import`。
- `plan_analysis.json` 导入为已过期推断结果，不自动形成计划。
- Paper Radar、SearchIntent、ProjectPaper 和 Evidence Ledger 直接通过现有 SQLite 身份关联。

### 17.2 双路径期限

- P3.1-P3.3 允许旧 API 读取新状态适配器。
- 新 UI 稳定并通过真实项目验收后，旧页面只读保留一个发布周期。
- P3.6 删除旧缓存写入和旧聚合逻辑。
- 不允许新旧路径同时写入同一状态。

## 18. 风险与控制

| 风险 | 控制 |
|---|---|
| 自动发现产生大量噪声 | 分阶段发现、规则优先、权威需确认、标注集评测 |
| 项目快照过大 | 分区存储、物化摘要、Artifact 保存大对象 |
| 文件监听不稳定 | 哈希确认、轮询降级、手动刷新 |
| 模型项目理解成本过高 | 变化文档增量、缓存、预算、异步和 `unreviewed` |
| 状态推断误导用户 | 三类状态分离、证据门禁、人工确认 |
| 跨功能关联形成复杂耦合 | 使用稳定 ID、事件和关联表，不直接调用 UI 私有状态 |
| SQLite 写入竞争 | 短事务、Job lease、批量事件、指标监控 |
| 重构形成长期双路径 | feature flag 有删除阶段，P3.6 为强制退出点 |
| 只对 Conflux 调优 | 至少三个不同类型真实项目和冻结 A/B |

## 19. 暂停与升级条件

出现以下情况时暂停当前阶段，不通过继续堆叠规则解决：

1. 自动文档分类在三项目集上无法达到 Macro-F1 0.80，且主要错误来自领域语义而非规则缺口。
2. `ProjectContextSnapshot` 需要复制 EvidenceLedger 或 SearchRun 的权威数据才能工作。
3. 页面仍需要同步执行扫描或模型才能显示可用状态。
4. YAML 与 SQLite 出现同一字段双写。
5. 连续两次修复都要求扩大核心状态协议，说明领域模型尚未稳定。
6. SQLite 在真实项目任务并发下持续出现写入瓶颈，再单独评估 M6 条件，不提前假定需要服务化。

## 20. 启动前确认项

P3 实施前需要确认：

1. 接受 P3 以 Research Workstream 和证据复核为中心，不建设通用项目管理看板。
2. 接受 YAML 只保存人工声明，SQLite 保存观察、事件、推断、关联和复核状态。
3. 接受自动发现可以生成候选，但权威文档和计划状态必须人工确认。
4. 接受页面只读取物化快照，所有测试、远程检查和模型分析异步运行。
5. 接受分支只做关联和状态观察，P3 不执行 Git 修改操作。
6. 接受先完成 P3.0-P3.3 的项目理解与使用体验，再进入论文、查询、RAG 和实验联动。
7. 接受以三个真实项目的任务完成率、证据正确性、性能和成本作为退出依据，而不是仅以测试数量或页面完成度验收。

## 21. 最终退出标准

P3 只有同时满足以下条件才可标记为完成：

- 用户只提供项目路径即可得到可审查项目理解。
- 首屏、增量扫描和事件更新达到第 13 节性能指标。
- U1-U6 任务完成率达到 90%，且用户能正确区分人工计划、机器事实和模型建议。
- 文档发现、来源定位和完成状态建议达到质量门槛。
- 至少两个真实项目完成论文/RAG/研究查询/证据到计划复核的闭环。
- 所有状态建议、进展和周期摘要均可回到规范证据。
- 慢任务均持久、可恢复、可取消，页面不等待模型或远程服务。
- 旧项目监控聚合路径已移除，没有长期双写或双真相源。
- 全量测试、迁移测试、性能评测、真实项目 smoke 和可用性任务均保留可复现证据。
