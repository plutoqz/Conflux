# R1 — RAG 检索消融实验方案

> 日期：2026-07-30  
> 状态：方案定稿，待实施

## 1. 实验目标

定量回答以下三个问题：

1. **Chunk 粒度**：1024/256（当前默认）是否是最优分块策略？粗粒度（2048/512）和细粒度（512/128）在 precision/recall 上如何取舍？
2. **Embedding 模型**：`text-embedding-3-small` vs `text-embedding-3-large` vs `bge-m3`，在中文和跨语言场景下差异多大？
3. **Rerank 方法**：LLM judge（当前 `SemanticReranker`）vs 专用 Cross-Encoder（`bge-reranker-v2-m3-free`、`jina-reranker-m0`），各有什么优势？

## 2. 实验设计

### 2.1 核心原则

- **分层消融，避免组合爆炸**：变量分两阶段独立拟合，不在同阶段交叉
- **前层决策不依赖后层结论**：S1 在无重排条件下做，选定底座后再进 S2
- **单变量原则保留例外**：rerank 对 chunk 粒度敏感是已知限制（细粒度 hamper LLM judge 的上下文理解，粗粒度引入噪声影响 Cross-Encoder 精度），解决方案是 **S1 仅以无重排模式跑**，S2 在最佳底座上单独消融 rerank

### 2.2 实验矩阵

#### S1 — 底座选择（9 组）

| 变量 | 候选值 | 组数 |
|------|--------|:---:|
| **Chunk** | `512/128`, `1024/256`（默认）, `2048/512` | 3 |
| **Embedding** | `text-embedding-3-small`（默认）, `text-embedding-3-large`, `bge-m3` | 3 |

- **固定条件**：无重排（RRF 融合后直接返回）、检索 `top_k=60`（召回池足够大）、数据集 `zh-zh`
- **待选指标**：`Recall@10, Recall@20, MRR@10, NDCG@10`
- **决策标准**：以 `Recall@20` 为主指标（粗召回不能丢信息），`NDCG@10` 为辅助（排序质量）

#### S2 — 重排方法消融（4 组）

| # | 重排方法 | 模型 | 说明 |
|---|----------|------|------|
| 1 | 无重排 | — | 复用 S1 最佳配置结果，作为下界 |
| 2 | LLM judge | `qwen3.7-plus` | 当前 `SemanticReranker`，prompt 打分 relevance + directness |
| 3 | Cross-Encoder | `bge-reranker-v2-m3-free` | BAAI 经典重排模型，输出 query-passage 相关性分数 |
| 4 | Cross-Encoder | `jina-reranker-m0` | Jina AI 重排模型，对比实现差异 |

- **固定条件**：S1 选出的最佳 chunk + embedding
- **API 兼容性风险**：`bge-reranker-v2-m3-free` 和 `jina-reranker-m0` 是 Cross-Encoder，通常通过 `/rerank` 或专用 endpoint 调用，而非 `/chat/completions`。dmxapi 上两个模型均已注册，但需实测确认调用协议。如果 `/chat/completions` 调不通，此维度降级为「LLM judge vs 无重排」

### 2.3 不做的事

| 排除项 | 理由 |
|--------|------|
| Query 翻译 / HyDE | 独立维度（影响召回而非排序），应与 rerank 分离；留作后续 S3 |
| `key_points` + LLM 自动评分 | 引入评估者偏差，无法区分「检索错了」还是「评估者误判」 |
| keyword-only baseline | 中文分词效果差（验证时 recall=0），对检索路径选择无指导意义 |
| `cross_lingual` 配置（dense=0.9） | 代码已自动检测跨语言并调权，非独立实验变量 |
| `dense_only` 配置（1.0:0.0） | RRF 中 BM25 权重被 `1/(rank+60)` 大幅压缩，实际行为与 hybrid 差异极小 |

## 3. 评测数据集

### 3.1 三个评测集

| 评测集 | 语言方向 | 文档来源 | 题数 | 核心场景 |
|--------|:---:|------|:---:|------|
| **zh-zh** | 中文 query → 中文文档 | `data/documents/` 下 .md/.txt（GIS/政策/技术） | 10 | 同语言精确检索上界 |
| **zh-en** | 中文 query → 英文文档 | `data/documents/papers/` 下 .pdf（99 篇学术论文） | 10 | 跨语言检索——最高频且最难场景 |
| **en-en** | 英文 query → 英文文档 | 同上英文 PDF | 10 | 同语言跨语言对照基线 |

### 3.2 标签格式

```yaml
- id: "case_001"
  query: "ArcGIS Pro 中 ModelBuilder 的迭代器类型有哪些？"
  relevant_sources:
    - "esri--arcgis-pro-modelbuilder.md"
  must_contain:
    - "迭代"
    - "Iterator"
  language: "zh-zh"

- id: "case_zh_en_001"
  query: "ShapefileGPT 如何处理复杂多边形边界的拓扑错误？"
  relevant_sources:
    - "2410.12376v2.pdf"
  must_contain:
    - "topology"
    - "boundary"
  language: "zh-en"
```

**评分规则**：
- **grade=3**：source 匹配 + ≥50% `must_contain` 命中
- **grade=2**：source 匹配
- **grade=1**：source 不匹配但 `must_contain` 部分命中
- **grade=0**：source 不匹配且无关键词命中

> 不引入 LLM 自动评分（`key_points`），避免评估者偏差。`must_contain` 字符串匹配在 zh-zh 和 en-en 场景足够可靠；zh-en 的 must_contain 用英文关键词（文档语言），不受 query 语言影响。

## 4. 评测工具链

### 4.1 指标计算：ranx

使用 `ranx`（`pip install ranx`）替代自写指标函数，理由：

- 严格遵循 TREC 标准（NDCG/MRR 实现经学术界验证）
- 正确处理并列排名和空结果边界 case
- 内置 Bootstrap 显著性检验（`ranx.compare`），判断配置间差异是否统计显著
- 输出标准化报告（Qrels + Run → 一键报告）

**指标集**：

| 指标 | 用途 |
|------|------|
| `Recall@10` / `Recall@20` | 粗召回覆盖度（S1 主指标） |
| `MRR@10` | 首个正确答案的排位（对用户可见的 Top-K 敏感） |
| `NDCG@5` / `NDCG@10` | 排序质量（S2 主指标） |

### 4.2 输入格式

```python
# Qrels: {query_id: {doc_id: relevance_score}}
qrels = {
    "case_001": {"esri--arcgis-pro-modelbuilder.md": 3, "esri--arcgis-pro-layers.md": 0},
    ...
}

# Run: {query_id: {doc_id: rank_score}}
run = {
    "case_001": {"esri--arcgis-pro-modelbuilder.md": 0.92, "esri--arcgis-pro-get-started.md": 0.67, ...},
    ...
}
```

## 6. 实施步骤

```
Step 1 — 构建数据集
  ├─ 1a: zh-zh 10 题（基于现有 data/documents/ 中文档）
  ├─ 1b: zh-en 10 题（基于 data/documents/papers/ 中 PDF）
  ├─ 1c: en-en 10 题（英文 query，同上 PDF）
  └─ 1d: 标签自检（must_contain 是否能唯一命中目标文档）

Step 2 — 重写消融脚本
  ├─ 2a: 引入 ranx，替换 evaluate_ranking_full
  ├─ 2b: 实现 S1 矩阵（3 chunk × 3 embedding），--stage s1
  ├─ 2c: 实现 S2 矩阵（4 rerank），--stage s2
  ├─ 2d: 实现 Cross-Encoder reranker 封装（bge-reranker-v2-m3-free, jina-reranker-m0）
  └─ 2e: 验证脚本在 keyword+zh-zh 上可运行（干跑）

Step 3 — 运行 S1（预计 ~30 min）
  ├─ 3a: 索引数据（3 chunk × 3 embedding = 9 个向量库）
  ├─ 3b: 跑 9 组检索
  └─ 3c: ranx 报告 → 选定最佳 chunk + embedding

Step 4 — 运行 S2（预计 ~20 min）
  ├─ 4a: 在最佳底座上跑 4 组 rerank
  └─ 4b: ranx 显著性检验 → 产出最终配置建议

Step 5 — 跨语言验证
  ├─ 5a: 最佳配置在 zh-en 和 en-en 上各跑一遍
  └─ 5b: 三语言对比报告
```

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| Cross-Encoder API 不兼容（需要 `/rerank` endpoint） | S2 从 4 组缩为 2 组 | 先发一个 dry-run 验证 API，失败则 S2 只比 LLM judge vs 无重排 |
| zh-en 标签构建依赖 PDF 文本提取 | 标签不准确，跨语言评测不可靠 | 先抽 3 篇 PDF 试做标签，确认提取质量和标注可行性 |
| 9 个向量库索引耗时过长 | S1 无法一次跑完 | 脚本支持 `--stage s1 --chunk 1024/256` 单独跑一组，分批次 |
| bge-m3 通过 OpenAI compatible 协议行为异常（维度和归一化差异） | embedding 维度不匹配，检索失败 | 先发单个 query 验证 embedding 维度一致性和相似度分布 |
