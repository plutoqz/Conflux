## 0. 文档目的

本文档将《AI Agent 设计原理与工程实践》一书中的 Agent 设计哲学、架构原则和工程实践，映射到 Conflux 的具体优化方向。每个优化项包含三部分：

- **书中怎么说**：该设计的核心理念、关键论断和书中位置。
- **Conflux 现状**：当前 Conflux 在该维度的实现程度和差距（以代码为准）。
- **建议做法**：在 Conflux 中落地的具体方案、预期收益和风险。

**重要约束**：

1. 本文档是 RFC/候选集，不是独立的执行主线。通过评审的条目逐项合并进 `执行计划v1.md`。
2. 所有设计选择以 Conflux 的架构蓝图（`docs/architecture.md`）为上位约束。
3. V2 的 H-K 阶段（真实 A/B 评测、盲评校准）尚未闭合。在评估基线建立之前，不引入新 pipeline 节点或架构性改动。
4. "复杂度增加必须由评估数据证明收益"——这是本书和 Conflux 架构共识的核心原则。

## 1. Harness 工程总论

### 1.1 核心论断（书 §1.2）

> "当各家模型的能力越来越接近、不再是决定性的差异因素时，竞争优势就转移到了模型之外的工程实践。"
>
> "LangChain 的 Coding Agent 从 52.8% 提升到 66.5%（从排行榜 30 名开外跃升至前 5），改变的不是模型，而是 Harness。"

**Harness 五要素**：上下文 → 工具 → 约束 → 验证 → 纠正（构成闭环）。缺少任何一环都会有可靠性缺口。

**构建有效 Agent 三原则**：
1. 保持简单。直接的 API 调用优于复杂框架，清晰的代码优于聪明的抽象。
2. 保持透明。明确显示规划步骤、执行日志和决策轨迹。
3. 设计好工具接口（ACI，Agent-Computer Interface）。从 Agent 视角设计接口，让错误无法发生（防呆/Poka-yoke）。

### 1.2 Conflux 对照

| Harness 要素 | Conflux 已有 | 差距 |
|-------------|-------------|------|
| 上下文 | 系统提示、RAG 检索注入 | 无 Skills 机制、检索结果无中间压缩 |
| 工具 | Plugin 系统 + Capability Registry | 工具描述缺少使用示例和边界条件 |
| 约束 | Policy 校验、Circuit Breaker | 熔断较粗糙，缺少分级降级策略 |
| 验证 | Quality 评分、Audit 节点、FactCheck、P1 配对评审 Rubric、12 题代表集 + 批次退出判定 | 评估体系未覆盖 V2 全链路、未自动化回归 |
| 纠正 | FactCheck 修订、Source Status 降级 | 静默重试不足，失败后缺少自动恢复 |

### 1.3 三种学习范式（书 §1.1.2）

书中将 Agent 的学习机制分为三种范式，这是贯穿全书的基础框架：

| 范式 | 时机 | 持久性 | 成本 | 适用场景 |
|------|------|--------|------|---------|
| **后训练（Post-training）** | 训练时，修改权重 | 永久固化 | 极高（GPU 集群、数天到数周） | 稳定的行为模式、工具调用能力 |
| **上下文学习（In-Context Learning）** | 运行时，注入提示词 | 会话结束消失 | 极低（几个示例 token） | 临时格式适应、一次性任务 |
| **外部化学习（Externalized Learning）** | 运行时，写入外部存储 | 持久、可修正 | 低（一次 LLM 调用提炼） | 领域知识、操作经验、失败教训 |

后训练解决"如何让模型更聪明"，外部化学习解决"如何让 Agent 更能干"——两者互补而非替代。Conflux 作为应用层项目，不涉及模型训练，本文档的优化方向（Skills、经验沉淀）均属于外部化学习范畴。

### 1.4 编排模式选择（书 §1.2.5）

书中提倡"从简单到复杂"原则：单次 LLM 调用 → 工作流 → 自主 Agent。Conflux 已遵循此路径（V2 线性 6 步管道是工作流 + 有限自主的组合）。后续优化也不应为了 Agent 而 Agent——每个复杂度的增加都要有用评估数据证明的收益。

## 2. 上下文工程（书第 2 章）

### 2.1 Agent 状态栏（书 §2.6）

**书中怎么说**：

> "Agent 状态栏是上下文里的一个结构化信息块，由代码确定性维护——当前时间、会话已用 token 数、进度百分比、当前阶段、剩余预算。它让 Agent 不需要'猜'自己在哪里。"

**Conflux 现状**：

- V2 是确定性六步管道，阶段由代码控制，不会由模型自行重复。
- 预算已由 `_deadline_at` 硬执行（`graph_v2.py:318,627`），Agent 无需"猜"剩余时间。
- 注入变化的系统提示会破坏前缀稳定性，与 KV Cache 原则冲突。

**建议做法**：

状态栏的实际价值被显著收窄——它不是让 Agent"自主决策深化/收尾"（V2 的确定性管道不需要），而是让模型在 token 用尽前**提前简化回答**。因此仅注入最少信息：

```yaml
# 裁剪版：两句，注入到系统提示尾部（对 KV Cache 影响最小）
stage: "generate 2/3 sections"
budget: "remaining ~50s / ~35k tokens"
```

- 不注入完整运行状态（sources_retrieved、next_stage、model_calls 等）。
- 仅在剩余预算 < 30% 时追加 `⚠️ Keep answers concise, you are near the budget limit.`
- 实现为简单的 state→text 映射，不修改系统提示词模板本身。

预期收益：
- 模型在 token 不足时提前进入简化模式，减少硬截断。

### 2.2 Skills 机制（书 §2.5 + §8.4.2）

**书中怎么说**：

> "Skills 是把领域操作知识系统性地提炼为结构化的、可按需加载的能力模块。可以把 Skill 理解为一份'岗位操作手册'：新员工入职时不需要从头摸索，读完手册就能上手干活。"
>
> 渐进式披露（Progressive Disclosure）：元数据（常驻上下文）→ 核心流程（按需加载）→ 细则（仅调试时展开）。

**Conflux 现状**：

- 研究流程由硬编码的 Pipeline（graph_v2.py / graph_p15.py）定义。
- 没有"按研究领域加载不同方法论"的能力。

**建议做法**：

用两个真实领域验证 Skills 的可行性，验证通过后再固化格式：

1. 选择两个 Conflux 用户已经实际研究的领域（如 GIS 自动化 + AI 治理），手工编写 Skill 文档。
2. 在 `decompose` 节点前手动注入匹配的 Skill（先不做自动匹配）。
3. 跑 V2 A/B 对比（有 Skill vs 无 Skill），用现有评估框架量化收益。
4. 收益确认后再设计自动匹配机制和稳定格式。

Skill 格式草案（验证通过前不做规范）：
```markdown
---
skill_id: systematic-review
name: "系统综述方法论"
triggers: ["综述", "系统回顾", "state of the art"]
---
## 核心流程
1. 定义研究问题（PICO框架）
2. 系统检索（至少3个数据库）
...
```

### 2.3 上下文压缩（书 §2.7）

**书中怎么说**：

> "上下文腐化——上下文越长、噪声越多，注意力被稀释得越厉害。分层压缩策略：原始轨迹 → 结构化摘要 → 关键洞察。"

**Conflux 现状**：

- retrieve 节点的结果原样传给 generate。
- V2 检索结果通常不大，长研究才可能触发腐化问题。

**建议做法**：

先做简单的"按子问题分配证据"——不新增 LLM 压缩调用，而是让每个章节只接收与该子问题最相关的检索结果（而非全部结果）。这比 LLM 压缩更轻量、更可预测。

如果"按子问题分配"后仍然因为检索结果太大导致质量下降，再评估是否需要 LLM 压缩。届时需用 A/B 评测验证压缩 vs 不压缩的实际收益。

### 2.4 系统提示词工程（书 §2.4）

**书中怎么说**：

> "系统提示词的四层结构：角色与边界 → 业务规则与约束 → Few-shot 示例 → 工具定义。一旦稳定就不要改——因为它的任何变动都会导致 KV Cache 整体失效。"

**Conflux 现状**：

- 已有 YAML Prompt 加载器（`prompts.py:11`——`load_prompt()` + `load_system_prompt()`，指向 `prompts/` 目录）。
- 但并非所有系统提示词都已集中到 YAML；graph 代码中仍有内嵌字符串。

**建议做法**：

将剩余的 graph 内嵌 prompt 逐步迁移到 `prompts/` 目录。稳定后不频繁修改——如需调整行为，优先通过 Skill（§2.2）而非改动核心提示词。这是一次性整理工作，不独立建 Phase。

### 2.5 提示注入防御（书 §2.4.7）

**书中怎么说**：

> "提示注入（Prompt Injection）是 Agent 系统特有的攻击面——攻击者可能通过工具返回的内容、用户上传的文件、网页抓取结果注入恶意指令。"

**Conflux 现状**：

- **已有基础**：`web.py:1542` 的 `_sanitize_untrusted_content()` 实现了中英文提示注入模式匹配 + `prompt_injection_detected` 字段标记。`_blocked_page_reason()` 进一步过滤 CAPTCHA/访问控制页面。
- 但检测覆盖的是 Web 抓取路径——RAG 检索的文档块没有同等级别的消毒（RAG 来源是用户自己入库的论文，攻击面不同但并非零风险）。

**建议做法**：

1. 将 `_sanitize_untrusted_content()` 的调用扩展到 RAG 检索结果入口（低成本改动）。
2. 审计节点（`audit`）增加提示注入检测：检查最终报告是否被外部内容"劫持"。
3. 这是一次性安全加固，不独立建 Phase。

## 3. 项目偏好与持久化（书第 3 章）

### 3.1 项目级偏好替代用户记忆（书 §3.1）

**书中怎么说**：

> "用户记忆系统的本质是一个主动的、持续的学习过程，其目标是构建一个关于用户的简洁而有效的预测模型。"

**Conflux 现状**：

- 没有跨会话的用户/项目记忆。
- **关键约束**：架构蓝图 §9 明确"不允许 LLM 未经确认写入项目权威配置或知识库"。这意味着全自动 inferred memory（LLM 自动从会话提取事实并持久化）与架构冲突。

**建议做法**：

不在当前阶段建独立的用户记忆系统。更契合 Conflux 产品边界的方向是**项目级偏好**——与 M3（持久运行和初始化迁移）联合设计，所有持久写入可审查、可撤销：

1. **项目级研究配置**——每个项目目录下放 `conflux.yaml`，用户手动填写：
   - 研究领域（如 `domain: "GIS/GeoAI"`）
   - 优先数据源（如 `prefer_sources: ["arxiv", "semantic_scholar"]`）
   - 排除数据源（如 `exclude_sources: ["source_x"]`）

2. **已确认的来源偏好**——用户在多次研究后可手动确认"这个来源值得优先检索"→ 写入项目配置。这不是 LLM 自动推断的，是用户显式确认的。

3. **候选记忆机制**（M3 后）——LLM 可提取候选偏好，但仅写入"待确认区"，用户批准后才持久化。这符合架构的"人工确认保留在高风险边界"原则。

4. **历史研究策略复用**——研究完成后，检索关键词和过滤规则写入 run record（而非独立记忆存储），下次可通过 run 历史查询。

预期收益：
- 同一项目内的研究不每次从头开始。
- 符合架构约束（用户显式确认、可审查、可撤销）。

### 3.2 Agentic RAG（书 §3.3.4）

**书中怎么说**：

> "RAG 的四个层次：静态 RAG → 上下文感知 RAG → Agentic RAG → 深度知识提取。"

**Conflux 现状**：

- RAG 是固定 pipeline 节点（`retrieve`），在生成之前执行一次。
- 生成过程中不回溯检索。

**建议做法**：

**条件触发，不独立建 Phase**。等到以下条件满足后再启动：
1. V2 H-K 闭合，评估基线建立。
2. 有具体案例证明"一次检索不够"（检索结果中没有的内容→生成时发现缺口→但因为没有回溯而无法补充）。
3. 不引入模型驱动的工具调用循环（成本不可控），而是用 §2.1 裁剪版状态栏感知缺口 + 代码控制的定向补充检索。

## 4. 工具设计（书第 4 章）

### 4.1 专用工具还是 Skill + 通用执行器（书 §4.2.1）

**书中怎么说**：

> "Agent 的能力有两种基本的表达形态：专用代码工具（结构化函数调用）和 Skill + 通用执行器（自然语言文档描述操作流程）。选择取决于参数复杂度、变更频率和模型能力。"

**Conflux 现状**：

- 当前只有专用工具模式（rag_search、web_search、ask_model）。
- 好处是工具少而精（3 个核心工具），坏处是新增研究策略需要改代码。

**建议做法**：

- 现有 3 个研究工具保持为专用工具（参数稳定、调用频繁）。
- Skills 机制（§2.2）补上"文档描述策略"这条路径。
- 每新增一个能力时按上述三维度判断走哪条路。

### 4.2 工具描述优化（书 §4.2.4）

**书中怎么说**：

> "当 Agent 频繁选错工具时，应优先检查工具描述而不是怀疑模型能力。为每个工具附带 1-5 个真实调用示例——准确率可从约 72% 提升到约 90%。"

**Conflux 现状**：

- **关键事实**：V2 是代码固定调用 RAG/Web，并非模型在 Registry 中动态选工具。因此给 `CapabilitySpec` 增加 `usage_examples` 字段**没有当前消费者**——声称的"工具选择准确率提升"在当前架构下不会自动发生。

**建议做法**：

等到 Conflux 出现真正的动态工具选择场景（如 P2 项目驱动论文雷达需要 Agent 在不同来源间自主选择，或 MCP 集成后工具数量增加需要选工具）时，再增加 `usage_examples` 和 `limitations` 字段。在此之前不修改稳定协议 `CapabilitySpec`。本节仅作为设计原则记录。

### 4.3 参数传递保真性（书 §4.2.5）

**书中怎么说**：

> "一种比功能缺失更隐蔽的反模式是**静默输入转换**——工具在执行前悄悄地'修正'模型的输入参数。模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差。"

**Conflux 现状**：

- `tools/web.py` 的查询在发送前有 URL 编码和关键词处理。
- `tools/rag.py` 的检索可能对查询做分词和规范化。
- 逐工具审查其输入处理链是否对调用方透明。

**建议做法**：

1. 审查所有工具的输入处理链，确认不存在对模型意图的静默修改。
2. 如果查询改写/规范化改变了原始意图，必须在工具返回中标注。
3. 将此原则写入 Conflux 的插件开发文档。

### 4.4 MCP 协议集成（书 §4.3）

**书中怎么说**：

> "MCP 采用客户端-服务器架构。一次开发，处处可用——一个 MCP 服务器可以同时被 Cursor、Claude Desktop、OpenClaw 等任何兼容的客户端使用。"

**Conflux 现状**：

- 插件系统有类似概念（Capability/Plugin），但协议不同。
- 架构蓝图 §5.2 已预留："MCP 可以作为外部能力桥接协议，但必须经过 Conflux 的 Schema、证据分类、权限和审计包装"。

**建议做法**：

**独立条件触发，不与自我进化绑定**。需满足架构蓝图 §10 的"至少两个真实使用场景"原则：

1. **MCP Client**——当用户需要接入的 MCP Server ≥2 个（如 arxiv-search + github-tools）时启动。
2. **MCP Server**——当外部 Agent 需要调用 Conflux 研究能力 ≥2 个场景时启动。

两者各自独立立项，各自独立评估。

### 4.5 通用工具优先（书 §4.2.3）

**书中怎么说**：

> "通用工具优于专用工具，除非存在明确的安全、权限或性能理由。Claude Code 仅需七个核心工具。"

**Conflux 现状**：

- 工具数量合理（rag_search、web_search、ask_model），符合"少而通用"的原则。
- 没有统一的"通用执行器"（如 code interpreter）。

**建议做法**：

code interpreter 暂不引入——等待至少 2 个真实用户场景驱动（如报告中需要生成图表、需要沙盒执行数据分析代码）。

## 5. 评估体系（书第 6 章）

### 5.1 现状复核与增量建议

**书中怎么说**：

> "评估体系的首要价值不是给当前系统打分，而是让你能快速、可靠地跟上模型的演进。"

**Conflux 现状（纠正前版"无"的误判）**：

- **已有**：`p1_evaluation.py` 的匿名配对 LLM 评审 + 六维 Rubric（correctness/breadth/depth/case_specificity/recommendation_value/coherence）。
- **已有**：`research_evaluation.py` 的 12 题代表集（`evaluation/generalized_research_representative_set.json`）、批次退出判定（包括盲评中位数 ≥4.0、连续三批通过等退出线）、`consecutive_batches_reach_exit_line()`。
- **缺口**：评估体系覆盖的是 P1/P1.5，尚未系统化覆盖 V2。V2 H-K 阶段正是要弥补这个缺口。

**建议做法**：

**不做重复建设**——不新建一套评估框架。在现有基建上增量补强：

1. 闭合 V2 H 阶段（真实 A/B 评测），复用现有的匿名配对评审和代表集。
2. 将 Rubric 和 LLM-as-a-Judge 的调用路径从 P1.5 适配到 V2——实质是复用 `p1_evaluation.py` 的评审逻辑。
3. 建立回归测试流程：每次改 Pipeline/Prompt 后跑代表集 + 自动评审，生成回归报告。但不建独立的"评估平台"——集成到现有的 `research_evaluation.py` 即可。
4. 模型替换实验和消融实验作为 conditionally triggered 能力——有模型切换或架构变更时才启动。

**评估数据集设计原则（书 §6.3）**——作为后续扩展评估集时的参考：
- **分布性测试**：覆盖边界和失败场景，不只测成功路径。
- **难度分层**：单步事实 → 多步推理 → 跨来源综合 → 冲突仲裁。
- **配对比较与 Elo 排名（书 §6.5.2）**：判断"新模型/新 Pipeline 是否显著优于旧版本"时使用头对头配对 + Elo 评分而非简单比平均分。

### 5.2 组件级评测数据收集（R 阶段新增）

**设计动机**：

Conflux 简历上声称的三大核心能力——混合检索、证据仲裁与 FactCheck、泛化深度研究——目前均有工程实现但**缺乏组件级量化对比数据**。V2 H-K 的端到端盲评回答的是"管道整体好不好"，不能替代"每个核心组件贡献了多少"。组件级消融数据直接服务于：

1. **简历与面试**：为每条核心能力提供具体数字（"RRF 融合相比纯 Dense 在跨语言场景召回率提升 X%"）。
2. **优化决策**：消融数据揭示当前架构的真实瓶颈，指导后续优化优先级。
3. **回归防守**：每次修改 Pipeline/Prompt 后跑组件级评测，确保核心能力不退化。

**评测设计**：

```
R：组件级评测数据收集（2 周，穿插在 A 和 B 之间）【❌ 未启动】

├─ R1: RAG 检索消融矩阵
│     配置组（5 组）：
│       A. 纯 Dense（ChromaDB similarity_search only）
│       B. 纯 BM25 + jieba 分词（rank_bm25）
│       C. Dense + BM25 简单拼接（取各自 top-k 直接合并，不做 RRF）
│       D. RRF 融合（当前方案，dense_weight=0.7, bm25_weight=0.3）
│       E. RRF + SemanticReranker（当前完整方案）
│     场景组（3 组）：
│       1. 英文查询 × 英文文档
│       2. 中文查询 × 中文文档
│       3. 中文查询 × 英文文档（跨语言场景）
│     共计：5 × 3 = 15 组，每组 10 个查询
│     指标：recall@5, recall@10, NDCG@5, MRR, irrelevant_hit_rate
│     数据来源：复用 scripts/eval_p1_retrieval.py 的 graded relevance 框架，
│              改造为自动化多配置对比
│     产出：消融对比表 + 跨语言退化分析 + 各组件边际贡献
│
├─ R2: Web 搜索质量评测
│     15-20 个时效性查询（如"2025 年大模型推理优化最新进展"）
│     人工标注搜索结果相关性（1-3 分：不相关/部分相关/直接相关）
│     指标：搜索命中率、抓取成功率、有效证据率、provider 贡献分布
│           （DuckDuckGo / Bing / Google / SerpAPI 各自命中占比）
│     产出：Web Agent 独立质量报告 + 薄弱环节识别
│
├─ R3: P1 消融实验数据收尾
│     已有 scripts/eval_ablation.py 的 4 配置（Single / Multi / Multi+Arb / Full）
│     针对 4 个场景查询跑全量数据，收集中间产物：
│       - 各配置的证据节点数量
│       - 共识声明占比
│       - 来源泄露率（非 evidence 来源进入最终报告的比例）
│       - 模型推理来源 对 外部来源 的依赖比
│     产出：消融对比表 + 仲裁机制的边际贡献量化
│
└─ R4: 端到端门禁统计
     用已有评测集（eval_p1.py 的 26 案例 + eval_p1_5.py 的 14 案例）跑一遍：
       - FactCheck 通过率分布（passed / partial / failed）
       - 五维质量分分布（研究过程/回答质量/证据质量/引用质量/核实修订）
       - 门禁实际拦截案例及原因分类
       - 引用覆盖率分布（standard vs deep profile 分别统计）
     产出：门禁有效性报告 + 通过率统计
```

**设计原则**：

1. **一次只测一个变量**：R1 的 5 组配置每次只改变一个组件，保证归因明确。
2. **复用现有基建**：不新建评测框架，直接在 `scripts/eval_p1_retrieval.py`、`scripts/eval_ablation.py` 上增量改造。
3. **数据驱动后续决策**：R 的结果直接影响 D（Skills 验证）、H（Agentic RAG）是否值得启动——如果组件级提升已经接近天花板，就不该在架构层面加复杂度。
4. **与 A（V2 H-K）并行，互不阻塞**：R 跑组件级消融，A 跑端到端盲评，两个维度互补。剩余 9 题 V2 代表集可在 R 进行中作为后台回归。

**与书中评估体系的衔接**：

- 书 §6.3 的"分布性测试"和"难度分层"——R1 的跨语言场景对应分布性（中→英是退化场景），R2 的时效性查询对应难度分层。
- 书 §6.5.2 的配对比较与 Elo——R3 的消融实验形成 4 组配对数据，可进一步用 Elo 排名量化仲裁的净收益。
- 书 §6.4 的"评估必须成为开发流程的一部分"——R 的目标正是把组件评测嵌入到日常开发循环中，而非一次性活动。

## 6. 自我进化（书第 8 章）

### 6.1 外部化学习（书 §8.1-8.2）

**书中怎么说**：

> "模型'记性差'是特性而非缺陷，它逼着我们主动、显式地做知识提炼。学习不会自动发生，必须被显式设计出来。"

**Conflux 现状**：

- 每次研究完全独立，研究完成后不沉淀经验。

**建议做法**：

**与 M3 联合设计，不提前建 jsonl 第二套存储**。方向如下：

1. run record 中已经记录了搜索关键词、来源状态、检索结果。P2 项目驱动论文雷达启动后，利用这些已有记录做研究策略推荐（如"上次类似话题中 ArXiv 来源质量最高，建议优先检索"）。
2. Skills（§2.2）是经验沉淀的更自然载体——把"某领域有效的研究策略"写成 Skill 文档，由用户在验证后手动确认。
3. 不设 reflect 节点、不自动沉淀经验摘要，不新增 LLM 调用路径。

### 6.2 从失败中学习 + 工作流录制

**暂缓**。这两项依赖 M3 持久化、Skills 机制成熟和评估基线建立，不适合在 V2 H-K 未闭合前引入。

书中概念（Reflexion、工作流录制、策略摘要）作为方法论参考保留在本文档中，待前置条件满足后重新评估。

## 10. 书中方法论是否采纳的判断原则

1. **符合架构蓝图**：不违背"本地优先、证据优先、协议优先"三条核心约束。
2. **有真实场景驱动**：至少 1 个已知的 Conflux 使用痛点能被该优化解决（演进原则 §10）。
3. **投入可控**：不要求大规模重写、新增重量级依赖或建设尚不存在的基建。
4. **可独立交付和评测**：每个优化可以独立完成、独立跑 A/B 验证收益，不形成链式依赖。
5. **不影响当前主线的闭合**：V2 H-K 未完成前，不引入新 pipeline 节点。

以下书中提及的方向 **明确不做或暂缓**：

| 书中概念 | 不做/暂缓原因 |
|----------|-------------|
| 可视化拖拽编排器（§1.2.5.4） | 架构蓝图 §9 明确不做 |
| 端到端模型训练 / RL（第 7 章） | 超出 Conflux 范围 |
| 多模态语音/视觉 Agent（第 9 章） | 超出当前产品定位 |
| 大规模多 Agent 社会（§10.6） | 实验性方向，无真实场景驱动 |
| 用户记忆 — 自动 inferred memory（§3.1） | 与架构"LLM 未经确认不得写入知识库"冲突；改为项目级偏好 + 与 M3 联合设计 |
| 睡眠学习 — 离线记忆整合（§8.4.3） | 待 M3 持久化和项目偏好体系建立后评估 |
| 工具自动生成 / MCP-Zero（§8.5） | 风险高，无真实场景 |
| 工作流录制与回放（§8.4 实验 8-2） | 依赖 Skills + M3 持久化基础成熟 |
| 经验沉淀 / reflect 节点（§8.1） | 依赖 M3；当前利用已有 run record 即可 |
