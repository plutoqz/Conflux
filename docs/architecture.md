## 1. 文档职责

本文档只回答四个问题：Conflux 的长期定位是什么、核心边界是什么、扩展应该遵守什么原则、哪些方向明确不做。它不承担任务清单、文件改动列表、数据库迁移脚本或阶段验收记录。

文档职责如下：

- `README.md`：当前已经实现并可复现的能力。
- `PRODUCT.md`：目标用户、产品目的和产品设计原则。
- `DESIGN.md`：工作台视觉和交互约束。
- `docs/architecture.md`：已批准的长期架构蓝图。
- `docs/plans/execution_plan_v1.md`：已批准并持续更新的第一版实施方案与验收记录。
- 代码、测试和评测产物：当前实现事实的最终依据。

如果蓝图与具体执行方案发生冲突，先停止受影响的实施任务，更新决策记录，再继续开发。不能通过在两个文档中分别维护不同解释来解决冲突。

## 2. 产品定位

Conflux 是一个本地优先、证据治理优先、可扩展的 ResearchOps 运行时。它连接：

```text
研究画像 -> 论文发现 -> 知识入库 -> 证据调研
     -> 报告与决策 -> 项目计划 -> 进度审计 -> 证据复核
```

目标用户是具备一定技术基础的研究生、个人研究者和需要维护本地研究工作区的工程人员。Conflux 提供基础能力、运行设施、证据协议、评测和人工门禁；用户可以通过配置或代码接入自己的数据源、算法和研究流程。

Conflux 不是通用聊天机器人，也不是试图覆盖所有研究领域的全包产品。

## 3. 已批准的核心方向

### 3.1 基础执行与语义判断分离

确定性逻辑适合处理数据读取、去重、格式解析、硬性过滤、索引写入、Schema 校验、文件审计和安全门禁。

搜索结果和论文的语义相关性、研究价值、证据质量、排序和是否需要深评，必须由 LLM 结合研究上下文判断。关键词重合、固定权重或传统相关性分数只能用于扩大召回、粗排、异常过滤和压缩上下文，不能作为主要结论。

LLM 评审结果必须保留理由、置信度、不确定性和模型/Prompt 版本。LLM 不可用时，结果标记为 `unreviewed` 或延后处理，不得静默回退并自动入库。

### 3.2 多智能体是执行策略

多智能体用于拆分检索、分析、仲裁、综合、核查或开放式计划等职责，但不以 Agent 数量作为产品目标。普通任务可以使用一个分析节点；冲突、高风险或证据不足时再增加批评、仲裁或深化节点。

### 3.3 证据是一等对象

结论必须能够回到来源快照、论文或文件身份、精确引用区间、提取步骤、模型判断和最终报告。证据应支持声明、支持关系、矛盾关系、替代关系和受影响产物的计算，而不是只在 Markdown 末尾拼接引用。

### 3.4 人工确认保留在高风险边界

知识入库、项目计划写入、文件覆盖、高风险结论接受和不可逆副作用必须经过明确确认。模型可以提出候选、差异和理由，但不能单独成为权威写入者。

## 4. 总体架构

```text
CLI / Workbench / Scheduler
            |
      Application API
            |
  Workflow Runtime + Policy
            |
  Capability / Plugin Registry
            |
Research | Papers | Projects | Audit | Knowledge
            |
Repositories | Run Store | Artifact Store | Vector Index
```

架构采用模块化单体作为当前形态，并为后续替换存储、Worker 和插件运行时保留适配器边界。当前不以微服务数量或分布式组件数量体现成熟度。

### 4.1 核心层

核心层负责运行上下文、步骤状态、事件、预算、取消、审批、策略、Artifact 引用和存储端口。核心层不包含具体 Web 搜索、论文来源或领域算法。

### 4.2 扩展层

扩展层提供稳定的 Plugin、Capability、Workflow、Policy、Evaluator 和 Renderer 协议。第一方功能必须通过同一协议接入，避免核心专门为内置功能保留另一套通道。

### 4.3 适配层

适配层连接模型服务、RAG、Web、Chroma、SQLite、文件系统、CLI、HTTP 和工作台。适配器可以替换，但不能改变证据、审批和运行状态的语义。

## 5. 扩展模型

### 5.1 扩展类型

- `Connector`：连接 Zotero、GitHub、数据库、搜索服务或内部知识库。
- `Capability`：执行检索、解析、模型评审、索引、Git 检查等原子操作。
- `Workflow`：组合能力、智能体节点、条件路由和人工确认。
- `Policy`：控制预算、权限、重试、证据门禁和人工升级。
- `Evaluator`：计算引用、证据、成本、延迟和领域质量指标。
- `Renderer`：生成 Markdown、HTML、JSON 或其他导出格式。

### 5.2 扩展边界

扩展接收声明的输入和受限运行上下文，不直接持有完整工作流状态，也不依赖核心私有对象。扩展通过结构化 `StepResult` 返回状态、输出、证据引用、产物引用、指标和错误。

每个扩展应声明：

- 唯一 ID、版本和 Conflux SDK 兼容范围。
- 输入输出 Schema。
- 配置和 Secret 引用。
- 文件、网络、模型和副作用权限。
- 超时、资源限制、幂等性和迁移策略。

第一阶段只支持用户明确安装并信任的进程内插件。后续只有在真实服务化或隔离需求出现时，才增加子进程或远程运行时。MCP 可以作为外部能力桥接协议，但必须经过 Conflux 的 Schema、证据分类、权限和审计包装。

### 5.3 用户自定义方式

- YAML：组合已安装能力、声明输入输出、条件、预算和审批点，不执行任意 Python。
- Python SDK：实现新连接器、领域算法、评测器和复杂工作流。

不建设面向非技术用户的可视化拖拽编排器。用户可以使用文本化工作流、Schema 校验、静态检查、Dry Run 和文本图预览。

## 6. 工作流语义

工作流节点分为三类：

- `deterministic`：数据读取、去重、解析、硬过滤、索引、Schema 校验和文件审计。
- `agentic`：搜索/论文语义评审、研究价值判断、证据质量评审、比较、综合、冲突解释、开放式计划和核查。
- `human`：知识入库、计划写入、文件覆盖和高风险结论接受。

工作流必须有明确输入输出、稳定版本、循环停止条件、预算和副作用策略。查询深度由证据覆盖、来源独立性、冲突、时效性、风险、预算和用户选择共同决定，而不是固定打开所有循环。

成熟深度研究应用的查询规划、多轮搜索、来源扩展、并行探索、上下文压缩、报告生成和递归深化可以作为方法参考，但 Conflux 通过证据协议、成本预算和离线评测决定是否采用，不复制无必要的流程复杂度。

## 7. 数据蓝图

### 7.1 权威数据

- 项目和研究画像定义。
- 用户的论文筛选与知识入库决策。
- 审批记录、工作流运行状态和证据关系。
- 原始来源快照或可验证的来源身份。

### 7.2 派生数据

Chroma 向量索引、缓存、临时检索结果和预览均可重建。索引必须记录 embedding、chunker 和语料版本。

### 7.3 产物与 Secret

报告、Trace、Evidence JSON、审计结果和导出文件作为不可变 Artifact 管理。API Key 和访问令牌只通过环境变量、系统 Keyring 或受控 Secret 服务提供，不进入 Prompt、日志、普通数据库字段或插件状态。

### 7.4 部署演进

本地模式使用 SQLite、对象目录和本地向量索引；团队模式再根据真实需求替换为 Postgres、对象存储、独立 Worker 和隔离插件运行时。Repository、ArtifactRef、Workflow 和 Evidence 语义不因存储替换而改变。

## 8. 差异化主线

### 8.1 Evidence Ledger

保存来源快照、声明、引用区间、支持/矛盾/派生关系、LLM 评审和报告转换链，支持版本和影响分析。

### 8.2 ResearchOps 闭环

让论文、知识、证据、报告、项目计划和进度审计共享实体关系，用户能够从计划结论回到原始证据，也能从来源变化发现需要复核的旧结论。

### 8.3 工作流评测

比较不同检索器、LLM 评审、Prompt、模型、预算和深化策略，关注相关性、证据覆盖、引用正确率、冲突识别、失败来源泄漏、成本和延迟，而不是页面数量、报告长度或 Agent 数量。

### 8.4 示例扩展

第一方示例用于验证 SDK、领域适配和文档体验。具体名单不在蓝图中固定，待扩展协议稳定后按真实价值、数据可得性、维护成本和边界覆盖单独选择。

## 9. 明确不做

- 不建设通用低代码平台或可视化拖拽编排器。
- 不把所有 Python 函数包装成 Agent。
- 不以搜索页面数、报告长度或 Agent 数量与深度研究应用竞争。
- 不在当前阶段建设插件商城、复杂微服务集群或多租户 SaaS。
- 不自动提交、推送、切换或修改用户 Git 仓库。
- 不允许 LLM 未经确认写入项目权威配置或知识库。

## 10. 演进原则

- 没有至少两个真实使用场景的抽象不进入稳定核心。
- 发现边界错误、重复数据流或长期兼容层时，优先修正而不是继续扩展。
- 测试集中在协议边界、关键状态转换、证据正确性、迁移和高风险副作用。
- 安全措施由当前威胁模型驱动，先保护 Secret、路径、插件权限、审批和不可信内容，不提前建设未被需求触发的分布式安全体系。
- 核心离线测试保持快速，真实模型、网络、压力和高成本评测按变更风险分层运行。
- 每个实施阶段结束后复盘抽象复用、技术债、测试成本、安全边界和用户体验，必要时回到蓝图修订方向。
